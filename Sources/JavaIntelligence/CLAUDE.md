- **`JavaIntelligence`** — native Java indexing and completion (JDK discovery, source and JAR stubs, type resolution, completion) with **no dependency on `Penumbra`**. Umbra wires it through `Umbra/Sources/Umbra/Intelligence/IDEJavaSupport.swift`. Completion (`Sources/JavaIntelligence/Completion/`) parses with a dummy identifier at the caret (`JavaCompletionProvider.dummyIdentifier`), types lambdas and method references through the target parameter's functional interface, resolves source members against their declaring file's imports, classifies the site (`JavaCompletionContextClassifier`: member access, `::`, import/package, `@`, `new`, type-only, `case`, class body, statement), ranks by expected type (`JavaExpectedType`, `JavaAssignability`), auto-imports classes and, for classes listed in `JavaImportPolicy.staticMemberClasses`, their public static members (`JavaImportInserter`, `JavaImportPolicy`; excluded classes stay out even on a second Ctrl+Space), offers `@Override` stubs in class bodies, and doubles as parameter info (`JavaSignatureHelp.swift`). For a Gradle project, a trusted sync (`GradleCommandRunner` plus an init script) replaces the whole-folder `.java` walk with per-module source sets and resolved dependency JARs. Go to Definition (`Sources/JavaIntelligence/Navigation/`) resolves into attached sources when present (a JDK `lib/src.zip` or a dependency's adjacent `*-sources.jar`, via `JavaAttachedSources`) and otherwise falls back to decompiling the `.class` file with [Sunflower](https://github.com/alex-cova/sunflower) (`FernflowerKit`, `JavaClassDecompiler`) — gated by a one-time user agreement (`JavaDecompilerAgreement`) that only a manual navigation (never Cmd-hover) can trigger, via `JavaGoToDefinitionProvider.setDecompilerConsent(accepted:request:)`. Compiler diagnostics (`Sources/JavaIntelligence/Diagnostics/`): `JavaCompilerDiagnosticsService` is a `DiagnosticProvider` that runs the JDK's `javac` (`JDKInstallation.javac`) over the editor's text — `JavacInvocationBuilder` builds the command (Gradle source-set classpath/sourcepath, `--release` capped at the JDK, `--add-modules` from the source set's `JavaCompile`, `-proc:none` except a project's own Lombok jar; a plain folder infers its package root), `JavacOutputParser` parses stderr — and returns the last result while a debounced (600 ms idle), cancellable, 2-at-a-time compile runs, pushing finished results through `setResultHandler`. It stays off until Umbra configures it (`IDEJavaSupport.refreshCompilerDiagnostics()`: a plain folder, or a Gradle project that has synced; the `javaCompilerDiagnostics` preference), and `compileNow(_:force:)` backs the recheck after save and after sync. Tree-sitter syntax errors (`JavaSyntaxDiagnostics`: a `SyntaxDiagnosticProvider` over the inspections' shared parse cache, token names in javac's spelling) arrive before `javac` is configured; `JavaSyntaxAwareDiagnostics` pairs them with the compiler run and drops `javac` parser errors on lines a syntax problem already covers. Go to Implementation (`JavaGoToImplementation`) lists the project classes that extend or implement a type, or override a method (through the inheritor table for a project type; a closure scan over `JavaIndex.projectClassStubs()` for a library type, whose project subclasses can pass through library classes; scoped to the file's Gradle source set). The inheritor table (`JavaInheritorTable`, `JavaInheritors`, `Index/JavaInheritorIndex.swift`) maps each written supertype's simple name to the project classes that name it, built like the member table (project shards once off the actor, open buffers per generation); `JavaInheritors.subtypes(of:index:)` resolves the candidates against their declaring files and walks transitively, so it never mixes two classes of the same simple name. It feeds `new ` completion with an empty prefix (project implementations outside the scanned packages), the type hierarchy's subtype expansion and Go to Implementation. JARs and the JDK are never results, but a library class between a project class and the type no longer ends the walk: written supertypes that resolve to a library type below the query seed the queue (the library bridge, verified the same way). `swift run -c release PerfHarness java-inheritors synthetic --files N`. Hover (`Sources/JavaIntelligence/Hover/`): `JavaHoverProvider` shows the declaration (`JavaSignatureText`) and Javadoc (`JavadocMarkdown`) of the symbol at the caret, from source stubs or from an attached `src.zip` / `*-sources.jar` (never decompiled); a resting caret (`.idle`) only pops up when there is documentation, an explicit request (`.manual`) always does. `JavaCodeActionProvider` offers "Import `a.b.X`" for the type name at the caret (from the index, without waiting for javac) and for a `cannot find symbol … class X` error on the caret's line, "Import static `Owner.member`" for an unqualified call or field, and "Replace with single class imports" on a star import. `JavaAutoImport` inserts the one unambiguous class after idle, and the names in a paste, and never imports `List` while both `java.util` and `java.awt` define it. It also offers a remove-unused-imports action (`JavaUnusedImports`, conservative: syntax errors yield no edits, Javadoc references keep their imports, `*` imports stay). `JavaBreadcrumbProvider` labels the caret's enclosing declarations (`Outer<T> › put(String, int)`). `JavacDiagnosticsMapper` turns a whole Gradle build's `javac` output into diagnostics per file, and `JavaRunConfiguration` / `JavaRunConfigurationStore` (`Sources/JavaIntelligence/Launch/`) hold a project's launches (see the run configuration paragraph below). `JavaFormatter` (`Sources/JavaIntelligence/Formatting/`) is a whitespace-only formatter over the tree-sitter tree — indentation (blocks, `case` labels, brace-less bodies, two-level continuation), spacing between tokens, trailing spaces, blank-line runs; it never joins, splits or moves lines, refuses a file that doesn't parse cleanly and any result whose non-whitespace changed. `JavaFormattingProvider` wraps it as a `FormattingProviding` (whole file, or only the selected lines with every line break kept), and `JavaFormatEdits` turns the result into minimal per-line edits so carets stay put. `JavaImportOrganizer` sorts and prunes imports (other, then `javax.*` and `java.*` as one group, then static; a comment inside the block limits it to removal and to point insertion) and collapses a package or static owner into a star at `JavaImportPolicy`'s counts (5 classes, 3 static names; 999 or a non-positive count never collapses). The Gradle model (format version 7) records each source set's runtime jars, runtime project dependencies and output directories; `JavaGradleProjectModel.runtimeClasspath(forFile:)` returns them in `java -cp` order (used by the classpath run target). ⌘-click (Go to Definition) on the name of an abstract declaration — an interface, an abstract class, a non-static non-private interface method, or an abstract method — returns its implementations instead (`JavaGoToImplementation.isAbstractDeclaration`); several ⌘-click targets pop up next to the click in `NavigationChoicesView` (↑/↓, Return, Esc; `JumpToDefinitionController.onPresentChoicesAtClick`), while ⌘B/⌥⌘B still use `onPresentNavigationChoices`. Go to Implementation also finds generic overrides (`compareTo(Foo)` for `Comparable<T>`), anonymous classes and enum constant bodies, and labels/sorts its picker results. `JavaTypeHierarchyProvider` (`Sources/JavaIntelligence/Hierarchy/`) builds the supertype tree (superclass, then interfaces, cycle-safe) and lazily expanded project subtypes; Umbra shows it in the Hierarchy bottom-panel tab (`EditorActionID.typeHierarchy`, ⌃H in the IntelliJ keymap, `EditorIntelligenceController.onRequestTypeHierarchy`). `JavaSemanticTokenProvider` (`Sources/JavaIntelligence/Semantic/`) classifies identifiers (types by kind, methods, fields, enum constants, parameters, locals; locals shadow fields) in one scope-aware pass, and `TextView.setSemanticHighlights(_:)` (`SemanticHighlightStore`) paints them over the tree-sitter colours, colour only, following edits until the next set (Umbra: `semanticHighlighting` preference, on by default). `JavaInlayHintProvider` (`Sources/JavaIntelligence/Inlay/`) produces, per `JavaInlayHintOptions` (a fixed value, or `setOptionsSource` asked at every request), parameter-name hints for calls that bind to exactly one method, and type hints (`InlayHint.Kind.type`, label `: List<String>`) after `var` locals, `for (var …)` variables and implicitly typed lambda parameters. Type hints type the declaration's initializer with `JavaExpressionTyper.resolvingVarLocals` against the locals of the enclosing block (candidates of one block share one resolution; at most 60 declarations per request), skip initializers that already say the type (`new`, a cast, a literal, a factory like `List.of`) and ones that can't be typed (`Object` is what a failed inference falls back to, so it is never shown). `resolvingVarLocals` resolves `var` locals in passes against every other local, because the list is source order within a block. `TextView.inlayHints` (`InlayHint`) renders them by widening the preceding character, so they are display-only (Umbra: `javaInlayHints`, `javaInlayVariableTypes`, `javaInlayLambdaTypes`, all off by default; hints refresh after edits and when scrolling leaves the requested range). Tests: `JavaInlayHintProviderTests`. `JavaCodeVisionProvider` (`CodeVisionProviding`, same folder) gives a lens to every class, interface, enum, record, method and constructor: `codeVisionAnchors(for:)` is one pass over the tree (at most 400, the room for all of them), `codeVision(for:anchors:)` then labels the anchors on screen — `N usages` from `JavaFindUsagesProvider.findUsages`, and for interfaces, abstract classes and abstract or interface methods `N implementations` from `JavaGoToImplementation.resolve`. A search is expensive (it parses the files that mention the name), so results are cached by declaration signature and `JavaIndex.generation` (counts follow what the index knows, i.e. saved files), two run at a time and at most 40 per request. Options (`JavaCodeVisionOptions`) are read through `setOptionsSource`. Tests: `JavaCodeVisionProviderTests`. `JavaRunConfiguration` is now named and kept in a per-project list with a selected entry (`JavaRunConfigurationStore`, old files still load); a `.classpathMain` target launches `java -cp <runtime classpath> pkg.Main`, building the module's `classes` task first when its outputs are missing, and Umbra shows a run configuration picker in the toolbar. References (`Sources/JavaIntelligence/References/`): a persistent identifier index (`JavaNameIndex`, `JavaIdentifierScanner`, `refs.idx` shards via `JavaNameIndexShardWriter/Reader`, beside `sources.idx`; per-file stamps compared with one `getattrlistbulk` pass per directory (`JavaSourceStampScan`), an in-place posting update (`rewrite(from:removing:replacing:to:)`, returning the reader it already built) when a readable shard exists, open-buffer overlay; Umbra refreshes it and force re-indexes stubs when `IDEProjectWatcher` reports `.java` changes on disk) lists the candidate files for an identifier; a persistent role index (`JavaRoleIndex`, `JavaIdentifierRole`, `roles.idx` shards beside `refs.idx` with the same stamps, overlay and incremental rewrite) narrows those by the syntactic role the target kind can match (`JavaSymbolID.candidateRoles`: calls, member accesses, type names, declarations, imports, bare names), so a file that mentions `foo` only as a type is never parsed for a method `foo` — and usages are then verified on demand instead of stored: `JavaSymbolIdentity` maps the caret to a `JavaSymbolID` (type, method with parameter keys, constructor, field, local by declaration range), `JavaFileUsageResolver` resolves every same-named identifier in a file (one parse and reusable context per file; unresolvable overloads or receivers are `.ambiguous`), `JavaLocalUsages` handles locals without the index, and `JavaUsageSearch` fans out over the roots that can see the declaration. `JavaFindUsagesProvider` answers `.references` for Java (methods search every member of `JavaMethodFamily`, which is built from the index only, so unsaved buffers and anonymous classes are not in it); `JavaGoToSuperMethod` answers `.superMethod`. `JavaRenameProvider` (`Sources/JavaIntelligence/Refactoring/`, a `RenameProviding`) renames types (with imports, static imports, Javadoc links and the `Old.java` file), locals, parameters (`JavaRenameProvider`), and methods (the whole override family), fields, enum constants and record components (`JavaMemberRename`); a family member in a JAR, the JDK or a generated root blocks the rename, ambiguous or read-only usages are left out of the edit unless the user ticks them in the preview, and Umbra gives it the same candidate source as Find Usages, `JavaIndexedOrScanningCandidates` (the name index for roots it has a shard for, a text scan only for roots it does not; an open buffer's unsaved text reaches the index through its overlay). Completion quality is tracked by a golden corpus (`Tests/PenumbraTests/Fixtures/JavaCompletionCorpus`: `cases/*.java` with `/*|*/` caret and `//! key: value` expectations, a fixture `project/`, `baseline.json` ratchet; `JavaCompletionCorpusTests`, `JAVA_COMPLETION_CASE=Prefix` to run a subset, `UPDATE_JAVA_COMPLETION_BASELINE=1` to ratchet; plan and gap list in `docs/JAVA_PARITY.md`) and release latency by `swift run -c release PerfHarness java-completion synthetic [--jars N]` and `swift run -c release PerfHarness java-name-index <java-source-directory|synthetic> [--files N]`. Semantics behind it: generic-aware assignability (`JavaAssignability`, `JavaMemberLookup.asSupertype`), JLS overload phases (`JavaExpressionTyper.resolveOverloads`), lambda/poly-expression targets (`JavaExpressionTarget`), type-variable bounds (`JavaResolutionContext.typeParameterBounds`), inherited and dotted nested types, class-file `$` names normalized to `.` (shard format v3). `JavaIndex` has package tables, a decoded-stub cache that drops its oldest entry when full, a `generation` counter and a generation-scoped member-set cache; class names are bucketed by word start the same way members are (`JavaWordBuckets`); `classes(matching:)` ranks with `CompletionMatcher.tier` and decodes stubs only for the names it keeps; `classes(simpleName:)` is the exact simple-name lookup, and `classStub(qualifiedName:)` jumps to the shard that wins the name; the completion provider reparses incrementally. - **Stub reuse while typing** (`Syntax/JavaStubReuse.swift`; numbers in `docs/JAVA_COMPLETION_BASELINE.md`). `JavaCompletionProvider.parse` reparses from its previous tree and, when the one contiguous edit lies strictly inside a method or constructor body, moves the previous `JavaSourceFileStubs` past it instead of rebuilding: `JavaSourceStubBuilder` never reads bodies, and the only ranges a stub carries are the class `nameRange`s, which shift by the edit's length. Reuse requires, in the old and the new tree, the body's start unchanged and its end (and every ancestor's) moved by exactly the delta, a real closing `}`, no stub range inside the replaced bytes, and **no syntax error anywhere outside the body** (tree-sitter recovers from errors globally, so an error elsewhere can re-shape a far declaration when this body is edited; found by the deep campaign, pinned by `testErrorRecoveryElsewhereInTheFileIsNotReused`). Anything else rebuilds. If `JavaSourceStubBuilder` starts reading something new from a body (or a stub gains a range other than `nameRange`), the reuse conditions must change with it. `UMBRA_JAVA_STUB_REUSE=0` turns it off; `JAVA_STUB_REUSE_ROUNDS=40 swift test --filter JavaStubReuseTests` runs a deep random campaign against the full rebuild.
- **Reparse cost after an edit** (`Sources/LanguageSyntax/ParseEdit.swift`, `Syntax/JavaStubReuse.swift`, `JavaCompletionProvider.repairedText`; numbers in `docs/JAVA_COMPLETION_BASELINE.md`). `ParseEdit.diff` (also used by `DocumentParseCache` for every language) finds the common prefix and suffix with blocked `memcmp` and counts newlines once, over the shared prefix, with an eight-bytes-at-a-time count; the old and new end points are that start point advanced over the changed bytes only. `ParseEdit.referenceDiff` / `referencePoint` are the original implementations, kept as the oracle (`ParseEditDiffTests`) and reachable with `UMBRA_PARSE_EDIT_REFERENCE=1`. The completion request's text repair is `JavaCompletionRepair` (it also closes a lambda or body brace opened inside a call that is still open on the caret's line, `closingSequence`) (`Completion/JavaCompletionRepair.swift`): it works on UTF-8 bytes, converts the caret's UTF-16 offset once with `JavaUTF8Offsets` and builds the repaired `String` in one allocation. Do not reach into a large `String` with `NSString`, `utf16.index(offsetBy:)` or `String ==` on the request path: each is O(n) per new string for any text with a non-ASCII character (a file with one `é` made a typing request nine times slower), and `ReferenceRepair` in the tests is the original implementation, used as the oracle. What tree-sitter itself costs after an edit depends on the arity of the nodes on the edit path (a class body with 24,000 members: 17 ms; the same lines in classes of 100 members: 0.3 ms), not on the file's line count. `PerfHarness java-parse-edit synthetic [--per-class N]` times each piece.

- **Shared across windows.** `GradleTrustStore`, `JDKSelectionStore` and `JavaRunConfigurationStore` are used through one instance per app in Umbra, and each reloads its JSON file when it changed on disk (`FileChangeStamp`, which reads the modification date through `FileManager`: `URL.resourceValues` caches per `URL` value and would never see a change) before reading or merging its own change, so a second writer is not overwritten. `JDKIndexRoot.make(for:)` picks the JDK's root: `ct.sym` unless it has no signatures for the JDK's own release (Oracle 21's does not), then `jmods/` (shard kind `jmods-exported`: only packages each module's `module-info.class` exports to everyone, read with `ClassFileReader.unqualifiedExports(ofModuleInfo:)`, like `ct.sym`), so an empty `ctsym` shard is never read; `IDEJavaSupport.indexJDK` also keeps a working JDK reader when the new one has no classes. `JavaSharedShardHub` (`Sources/JavaIntelligence/Scanning/`) runs one indexing pass per shard, hands the same parsed `JavaIndexShardReader` to every caller, and keeps at most four for the JDK shard. For dependency jars (`indexJars(_:)`, `readers(for:)`) it claims each shard once across callers, sends waiters a `rootSkipped` per jar so their counters reach their totals, parses missing readers in parallel, and holds readers weakly while any window uses them; release jars from Gradle/Maven caches (`JavaJarCachePolicy.isImmutableArtifact`) also stay in an LRU bounded by `maxRetainedNames`, and `trimMemory()` empties it. Every request compares the reader's stamp with the shard file's, and the scheduler's freshness check reads only the shard header (`JavaIndexShardReader.readStamp(at:)`), never the whole table. Shard files are written atomically, so another process never reads half of one.

- **Warm `javac` analysis server** (`Umbra/Sources/Umbra/Tools/JavaAnalysisServer/`, client in `Sources/JavaIntelligence/AnalysisServer/`). The server (`com.umbra.analysis.JavaAnalysisServer`, built by `build.sh` with `javac --release 17`, bundled like `java-debug-adapter.jar`) reads JSON lines over stdio and runs a fresh `JavacTask` per `check` over a cached per-module `StandardJavaFileManager`, so classpath jars stay open; the checked file and every overlay are explicit in-memory units, so open buffers shadow the disk. It runs the full pipeline with class output discarded, and reports each diagnostic's `getCode()` key with exact UTF-16 offsets plus the CLI's line/column (which differ for keys like `missing.ret.stmt`, whose span covers the body but whose position is its end). `attribute` resolves the symbols at a list of UTF-16 positions (`Trees.getElement`) and returns each one's kind, simple name, qualified name and, when the declaration was compiled from source, its file and line range. `JavaAnalysisServerClient` (an actor over SubprocessKit, never `Foundation.Process`) starts the server lazily, restarts on crash with backoff, replays `configure` after every relaunch, shuts down after 10 idle minutes, and matches responses by request id; `JavaAnalysisServerHub` shares one client per JDK home across windows. The library ships no jar: Umbra injects the jar URL and JDK. Tests: `Tests/PenumbraTests/JavaIntelligence/Parity/JavaAnalysisServerTests` (skipped without a JDK; `testCheckMatchesCliJavac` proves `check` reports the same places as CLI `javac`). `attribute` is what the differential harness scores Umbra against (`JavaDifferentialTests`, `docs/JAVA_DIFFERENTIAL.md`).

- **Warm diagnostics in the editor (Phase 2).** `JavaCompilerDiagnosticsService` prefers the server when a backend is set (`setServerBackend`, one client per JDK home) and the cold CLI stays the fallback; `JavacInvocationBuilder.resolve` shares the classpath truth between both paths. The server module is reconfigured only on change, checks carry every open Java buffer as an overlay (async provider the host snapshots on the main actor), diagnostics map to exact ranges with `javac:<key>` codes, and the idle wait is host-set from the Autoreparse Delay (`setIdleDelay`; a warm-server backend, when one lands, splits it per backend with a zero server wait). Same-text refreshes never restart a waiting or running compile (`force` on `schedule` is the only restart channel). `JavaDiagnosticsMerger` (inside `JavaSyntaxAwareDiagnostics`, which now also folds the inspection service in — there is no separate inspections provider entry anymore) drops inspection findings that restate a fresh keyed `javac` error (`unresolved-*` against `cant.resolve*`, `unreachable-code` against `unreachable.stmt`); unkeyed CLI diagnostics and stale results suppress nothing. The first key-driven quick fixes live in `JavaCompilerQuickFixes` (import rekeyed on the code; *Add throws* / *Surround with try/catch* for unreported exceptions, *Implement methods* for unimplemented abstracts, *Add return statement* for missing returns). Umbra wires the backend in `IDEJavaSupport.refreshCompilerDiagnostics` (JDK 17+ only, jar from the bundle with a repo fallback) and runs `swift run -c release PerfHarness java-analysis-server synthetic` for the warm-check number (57 ms warm median on 2k lines here; the 300 ms exit gate wants the full idle-to-errors path on a synced Gradle project).

- **⌘-click latency and misses** (follow-up). `JavaParseMemo` keeps the last 12 parses (24 MB) that Go to Definition asked for, keyed by length and a 64-bit hash of the text, with the file stubs per path: hovering a word, clicking it, hovering the next one, and a jump into a class that was just opened all reuse the parse (a warm request at 10,000 lines is about 5 ms, down from 28; the first on new text still parses, about 2.8 ms per 1,000 lines). It is also what every feature that parses the buffer once typing pauses shares (semantic colours, gutter markers, breadcrumbs, auto-import, the role index's overlay, hover, the bulb, syntax diagnostics of an untitled buffer): one parse per distinct text, concurrent requests for it waiting on the parse in progress instead of starting another (a 120-character burst in a 20,000-line file measured ten full parses of one text before, `IDEHostEditCostTests`). Trees it hands out are shared and read-only (edit a `copy()`); bulk work such as indexing a project does not go through it. It is not `JavaDocumentParseCache`: that one keeps one tree per file and edits it, and reuses by the text of the document, never its version (the adapter's snapshot, the editor's live document and a completion request number their documents on their own, so a version comparison missed and re-parsed the file from scratch). `JumpToDefinitionController` copies the buffer once per `contentGeneration` and hands a click the result ⌘-hover already found for the same word in the same text (`cachedHoverResult`). Measure with `swift run -c release PerfHarness java-goto-definition synthetic [--lines N]` (click and hover, cold and warm, per kind of site; the request is built before the timer starts, and `PENUMBRA_GOTO_SITE=jdk_type` keeps one kind of site so a sampler sees only it). Warm costs that used to grow with the file or repeat per click: `SyntaxNode.children`/`namedChildren` were quadratic (`ts_node_child(i)` per index; now one cursor walk, which every Java feature that lists a type's members gained from), `JavaNavigationText.textRange`/`position` scanned the text through `NSString.character(at:)` once per end (now one pass over the UTF-8 bytes, `LineScan`), `utf8ByteOffset` copied the prefix, and a JDK or dependency click re-opened `src.zip` and parsed its ~30,000-entry central directory (`ZipArchiveCache`: six archives kept, re-opened when the file's size or modification date changes; the extracted copy under `attached-sources` is rewritten only when it is stale). Release, 20,000-line current file, warm click: project symbols 0.25 → 0.16 ms, local variable 3.2 → 0.6 ms, JDK type or method 5 → 0.3 ms; a click on a name the current class declares still costs ~1.8 µs per member of that class (the live stubs bypass the shared member cache), 6 ms at 3,300 members. Tests: `JavaNavigationTextTests` (against the `NSString` walk), `SyntaxNodeChildrenTests`, `ZipArchiveCacheTests`. Constructors narrow by argument types as methods do (`new Foo("m", cause)` goes to `Foo(String, Exception)`); an argument whose type cannot be determined leaves every candidate (`refine`), instead of letting the overload resolver guess. ⌘-click on the name of a method that overrides or implements another goes to that method. A request sees the buffer's own classes (`JavaIndex.liveStubs`, a task-local that `JavaNavigationSession.withLiveStubs` sets and that bypasses the shared member cache), so code typed a moment ago resolves before the overlay's 300 ms debounce catches up. Corpus: 172 cases, among them the shapes real services are made of (generic repositories, `Optional` and stream chains, builders, inherited generics, exceptions).
- **First completion in a file (cold member lookup).** `JavaMemberLookup` reads the file a *source* class is declared in (package and imports) to resolve the names in its signatures, and resolving one simple name (`nestedType`) walks the supertypes of the class around it (`ancestorQualifiedNames`, which makes a fresh `DeclaringFileCache` per call). That read used to parse the file with its own `JavaSyntaxParser` every time: on a 500-line project class (`Context` in ecs-deployer, 68 members) the first `.` after opening a file cost ~110 ms of the provider's ~125, nearly all of it re-parsing the same declaring files (the file being edited parses in ~1 ms). `contextOfDeclaringFile` now goes through `JavaParseMemo.shared.parsed(source:url:)`: same text, same tree and stubs, one parse per distinct text. Real projects, first request in a file, first draw median: ecs-deployer 130 → 28 ms, sxb-stock 61 → 33 ms (p95 163 → 49). Tests: `JavaDeclaringFileMemoTests` (same members with an empty and a warm memo, changed bytes never answered from an older parse, eviction, missing file, NFC vs NFD kept apart). The provider's own parse of the edited file is deliberately *not* seeded from the memo: it parses the *repaired* text (dummy identifier at the caret), whose bytes no feature has parsed, and the memo's key is length plus a 64-bit hash, which cannot prove byte identity; the first request in a 120,000-line file still costs ~330 ms of parse (`docs/JAVA_COMPLETION_BASELINE.md`, "End to end"). Stage timers `members.declFileRead/declFileBuild/resolve` show where a cold member walk goes. `JavaIndex.hasSubpackages(of:)` answers the typer's "is this name a package prefix" from a set (the scoped package pool is cached per generation, scope and module visibility) instead of rebuilding it per call.
- **Hardening pass (saves, non-ASCII, file switches).** (1) `JavaIndex.setSources` is `async` and builds the name tables in a detached task, then swaps them in with the rest of the state in one step (`sourcesBuildToken`: an overtaken call returns without applying; `sourcesBuildHook` is the test seam). It used to run inside the actor, so a completion asked after a save waited the whole rebuild (~200 ms at 46,000 names, ~650 ms at 146,000); now it is answered from the previous sources (0.5 ms). (2) `JavaNavigationText.fullText` returns a native UTF-8 string (`nativeUTF8`): the document text arrives backed by `NSString`, and with any non-ASCII character every `withUTF8` / `Array(text.utf8)` on it walked the text one UTF-16 unit at a time through `characterAtIndex` (41 ms of repair at 120,000 lines; warm first draw 54.6 → 19.9 ms). Convert once, in bulk, where a string enters; do not add `withUTF8` on a string of unknown origin on a hot path. (3) The controller drops a popup and the request in flight when the adapter's current document is not the one they were made for (`completionDocumentID`), because a tab switch is `setState` on the same `TextView`. (4) `JavaParseMemoStatistics` (`@_spi(Benchmarks)`) counts hits, parses, evictions and re-parses of just-evicted text; capacity 12 measured sufficient. Measurements and what was not built (layered base index, per-file stub shards): `docs/JAVA_COMPLETION_BASELINE.md`, "Hardening pass".
- **Completion quality (recall, ranking, insertion).** `docs/JAVA_COMPLETION_QUALITY.md` has the oracle, the per-context numbers and the limits; `JAVA_QUALITY=1 swift test --filter JavaCompletionQualityTests` reproduces them on gson and jackson-core (`JAVA_QUALITY_STATS=1` adds the usage counts the app has). Rules that came out of it: an expected type belongs to the *whole* expression, so a bare identifier followed by `.`, `[`, a comparison/arithmetic operator or `instanceof` gets none (`JavaExpectedType.continuesAsLargerExpression`); `throw` expects `Throwable`; with no expected type after `new`, every in-scope class is a candidate (the capped classpath search alone loses `java.lang`); a variable bounded `A & B` has the members of both (JLS 4.9), not the common ones. What an accepted item writes next to existing text (`foo|(x)`, `new Foo|<T>()`, `(Foo|)`) is `EditorIntelligence/Completion/CompletionInsertion.swift`, shared by the controller and the harness — change it there, not in the controller.
