# Java profiling model (`Sources/JavaIntelligence/Profiling`)

Loaded when working under `Sources/JavaIntelligence/Profiling`. Split out of `Sources/JavaIntelligence/CLAUDE.md`.

- **Profiler model, beyond the first cut** (`Sources/JavaIntelligence/Profiling/`; UI: `Umbra/Sources/Umbra/Profiler/CLAUDE.md`). Every event keeps its time: `JFRTextParser.parseTimestamp` reads `23:59:46.198 (2026-10-13)` (local time and date as `jfr print` writes them, or ISO) into milliseconds, so only differences mean anything, and `JavaProfile` offsets them from the first event it reads. Besides the prefix trees, `JavaProfile` keeps a bounded **sample table** per kind (`JavaSampleTable`: time, thread index, the leaf node of the sample's stack and its weight; 2 M rows, then `dropped`), so a thread filter or a time range is a pass over it plus `JavaProfileTree.reweighted(selfCounts:)` (totals by one reverse walk, because a node is created after its parent; empty nodes drop out of `children(of:)`), never a rebuild; `JavaProfile.tree(of:thread:range:)` keeps the last six answers. `cpuByThread` and its 64-thread cap are gone. The wait kind (`contention`, weights in µs) now holds `JavaMonitorEnter`/`Wait`, `ThreadPark`, `ThreadSleep`, `SocketRead/Write` and `FileRead/Write` with a synthetic leaf frame saying what for (`sleeping`, `socket read <host>`, `file read <name>`, the port left out so connections group); `jdk.CPULoad` and `jdk.GCHeapSummary` become `cpuLoad` and `heap` series and GC pauses carry a start. `estimatedCPUSamplePeriodMilliseconds()` is the median gap of the busiest thread (a recording's period is not always the `profile` setting's 10 ms). `JavaProfileTransforms` are the call tree's what-ifs as pure functions over a tree (`focusingOnSubtree`, `focusingOnCall`, `excludingSubtree`, `excludingCalls`, `collapsingRecursion`, `hidingFrames` with `JavaClassPattern` as its name matcher: a plain name is the class, its nested classes or a package, `*` is a wildcard, `backTrace`, `mergedCallees`); `JavaProfileTimeline.build` buckets the table into per-thread running/waiting/allocating shares (a CPU sample stands for one period, a wait for its duration), `nearestSample` is what a click lands on; `JavaProfileComparison.compatibility(baseline:target:kind:thread:basis:)` says first whether two recordings can be set against each other (`.incompatible` for a kind or thread the baseline lacks, `.warning` for CPU periods 1.5× apart); `JavaProfileComparison.compare` matches frames of two recordings **by method** (line dropped, since lines move between versions), merges them into one tree whose node is as wide as the larger side (children always fit) and keeps both counts per node and a per-method table; `JavaLineProfile.build` is each line's total (counted once per sample) and self cost per top-level class, for the editor hints — plus per recorded source file, for Swift time profiles whose frames carry `<source line>` and `<path>` (`XCTraceTimeProfileParser`; the path is kept per method on `JavaProfileSymbols`, JFR frames carry none). Recording options: `JavaFlightRecorderOptions` (template profile/default/custom `.jfc`, period, `stackdepth` default 128 as `-XX:FlightRecorderOptions=stackdepth=`, allocation throttle, wait threshold; event settings on the command line need Java 17), `JavaFlightRecorder.vmArguments(file:options:jdkFeatureVersion:)` names the recording `umbra` (so `jcmd JFR.dump name=umbra` finds it) and the Gradle script takes `umbraProfileSettings`, `umbraProfileStackDepth`, `umbraProfileOptions` and `umbraProfileRun` (every forked JVM gets `-Dumbra.profile.run=<id>`, which `jps -v` shows: `JavaLiveCommands.pids(inJPSOutput:runID:)`). `JavaProfileRunInfo` is `run.json` beside the recordings (label, dates, JDK, settings), `JavaRecentProfile.list` the newest runs with it. `JavaLiveMetricsParser` reads `jcmd GC.heap_info` (G1 in both spellings, Parallel, Serial, ZGC, Shenandoah by shape) and `PerfCounter.print` (Java thread counts, metaspace), fixtures from JDK 21 and 26. Format notes learned from real output: `jfr print` writes `startTime` in local time with the date in parentheses, percentages as `0.12%`, sizes as `1 byte` / `5.0 MB`, and nests `heapSpace = {…}`; G1's PerfData lags (updated per collection), so heap use comes from `GC.heap_info`. Tests: `JavaProfileTimeAndQueryTests`, `JavaProfileTransformTests`, `JavaProfileTimelineTests`, `JavaProfileComparisonTests`, `JavaLineProfileTests`, `JavaFlightRecorderOptionsTests`, `JavaLiveMetricsParserTests`, `JavaLiveCommandsTests` (fixtures `Tests/PenumbraTests/Fixtures/JavaProfiling`: `mixed-print.txt` is a real JDK 21 print of sleeps, a monitor wait, a socket read, allocation and GC; `mixed-print-jdk<N>.txt` are the prints of `generate/Mixed.java` under JDK 21, 22, 24, 25 and 26, made by `generate/regenerate.sh <jdk home>…` and all read by `JavaProfilingJDKFormatTests` with the same assertions (JDK 26 adds `jdk.SocketWrite`; no JDK 17 was installed, so add one when there is); `heap-info-*.txt`). Release numbers (`swift run -c release PerfHarness java-profile-import synthetic --samples 60000 --depth 128`): import of 193 MB 1.1 s; a range or thread query 0.1 ms, the timeline 5 ms, line costs 10 ms, a comparison 16 ms.
