# GitHub API and permissions

Documentation checked 2026-11-24. Target GitHub.com over HTTPS. Pin REST to `2026-03-10` and send `Accept: application/vnd.github+json` unless an endpoint requires another representation. Read pagination through validated `Link` URLs. Permissions below name GitHub App repository permissions for user access tokens unless stated otherwise. The effective access depends on the authenticated user, app permissions, installation coverage, and policy. Verify changed API capabilities and ambiguous permission combinations against a disposable installation before enabling writes. [REST versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions) · [App permission listing](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps) · [User-token endpoint listing](https://docs.github.com/en/rest/authentication/endpoints-available-for-github-app-user-access-tokens)

In the matrix, `R` means `/repos/{owner}/{repo}` and `P` means `R/pulls/{pull_number}`.

| Phase and operation | Endpoint or transport | Permission and constraints |
| --- | --- | --- |
| 2a Device authorization and rotation | `POST github.com/login/device/code`, `POST github.com/login/oauth/access_token` | Device-flow-enabled app and public Client ID. Use `urn:ietf:params:oauth:grant-type:device_code` or `refresh_token` as appropriate. Honor pending, slow down, denied, and expiry, including OAuth errors inside HTTP 200. Refresh of a device-flow grant requires no client secret. [Device flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#using-the-device-flow-to-generate-a-user-access-token) · [Refresh](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens) · [Form body example](https://docs.github.com/en/apps/creating-github-apps/writing-code-for-a-github-app/building-a-cli-with-a-github-app) |
| 2a Identity | `GET /user` | Authenticated user identity. Persist the numeric user ID and update mutable display login after verification. [Users](https://docs.github.com/en/rest/users/users#get-the-authenticated-user) |
| 2b Discovery | `GET /user/installations`, `GET /user/installations/{installation_id}/repositories`, `GET R` | User token for installation endpoints. Metadata read for repo details. Public metadata access does not prove installation access. [Installations](https://docs.github.com/en/rest/apps/installations) · [Repositories](https://docs.github.com/en/rest/repos/repos) |
| 3 Browse and blob fallback | `GET R/branches`, `GET R/contents/{path}?ref={sha}` | Contents read. Apply server and client file limits and distinguish directory, regular file, symlink, and submodule. Never use returned links as authenticated destinations. [Branches](https://docs.github.com/en/rest/branches/branches) · [Contents](https://docs.github.com/en/rest/repos/contents) |
| 3 Publish | `POST /user/repos`, `POST /orgs/{org}/repos`; existing Git clone, fetch, and push | Creation requires Administration write. Validate owner and installation visibility following creation. Git transport uses existing authentication and trust. App-token Git injection requires independent verification before shipping. [Repositories](https://docs.github.com/en/rest/repos/repos) |
| 4 PRs | `GET/POST R/pulls`, `GET/PATCH P`, `GET P/files`, `GET P/commits`, `GET/POST/DELETE P/requested_reviewers` | Pull requests read/write according to method. The REST file listing is capped at 3,000. [Pull requests](https://docs.github.com/en/rest/pulls/pulls) · [Review requests](https://docs.github.com/en/rest/pulls/review-requests) |
| 4 Merge and branch update | `PUT P/merge`, `PUT P/update-branch` | Merge uses Contents write and expected `sha`. Update uses Pull requests write and expected head SHA; app also needs write access to head contents. Rulesets may reject either. [Pull requests](https://docs.github.com/en/rest/pulls/pulls) |
| 4–5 Review and checks | `GET/POST P/reviews`, `POST P/reviews/{id}/events`, `DELETE P/reviews/{id}`, `GET/POST P/comments`, `POST P/comments/{id}/replies`, `PATCH/DELETE R/pulls/comments/{id}`, `GET R/commits/{ref}/check-runs`, `GET R/check-runs/{id}/annotations` | Pull requests read/write; Checks read for check runs/annotations. Use documented commit, path, line and side fields. Validate pending-review range representation separately before enabling batch multiline submission. [Reviews](https://docs.github.com/en/rest/pulls/reviews) · [Review comments](https://docs.github.com/en/rest/pulls/comments) · [Checks](https://docs.github.com/en/rest/checks/runs) |
| 4–5 GraphQL PR operations | `POST /graphql` for review threads, `resolveReviewThread`, `unresolveReviewThread`, `markPullRequestReadyForReview`, `convertPullRequestToDraft`, `enablePullRequestAutoMerge`, `disablePullRequestAutoMerge`, `enqueuePullRequest`, `dequeuePullRequest`, `markFileAsViewed` and `unmarkFileAsViewed` | Use named operations and cursor pagination. Verify viewer capability and Pull requests read/write with the app user token. Use the same authorization boundary for GraphQL mutations as REST. [Pull requests schema](https://docs.github.com/en/graphql/reference/pulls) |
| 6 Issues | `GET/POST R/issues`, `GET/PATCH R/issues/{number}`, `GET/POST R/issues/{number}/comments`, `PATCH/DELETE R/issues/comments/{id}`, `GET R/labels` | Issues read/write. PR discussion comments use the issue-comment endpoints, which document alternate Pull requests permissions. Filter PR objects from Issues. [Issues](https://docs.github.com/en/rest/issues/issues) · [Issue comments](https://docs.github.com/en/rest/issues/comments) · [Labels](https://docs.github.com/en/rest/issues/labels) |
| 7 Actions | `GET R/actions/workflows`, `GET R/actions/runs`, `GET R/actions/runs/{id}/jobs`, `GET R/actions/jobs/{id}/logs`, `POST R/actions/runs/{id}/{cancel,rerun,rerun-failed-jobs}`, `POST R/actions/workflows/{id}/dispatches` | Actions read/write. Log redirects require a separate authenticated-origin download policy with a credential-free second request. [Workflows](https://docs.github.com/en/rest/actions/workflows) · [Runs](https://docs.github.com/en/rest/actions/workflow-runs) · [Jobs](https://docs.github.com/en/rest/actions/workflow-jobs) |
| 8 Releases | `GET/POST R/releases`, `GET/PATCH/DELETE R/releases/{id}`, `GET R/releases/assets/{id}`, release-specific asset upload on `uploads.github.com` | Contents read/write. Draft visibility depends on server access. Asset download and upload each need a reviewed origin and size policy. [Releases](https://docs.github.com/en/rest/releases/releases) · [Release assets](https://docs.github.com/en/rest/releases/assets) |
| 8 Notifications | `GET /notifications`, `PATCH /notifications/threads/{id}`, `DELETE /notifications/threads/{id}` | GitHub documents classic PAT authentication for these endpoints. A GitHub App user token cannot list the inbox. Evaluate optional separate classic PAT entry with notifications scope and organization limitations. Require authorized conditional polling and honor `X-Poll-Interval`. [Notifications](https://docs.github.com/en/rest/activity/notifications) |

Use resource-specific response types and structured errors. Honor retry-after, primary reset and secondary throttles. REST is the default for simple resources. GraphQL may combine nested PR detail fields if measured request counts and query costs improve. Treat GraphQL partial errors explicitly and bound cursor depth. [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) · [GraphQL rate limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)
