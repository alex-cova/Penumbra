# 04 — Performance and memory

Date: 2026-11-22, commit `afc43b7f`.

## Method

- **Hardware and software**: Apple M5 Max (18 cores), 64 GB, macOS 27.2.1, Apple Git 2.54.0 (Apple Git-157). AC power, display on (`caffeinate`). No `core.fsmonitor`, no `core.untrackedCache`.
- **Repositories**: generated by a script in the scratchpad (`bench/gen.py`). N tracked `.java` files of 40 lines each, 100 per directory, 31 commits (the history is shallow, so log costs are a lower bound), plus a `.gitignore`d `build/` with up to 5,000 files. Sizes: 100, 5,000, 50,000, 100,000 tracked files (100k = 815 MB working tree).
- **Tool**: `gitbench`, a release build linking the real `GitIntelligence` by path, so the arguments are exactly Umbra's. Each row is 1 warm-up plus 7 runs, reported as the median. The FS cache was warm (the files had just been written). **No cold-cache numbers**: `purge` needs root and was not run.
- **Umbra-side cost**: XCTest probes in a scratch clone (`AuditGitProbe3Tests`, `-c release`) drive `IDEGitStatusModel` on the same repositories. A 1 ms main-actor ticker records the largest gap.
- **This checkout**: read-only `git --no-optional-locks` commands on `/Users/alex/Developer/Penumbra` (5,536 tracked files, 826 commits, 25 GB of ignored `.build`).

**Git's cost against Umbra's wrapper.** Raw `/usr/bin/git … status` from Python on the 100k repository: 123.9 ms, against 120.8 ms through `SystemGitRunner`. The process floor (`git --version`) is 8.1 ms. The wrapper adds nothing measurable. Status time grows with **tracked file count** (stat of the index), not with the number of changes: 1 → 10,000 changes adds about 36 ms at 100k. `-uno` (no untracked scan) cut 100k status to 75 ms. `core.untrackedCache=true` passed with `-c` did not help, because `--no-optional-locks` keeps git from writing the cache.

## 2. This checkout: the ignored pass

| Command | Median | Entries |
|---|---:|---:|
| Hot status | 33.9 ms | — |
| `status --porcelain=v1 -z -unormal --ignored` (Umbra's ignored pass) | **1,671 ms** | 38 |
| `ls-files -z --others --ignored --exclude-standard --directory` | **30.1 ms** | 38 |

The two ignored listings are **identical**: diffed after stripping `!! ` and sorting. Umbra runs the 1.67 s command after **every** applied refresh: every save, every stage, every watcher batch, every app activation. It runs off main and is cancelled by the next refresh, so it does not block the UI. The CPU and disk cost on any project with a large ignored tree (`.build`, `node_modules`, Gradle `build/`) is about 55× what the equivalent `ls-files` costs. The earlier audit (F5, 5.14 s sample) moved `--ignored` off the hot status; it did not make the pass cheaper. **G-12.**

## 3. Umbra-side cost (release build)

| Measure | Result |
|---|---|
| `IDEGitStatusModel.parse` + `IDEGitChangeRows.listed`, 1,000 entries | 10.6 ms |
| … 10,000 entries | 90.8 ms |
| … 100,000 entries | **1,192 ms** |
| End-to-end warm refresh, clean tree: 5k / 50k / 100k | 55 / 82 / 143 ms |
| End-to-end warm refresh, 5,000 changes (5k repository) | 557 ms, largest main-actor gap 2.1 ms |
| End-to-end warm refresh, 10,000 changes, 50k / 100k | **1,165 / 1,200 ms**, largest main-actor gap **83 / 148 ms** |

- The parse runs off main (`nonisolated static`). Per-entry `NSString` path building, the walk up through ancestor folders in `markDirty`, which recounts `String.count` (O(n)) on each step, and a `localizedStandardCompare` sort are the likely costs. **This was not profiled.** Attribute it with Instruments before changing it.
- With many changes, the main-actor part (`apply` → dictionary comparisons and rebuilds of `statuses`/`changeByPath`, `changeSelection.reconciled`, `IDEGitChangeRows.listed`, and SwiftUI invalidation) blocks for 83–148 ms. That is a visible hitch.
- Of the roughly 1.2 s end-to-end at 10k changes, git accounts for about 0.16 s and the measured parse for about 0.09 s. **About 0.9 s is not attributed** by this audit. It was the same on the first load and on a warm refresh. Profile before optimizing.
- 10,000-change working trees are unusual (a mass reformat, a vendored-dependency bump, a botched line-ending conversion). Typical sessions (under 100 changes) cost git time plus under 2 ms.

## 4. Editor latency

- **Per keystroke**: no git work. The gutter diff runs 400 ms after typing pauses, off main, against a cached `HEAD` blob (`IDEChangeMarkers.swift`). `IDEHostEditCostTests` (not run in this pass) holds the editor's per-edit budget.
- **Per git refresh**: each visible pane's gutter re-diffs at once (`force: true, delay: .zero`). This is O(file length) per pane, off main, and dropped if the buffer changes.
- **Per save**: one refresh set plus one ignored pass, so on this checkout about 1.7 s of background git per save (G-12).

## 5. Process count per trigger

| Trigger | Git processes |
|---|---|
| Watcher batch, save, or stage completing | `status`, `symbolic-ref` (`+ rev-parse` when detached), `for-each-ref`, then the ignored `status`. Four, or five when detached. Plus `cat-file` per visible gutter on a HEAD-cache miss. Plus `rev-list`/`log` when ahead or behind changed. |
| Refs changed or app activated | The above, plus `log --all -n 300`, `for-each-ref`, `remote` (inside `log`), `log --all -n 5000 --format=%an` (when authors are stale), `stash list` |
| Discovery | Once per `setRoot`. The `GitRepository` is reused after that. |

`currentBranch` duplicates the `HEAD` file read (`state()`), so one process per refresh is avoidable. `remotes()` is called inside `log`, `commits(in:)` and `syncStatus`, so it runs several times per history load.

## 6. Resource behaviour

| Check | Result |
|---|---|
| Unbounded task creation | None. One refresh in flight plus a queued flag. One task per editor for the gutter, replaced on each schedule. |
| Caches | HEAD blobs: LRU, 128 entries and 32 MB (`IDEChangeMarkerTests` cover the caps). The command store keeps 500 records, with output capped at 4 KB each. Diff sessions live as long as their tabs. |
| Repeated full scans | `git status` is inherently a full index scan. Umbra adds a second full scan (the ignored pass) per refresh (G-12). |
| Main-thread git | None found. All git runs in `nonisolated` async functions. |
| Retain cycles and leaks | Tasks capture `[weak self]`. One `NotificationCenter` observer token per model is never removed (G-22, tiny). |
| Survives window close | Reads are cancelled. Mutations are killed rather than finished (G-14). The askpass server is process-wide by design. |
| Idle cost | With no file activity and the app inactive: no timers (background fetch is off by default), so no git processes. Each app activation costs one refresh set plus a history reload per window. |

## 7. Scaling verdict

Umbra's git cost grows with **tracked file count** (git's own index stat), plus **ignored-tree size** (the ignored pass), plus **change count** (Umbra's parse and publish, which dominates past about 5,000 changes). At 100k tracked files with few changes, a refresh is about 143 ms end to end, off main. That is fine on its own, but it is slow enough to trip the starvation in G-06 under sustained file activity. The highest-value fixes, in measured terms:

1. Replace the ignored pass with `ls-files -o -i --exclude-standard --directory` (1,671 → 30 ms here, identical output).
2. Fix refresh starvation (G-06).
3. Profile and reduce the parse/apply cost for large change sets (unattributed 0.9 s; 148 ms main-actor gap).
4. Drop the redundant `symbolic-ref` and the repeated `remote` calls (about 7 ms each; minor).
5. Consider opt-in `core.fsmonitor=true` with `core.untrackedCache=true` for very large repositories. That needs a write path for the index extension, so not `--no-optional-locks` for that one call. Measure first.

## 8. After the fixes (2026-11-23, release build, uncommitted)

**G-12, the ignored pass.** `GitRepository.ignoredPaths()` (`ls-files -z --others --ignored --exclude-standard --directory`) replaces `status --ignored`. On this checkout both listings hold the same 38 entries. `status --ignored` took 3.2-4.8 s and `ls-files` 0.04-0.05 s in the same run (a release build was using the CPU, so the status figure is higher than the 1.67 s measured earlier; the ratio is what matters). Tests: `testIgnoredPathsAreTheSameSetAsStatusReports`, `testTheIgnoredPassNeverRunsStatusOverIgnoredFiles`.

**G-13, a large change set.** Fixture: 100,000 files in 1,000 folders, 10,000 modified (`git status --porcelain` alone: 0.17 s). Measured with `IDEGitRefreshCostTests` (opt-in, `UMBRA_GIT_COST_REPO`), `swift test -c release`, a 1 ms ticker on the main actor:

| | before | after |
|---|---:|---:|
| `git status` (10,000 entries) | 150-196 ms | 150 ms |
| `IDEGitStatusModel.parse` | 632-655 ms | 34 ms |
| first load (`setRoot` to snapshot) | 870-913 ms | 205 ms |
| refresh, end to end | 950-958 ms | 224 ms |
| largest main-actor gap during a refresh | 143-144 ms | 11 ms |

Where the time went. The profile ruled out the suspects the audit named: sorting 10,000 shuffled paths with `localizedStandardCompare` costs 21 ms (plain sort 2 ms), and `IDEGitChangeRows.listed` under 1 ms. The cost was `markDirty`: for every changed file it walked every ancestor folder through `NSString.deletingLastPathComponent` and `appendingPathComponent`, which bridge to Objective-C, about 40,000 calls. It now walks up with string indices and stops at the first folder already marked (a folder's ancestors are marked when it is), and `parse` joins paths with a plain concatenation. The main-actor stall was `changeSelection.reconciled` building a 10,000-element `Set` to learn that nothing is selected; it now returns at once for an empty selection. Targets (gap under 50 ms, refresh under 400 ms) hold with `UMBRA_GIT_COST_BUDGET=1`. Not measured: the 50,000-file fixture, and Instruments (the ticker and phase timings were enough to find the cause).
