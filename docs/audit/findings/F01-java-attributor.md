# F01 — No Java attributor

- **Priority:** P0 (long pole; lands in P2) · **Severity:** Critical · **Confidence:** Confirmed · **Provenance:** A+B
- **Status:** ✅ Done for what completion needs (2026-11-04); the nominal `JavaType`, first-class capture conversion, intersection types and signature IDs on resolved members were decided against, with reasons (see Implementation notes, third pass) · **Owner:** Unassigned

## Evidence

- `JavaTypeSystem` (Sources/JavaIntelligence): no nominal type, no strict/loose/casting contexts, no capture conversion, `lub` erased with no type arguments.
- `JavaExpressionTyper` (~1,032 lines): hand-rolled switch over ~20 node kinds; default returns `nil` = silently no completion. Ternary/switch take first arm, not `lub`. Generic method variables never bound from assignment target.
- Warm `javac` exists only for diagnostics; quoted 57 ms warm check cannot sit on the completion path.
- Corpus: 214/253 = 84.6% passing (`docs/JAVA_PARITY.md`).

## Root cause

Completion runs a typer + stub resolution, not a JLS attribution pass over a resolved symbol graph.

## Fix sketch

Build the native Phase-4 attributor sketched in `Sources/JavaIntelligence/Semantics/CLAUDE.md`: nominal attributed type, capture conversion, target-argument binding, signature IDs. Do not wire javac into completion.

## Complexity / Dependencies

XL. Depends on F14 (scope tree) and F15/F17 indexes for full effect. Start foundations early; it gates most of P2.

## Acceptance criteria

- Completion corpus above 214/253 with zero regressions on previously passing cases.
- New fixtures pass: capture conversion, diamond, anonymous, method-ref exactness, pattern switch.

## Tests / benchmarks

- Existing Java completion corpus + parity baseline (jdk26).
- Completion p50/p95 via signposts at 20k/120k-line files (requires F06).

## Out of scope

Full IntelliJ parity, ML ranking (F18), JPMS visibility (F16).

## Implementation notes

2026-11-03, first pass. **The brief's baseline metric is stale.** `baseline.json` was a ratchet of 214 names recorded on JDK 26; the corpus now has 253 cases, none gap-tagged, and all 253 pass on this machine's JDK 27 (the ratchet is skipped on a JDK mismatch). "214/253 is the ceiling of the design" is therefore not supported by the numbers, and the corpus cannot measure attributor progress. `docs/JAVA_PARITY.md` still says 214/253 (generated by `JavaParityCorpusTests`, which is skipped on this machine, so it was not regenerated).

The corpus was extended with 23 `Attr*` cases for the brief's fixture list (wildcard capture, diamond, anonymous, method-ref exactness, pattern switch, ternary lub, lambda-return inference). 276 cases, 273 pass, 3 tagged `gap:`; baseline re-ratcheted on JDK 27. Findings and fixes:

- `List<? super X>` reads typed as `X` (unsound: offered `Integer` members on an `Object`). `JavaMemberLookup` now substitutes a `? super` variable's upper bound for returns and fields and keeps the lower bound for parameters, carried through supertype levels.
- Diamond with constructor arguments (`new ArrayList<>(List.of("a"))`) was raw. `JavaExpressionTyper.diamondResolved` binds the class's type parameters from the chosen constructor (selected on erased parameters). Anything left unbound stays raw, so a declared target still supplies the arguments as before.
- Pattern bindings (`case String s ->`, record patterns, guards, negated `instanceof`) were invisible to member completion because `receiverInfo` used the older `JavaLocalScope`. It now uses the scope tree for the enclosing method/constructor, merged with `JavaLocalScope` for names the tree loses in `ERROR` regions (the F14 weakness: `names[0].` before `}` lost the method's parameters). Two scope-tree bugs fixed on the way: `locals(atByteOffset:)` dropped `lambdaOrigin` for inferred lambda parameters, and returned a scope's declarations in source order instead of latest-first.
- Cost: a whole-file scope tree added ~5 ms to each large-file member completion (Release, 11.0 → 16.0 ms); building only the outermost enclosing executable restored parity (10.8 ms vs 11.0 ms parent, `java-completion synthetic`).

Open, tagged in the corpus: `yield s.` inside an unterminated arrow block (`gap: F14-error-recovery`). Not started: the nominal `JavaType`, capture conversion as a first-class operation, target-typed diamond/generic-method inference beyond what exists, signature IDs. The wildcard fix is a targeted substitution rule, not capture conversion.

Second pass, anonymous classes (`JavaAnonymousClass`): a synthetic `JavaClassStub` per anonymous body (extends the instantiated class or implements the instantiated interface, declares the body's members via the stub builder's own member scanner), found through a request-scoped task-local registry that `JavaIndex.classStub` consults, named by a hash of the creation text so a `var` initializer re-parsed from its own text gets the same type. `typed()` returns it for `new Foo() { … }` when a registry is set (only the completion provider sets one; everyone else keeps `Foo`), and the provider enters the enclosing anonymous bodies as the innermost types, so `this.`, unqualified members, captured outer locals, generic interfaces, a nested anonymous class and `var o = new Object() { … }; o.secret` work. 6 more cases (`AttrAnonymous*`); 282 cases, 281 pass, 1 tagged gap (`yield`). Release `java-completion synthetic` large-file member access 11.3 ms vs 11.2 ms parent. Limits: member type names resolve against the file as saved on disk (same as the buffer's named classes today); a diamond anonymous (`new Foo<>() {}`) keeps the written type's arguments; only the nearest named type's anonymous bodies are entered, not ones inside a local class body.

## Implementation notes, third pass (2026-11-04): closing F01

**Method.** The first two passes fixed what the brief's fixture list named. This pass wrote the shapes real code is made of before changing anything: 51 generic-inference probes (streams, collectors, `Optional`, `CompletableFuture`, method references, ternaries, switch expressions), 48 harder ones (nested wildcards, self-typed builders, recursive bounds, records, inner classes of generic classes, nested collectors, interface-typed receivers) and 18 capture-heavy ones (wildcard reads through lambdas, entry sets, `Class<?>`, `Supplier<? extends List<String>>`). First run: 4 of the first 51 and 5 of the next 48 failed; all 18 capture probes passed. The corpus is now 419 cases, all passing on JDK 27 (`docs/JAVA_PARITY.md` updated; baseline re-ratcheted, 116 new names).

**What was wrong and is fixed** (all in `JavaExpressionTyper`, `JavaTypeSystem`, `JavaMemberLookup`):

- **Generic-method inference solved in the wrong order.** Lambdas were typed first, so `Stream.iterate(1, i -> i + 1)` saw `T` unbound and became `Stream<Object>`, and `Collectors.toMap(s -> s, s -> s.length())` inside `collect(...)` never learned `T` from the stream. `typedMethodInvocation` now collects constraints in javac's order (JLS 18.5): explicit type arguments, the call's own target, the plain arguments, and only then the lambda bodies and method references, each typed against the substituted functional interface. A generic call passed as an argument (`Function.identity()`, `Comparator.comparing(...)`, `toList()`) is retyped against its parameter with what is known substituted in; when that parameter still mentions a variable only a lambda can bind (`mapping(s -> s.trim(), toList())` needs `U`), it waits until the lambdas have run. Fixes `Stream.iterate`, `Collectors.toMap`, `Function.identity()` in `toMap`, `Collections.max(list, comparing(...))` and nested `groupingBy`/`mapping`.
- **Several arguments for one variable took the first.** `List.of(1, 2.5)` was `List<Integer>`. Arguments now meet in their lub (JLS 18.5.2). The lub itself (`JavaTypeSystem.lub`) returned `nil` when the common supertypes had no single most specific member (`Integer`/`Double`: `Number & Comparable<…> & Constable`); it now takes the minimal members and represents the intersection by its class if there is one (`Number`), else its first interface by name (`preferredMinimal`).
- **Method references through an unbound receiver left the declaration's variables in the result.** `map(Map.Entry::getKey)` gave `Stream<K>` and `flatMap(List::stream)` `Stream<E>`: the reference's receiver is the functional interface's first parameter (`Entry<String, Integer>`), viewed as the named type, so its arguments flow into the return type.
- **Conditionals and `switch` expressions took the first arm.** `c ? 1 : 2.5` was `int`, `c ? arrayList : linkedList` was `ArrayList`. `conditionalType` follows JLS 15.25: a `null` arm gives way (and boxes), numeric arms promote (`byte`/`short` mix to `short`, else at least `int`, widest wins, boxed arms unbox), boolean arms stay boolean, reference arms meet in `lubKeepingArguments`, which keeps the type arguments the arms agree on (`AbstractList<String>`) and blurs the ones they do not to `?`. Switch expressions use all arms, `yield`s included.
- **Interface-typed receivers offered none of `Object`'s methods.** `Runnable r; r.` listed `run()` only; `toString`, `equals`, `hashCode`, `getClass` and the rest are implicit members of every interface (JLS 9.2). Queued after the superinterfaces so a declaration above wins. This also lets overload resolution and hover work on `iface.equals(x)`.
- **Inner classes of generic classes lost the enclosing type's arguments.** `Outer<String> o; o.inner().get()` was `T`. A member class written by simple name inside its generic outer now carries the enclosing type (`attachingOuter`; one level, instance member classes only), the walk seeds its substitution from the `outer` links, and `substitute` replaces a bare enclosing type variable that resolution left `unresolved`.
- The `yield s.` gap noted in the first pass (`F14-error-recovery`) is gone from the corpus: no case carries a `gap:` tag.

**Latency.** Release `PerfHarness java-completion synthetic`, three paired runs against the parent commit: large-file member access 11.0-11.3 ms before, 11.4-11.7 ms after (noise-level); lambda chain 7.1-7.5 against 7.1-7.4; the fast-path stages are equal (member access 0.136 ms, 0.131 after). No typer step the fast path takes got slower; the new work is in call typing.

**Tests.** `JavaCompletionCorpusTests` (419 cases, ratcheted; mutations: no deferral of generic-call arguments fails nested `groupingBy`/`mapping`, first-argument-wins fails `List.of(1, 2.5)` and `pick(1, "s")`, removing the interface `Object` members fails `Infer2TwoArgsSameVar`), and `JavaTypeSystemTests` for the lub of boxed numbers and of unrelated classes, `lubKeepingArguments` (arguments kept, arguments blurred), the enclosing-variable substitution and `conditionalType`'s numeric, boolean and null rules. The full library suite passes.

**Decided against, with reasons** (the brief's fix sketch listed these; the acceptance criteria are met without them, and nothing consumes them):

- *A nominal `JavaType`.* Resolution already produces `JavaTypeRef.classType` with a qualified name; the unresolved cases that remain are the ones the index cannot place, which a second type would only rename. It would touch every switch over `JavaTypeRef` in the module (and the shard format) to change no completion result. Revisit if an analysis needs to prove "fully resolved" statically.
- *First-class capture conversion.* Wildcards are read through `readSubstitution` (a `? super X` yields its upper bound on reads, `X` on writes), `concreteType` for functional parameters, and nested wildcards through supertype levels. 18 capture probes, including nested `Map<String, ? extends Collection<? extends Number>>`, `Class<? extends Enum<?>>` and lambdas over `List<? extends Number>`, all pass. Fresh capture variables matter for type checking (two captures of one wildcard are different types), which this code does not do; `javac` stays the oracle for diagnostics.
- *Intersection types.* Represented by one component (class if any). Members of the other components (`compareTo` on `List.of(1, 2.5).get(0)`) are not offered. Adding a `JavaTypeRef` case is the nominal-type problem again.
- *Signature IDs on resolved members.* `JavaSymbolID` (declared, erased signatures) is what usages, rename and navigation identify symbols by. A resolved member carries a substituted stub, so an ID computed from it would differ from the declared one (`List<String>.add(String)` against `add(E)`); attaching the declared key needs a field on `JavaMethodStub` and has no reader today.
- *`javac` on the completion path.* Out of scope in the brief and kept out.

**Remaining limits to know:** inference is still a single pass over the arguments (no joint solving of mutually dependent lambdas, no overload re-selection after lambdas are typed); inner-class outer arguments attach one level deep; the intersection representative is a heuristic; generic lub blurs differing arguments to `?` where the JLS gives `? extends lub(...)`; and `docs/JAVA_PARITY.md`'s generator is skipped on this machine, so its pass count was updated by hand.
