## Architecture and review

- The text buffer and editing engine remain the source of UTF-16 offsets. Virtual chips occupy Core Text advance space and use the existing line-fragment draw paths. Code Vision keeps the existing row-top inset and batched overlay. Same-anchor ghost text is immediately after the semantic chip. The caret continues to support the library's existing before/after visual affinity at that document position.
- The controller keeps a per-editor viewport request. It validates buffer identity as well as generation because a newly loaded buffer can reuse the previous numeric generation. It uses the workbench intelligence identity for split editor snapshots. The materialized buffer comes from the existing off-main shared cache.
- The LSP transport extension uses the existing message framing and forwards other methods to LanguageClient. It bounds in-flight inlay requests, removes cancelled continuations, rejects late responses and advertises the implemented tooltip resolve properties. Explicit text edits use the normal undo group and revalidate offsets and grapheme boundaries before applying.
- Version-manager values are bounded literal strings. They never supply a process, URL, or path. Sibling conflict reads skip symlinks and oversized files. The JDK folder action validates the selected installation against the declaration and uses the project selection only. There is no download or archive extraction path to assess.
- Workspace visibility overrides global visibility for that workspace. Provider and category switches still apply. A fresh profile enables Java parameter, variable and lambda hints. Java method chains and Code Vision stay opt-in.

- **Line-start placement implemented** (phase 1). Previously a hint at a line's first column was dropped, because a hint's room is added to the previous glyph's kerning. Now it is local offset 0. The line's first `LineFragment` carries a `leadingInset` (the chip's width), which the typesetter adds to that fragment's width, so wrapping and the content width account for it. The paint frame (`LineFragmentPaintSpec.frame`) is the text frame, shifted right by the inset, and the chip is drawn left of it (`LineInlayHint.leadingX` is `-width` at offset 0). Metal uses the frame directly. The Core Graphics view grows left by the inset and the renderer translates by it. `LineController` adds the inset in `caretX` and removes it in `closestIndex`, and a click on the chip lands at the line start (`inlayHintAnchor`). Ghost text at column 0 is unchanged. Tests: `InlayHintTests` (offset-0 local hint, caret shifts, click on the chip, wrapped line), `MetalDecorationTests.testLineStartChipSitsLeftOfTheTextFrameInBothRenderers` (Metal pill x equals the CG view's left edge).   **What it found, and what changed.** The first run showed the provider labeled nothing on any overloaded call (it bound only a call with exactly one candidate of that name and arity), so `over(1, 2)` and `over("s", 3)` got no hints although javac resolves them. A call is labeled only if every argument types, none is a lambda or method reference, and exactly one overload is left; it also applies to constructors. Cost, measured in Debug: 80 overloaded calls in one request took 19.1 ms against 14.7 ms for 80 plain calls. ### Performance investigation (Release, Metal, quiet machine)

- **Gates on the final code.** Native Java, 120,000 lines, 9.25 MB: warm p95 **8.9 ms** (budget 20), 162 hints, document cache 1 parse and 30 hits. Enter p95 added by 180 hints, mean of two rounds, `enter_fresh_middle` (budget 0.5 ms): 1k lines +0.170, 20k +0.265, 120k +0.199; decoration builds 2 per Enter; `metal=true` in every log.
- **Line-start hints.** `PerfHarness` now takes `PENUMBRA_INLAY_COLUMN` (default 8). Enter p95 added at column 0 against none: 1k +0.297, 20k +0.244, 120k +0.188 ms (`enter_fresh_middle`); `enter_fresh_top` +0.206, +0.172, +0.245. Mid-line hints in the same run: +0.108 to +0.176. Both stay under 0.5 ms with 2 decoration builds, so the leading inset costs about 0.03 to 0.13 ms more than a mid-line chip.
- **Where the 398 MB goes.** Measured with `malloc_zone_statistics` on the 8.8 MB file: the **syntax tree is 360 MB**, the file stubs 15.7 MB. On 40 real Java files (4.5 MB of source) a tree costs 26x its source overall (19x to 30x; the synthetic file is denser at 41x). The tree is the existing `JavaDocumentParseCache` entry the app keeps for an open document anyway; before this work every hint request built its own transient 360 MB tree, so what changed is that it is now shared and persistent, not that more is held. The hint path adds the stubs (15.7 MB, built once per tree) and a weak reference to the tree.
- **A finding that predates this work.** `DocumentParseCache` bounds itself by source bytes (32 MB) and 256 entries, but a tree costs about 26x its source, so the cap permits roughly 850 MB of trees before eviction (one document over the cap always stays). Normal use is far below that. Lowering `maxSourceBytes` to 16 MB would bound it near 420 MB at the price of re-parsing more when many large files are open; I have not changed it.
- **Cold first request, 120k lines (1.35 s unloaded).** A 3 s sample shows two one-time costs: the tree-sitter parse (the larger share) and the stub build for 120,000 methods (about a third of the busy time). Neither repeats while the text is unchanged. After an edit the cache hands back a new tree object, so the stubs of a file over the memo cap (8 MiB) are rebuilt on the next request (about 0.28 s at 120k lines); files under the cap go through `JavaParseMemo`, one parse per distinct text. Both run off the typing path.
- **Not measured:** Instruments memory cycles (open, split, switch, close), split-view and multi-module performance, time to first hint in the real app, Enter with Code Lens rows present, and the cost of the hover and rotor code.
