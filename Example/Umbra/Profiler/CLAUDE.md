# Profiler (`Example/Umbra/Profiler`)

Loaded when working under `Example/Umbra/Profiler`. Split out of `Example/Umbra/CLAUDE.md`.

- **Profiler** (`Example/Umbra/Profiler/`; model: `Sources/JavaIntelligence/Profiling/CLAUDE.md`; this extends the profiler paragraph in `Example/Umbra/Coverage/CLAUDE.md`, after IntelliJ's profiler pages). *The tab.* A profiled run opens its profile tab **when it starts** (`IDEJavaRunProvider.beginLiveProfile` → `IDEWorkspace.beginLiveProfile`, Settings ▸ Java ▸ Profiling ▸ Show Live Charts While Running): `IDEProfilerSession.Phase.live` shows `IDEProfilerLiveView` (Swift Charts: CPU, heap used/committed, Java threads live/daemon, metaspace; Capture Snapshot, Perform GC, Stop and Show Results), fed by `IDEProfilerLiveMonitor`, which finds the JVM (`IDERunSession.processIdentifier` for a plain `main`, else `jps -v` for the run's `-Dumbra.profile.run=` marker, which also covers Gradle forks), reads CPU, resident size and thread count from `proc_pidinfo` once a second (CPU time converted with `mach_timebase_info`) and heap, metaspace and Java threads from `jcmd` every other second. A JVM that refuses attach leaves the OS series and says so in `notice`; `captureSnapshot()` is `jcmd JFR.dump name=umbra` into the run's `snapshots/` folder and opens as its own tab. When the run ends, `finishLive(recordings:)` reads the recording **in the same tab** (`openProfile` finds the live session by `runID`; a session must be `.live` *before* it is shown, or showing it starts a load); no recording fails the tab with the reason (`endLiveProfile`). *The report.* Kinds are CPU · Allocations · Waits · GC with a thread picker for each; modes Flame Graph · Hot Methods · Call Tree · **Timeline**. `IDEProfilerSession.tree` is the shown tree: the kind and thread and the **time range** (`timeRange`, set by dragging across the timeline: `profile.tree(of:thread:range:)`), then `collapsesRecursion`, then the **what-if chain** (`transforms`: Focus on Subtree / Focus on Call / Exclude Subtree / Exclude Call from the flame graph and call tree menus, shown as removable chips; a node number in one names a node of the tree before it, so collapsing recursion clears the chain). It is cached by kind, thread, range, collapse, chain and load, and `treeRevision` is what a view that caches by node count (the flame graph) keys on, because a filtered tree has the size of the full one. Flame graph: boxes coloured by `FrameOrigin` (project yellow, library purple or grey in the dark theme, JDK blue, marker green; `classifyClass` asks the workspace's source roots once per class), match count with Previous/Next (`searchCursor`, the matches of the zoomed subtree, scrolled to), "fade nodes below N %", Fit, PNG copy and save (`pngData`), tooltip with the share of the caller. Method list: sortable `Table` with a `SplitPanes` detail (Back Traces, Merged Callees, Callee List: `session.detailTree`). `Timeline` (`IDEProfilerTimelineView`): CPU load (heap for allocations) with GC marks, then a `Canvas` lane per thread (busiest first, 64 at most), drag selects the range, a click shows the stack of the sample there. *Comparison.* The header's ⇄ menu picks a baseline (`BaselineCandidate`: another open profile, a recent run, a file); the baseline is read by a hidden session made with the same JDK candidates, and `session.comparison` merges it with the shown tree (kind and thread carry over, the time range and the what-ifs do not apply to the baseline). The flame graph draws the merged tree with `nodeTint` (red where the share grew, green where it shrank) and `extraTooltip`; Hot Methods becomes `IDEProfilerComparisonTable` (share before, now, change). The call tree draws the merged tree too, with Before / Now / Change per node (shares of each recording's total, or of the parent's in percent-of-parent mode; its context menu has no what-ifs and opens source by class name, since a merged tree's method numbers are its own). `session.comparisonCompatibility` (`JavaProfileComparison.compatibility`) is checked first: a kind or thread the baseline lacks is *incompatible* (`comparison` is nil, the chip says why, the plain tree stays), and a CPU sampling period more than 1.5× apart is a *warning* shown beside the baseline chip. *Hidden classes.* `session.classFilters` (`ClassFilter`: JDK, libraries by `classifyClass`, or a `JavaClassPattern`) are applied right after the thread and range, before recursion collapsing, with `JavaProfileTree.hidingFrames` (a hidden frame's callees attach to its caller; a sample with nothing left is the root's); they apply to both profiles of a comparison, and changing them clears the what-if chain like collapsing recursion does. Set from Presentation ▸ Hide Classes (JDK, Libraries, Matching…) and "Hide Class"/"Hide Package" in the flame graph, call tree and method list menus; shown as chips. *Settings.* Settings ▸ Java ▸ Profiling: recording settings (profile, default, custom `.jfc`), period, stack depth, allocation rate and wait threshold (`IDEPreferences.currentFlightRecorderOptions()`); each run writes `run.json` (`finishProfile` completes it) and Run ▸ Recent Profiles lists them. *Editor hints.* `IDEWorkspace.profileHints` (`IDEProfileLineHints`) holds the line costs of the profile tab the user last touched (`profileHintsSession`, rebuilt off the main actor on every query change, a stale result dropped by ticket): Java files under a source root get each line's share in the **annotation column** (`applyProfileLineHints`) and lines with at least 1 % of their own samples a tint, painted below coverage and the stopped line in `applyExecutionLineBackground` (`profileHeatBackgrounds`, which leaves lines other bands use). The annotation column is Git blame's too: `IDEBlameController.yieldsAnnotations` makes blame skip a file the hints own, and turning hints off (Settings, Run ▸ Show Profile Hints in the Editor) hands the column back (`refreshAnnotationColumnsInOpenEditors`). Tests: `IDEProfilerQueryTests` (class filters, compatibility, baselines), `IDEProfilerLiveMonitorTests` (a real JVM found by marker, read, snapshotted), `IDEProfileLineHintsTests`, `IDEInstrumentationViewsSmokeTests` (timeline, diff, live; `UMBRA_VIEW_SNAPSHOTS=<dir>` keeps the PNGs). Not done: a thread filter on the timeline lanes themselves, attaching to a JVM Umbra did not start, and live charts on Gradle forks are found by marker but have no end-to-end test with a real Gradle build.
