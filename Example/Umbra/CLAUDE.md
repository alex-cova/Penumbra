# Umbra (`Example/Umbra`)

Loaded when working under `Example/Umbra`. Moved out of the root CLAUDE.md.

- **`Umbra`** (`Example/Umbra`) — the macOS editor app shipped with this repo, intended as a **Sublime Text alternative**: lightweight, fast editing with project folders, split panes, symbol-aware navigation, session restore, a Problems panel (⌘⇧M; `IDEProblemsStore`/`IDEProblemsPanel`, a bottom-panel tab selected through `IDEBottomPanelTab`), and Java completion with Gradle module and dependency sync, hover with Javadoc, go to implementation, quick fixes, and saved run configurations (Java menu: Run Last Configuration ⌃⌥R, Edit Run Configuration…, Reformat Code ⌥⌘L, Optimize Imports, Show Context Actions ⌥↩; an "Optimize Imports on Save" preference, off by default). Build Project runs through the Gradle runner (asking for trust first) so its compiler errors land in the Problems panel (Sublime keymap by default). Find Usages results go to a Usages bottom-panel tab (`IDEUsagesPanel`, `IDEBottomPanelTab.usages`); Rename… (⇧F6 in the IntelliJ keymap) prompts for a name, shows a preview sheet (`IDERenamePreviewSheet`) and applies through `IDEWorkspaceEditApplier` (live buffers via `TextEditApplicator`, closed files written atomically inside the project folder). Finished Gradle syncs/builds and git actions are posted to `IDENotificationCenter` (`Example/Umbra/IDENotifications.swift`; the titlebar bell opens `IDENotificationPanel`, a toast announces each one — errors stay until dismissed — and live sync/indexing progress stays a separate `IDEStatusToast` card; Do Not Disturb and per-category switches persist in `UserDefaults`; `IDEWorkspace.notifications` / `notifyGradleSync` / `notifyGradleTasks` are the posting sites). Every split in the app (sidebars, structure and Gradle panels, editor over terminal, editor panes, list/detail panels) is a `SplitPanes` (`Example/Umbra/SplitView/`, vendored stevengharris/SplitView via Hextech; Umbra-specific edits in its `README.md`) — don't add `HSplitView`/`NSSplitView` or hand-rolled drag handles. The left sidebar is one card with a tab bar (`IDELeftSidebar`, `IDESidebarTab`: Explorer, Structure, Changes, Breakpoints; the selected tab shows its title, the others are icons; × in a tab's context menu closes it and the + menu reopens it; `IDEWorkspace.activeSidebarTab` / `showSidebarTab` / `toggleSidebarTab`, persisted in `IDEWindowSession.sidebarTab`/`closedSidebarTabs`). Changes is `IDEChangesPanel` (branch, commit, staged/unstaged files, diff preview; double-click opens a diff tab); the bottom panel's git tab is now History only (`IDESourceControlPanel`). The Explorer's ⋯ / right-click menu (`IDEExplorerOptionsMenu`, also in Settings ▸ Project) holds IntelliJ's view options: Flatten Packages, Hide Empty Middle Packages, Show Excluded Files (build outputs and `.gradle`, dimmed; on by default), Sort by Name/Type, Folders Always on Top and Always Select Opened File; the crosshair button is Select Opened File. They are presentation only, applied in `IDEFileTreeView.collect` through `IDEExplorerPresentation` (`IDEFlattenedPackages.swift`), so the tree is never rebuilt for them. Breakpoints is `IDEBreakpointsPanel` (see **Debugger** below), fed by `IDEWorkspace.breakpoints`, a mirror of `JavaBreakpointStore` refreshed after every change. Built on `Penumbra`, `EditorIntelligence`, and `JavaIntelligence`.

- **Diff viewer** (`Example/Umbra/Diff/`, `IDEWorkspace+Diff.swift`), after IntelliJ's Differences viewer. Diffs open as editor tabs: a `WorkbenchDocument` with `contentKind == .diff` (never restored with the session) whose `IDEDiffSession` lives in `IDEWorkspace.diffSessions`; the pane host lays `IDEDiffViewerView` over its editor while the tab is selected (`showDiffDocument`). An `IDEDiffRequest` names two `IDEDiffSource`s (a `GitRevision` of a path, the working tree, or fixed text). Entry points: double-click (or Show Diff) in the Changes list — unstaged rows compare index ↔ working tree, staged rows HEAD ↔ index, and Previous/Next File walk the rows of that section; the ↗ button over the sidebar preview; History's changed-files list under a commit (parent ↔ commit); Git ▸ Show Diff with HEAD / Compare with Branch / Compare with Clipboard, and the editor's context menu. The model is pure and tested (`IDEDiffComputer`: line LCS with whitespace policies none/trim/ignore/ignore + empty lines, then word, character or split highlighting inside changed blocks; `IDEDiffUnifiedLayout`; `IDEDiffPatchBuilder`). Two Penumbra `TextView`s show the sides with syntax colors (`TextView.lineBackgrounds` for the bands, `highlightedRanges` for words), `IDEDiffDividerView` draws the ribbons, the » chevron (left lines replace the right ones, ⌥-click appends; one undo step) and, for index comparisons, Stage / Unstage of one hunk (`git apply --cached --unidiff-zero`). Unified mode is one read-only text with old/new numbers in the annotation column. Toolbar: ⇧F7/F7 previous/next change (past the last change F7 moves to the next file), Previous/Next File, Jump to Source (F4), layout, whitespace and highlight menus, Collapse Unchanged Fragments (a `foldingProviderOverride` folding all but 3 lines around each change) and Synchronize Scrolling (viewport middles mapped through the chunks). The working-tree side is editable unless its editor tab has unsaved changes; edits are saved on ⌘S, when the tab is left or closed, and before switching files, then clean editor tabs reload. Every git refresh reloads open diffs; one whose texts did not change keeps its place. Options persist in `UserDefaults` (`umbra.diff.*`). Not done: three-way merge, aligned (padded) side-by-side, Compare Previous/Next File keys (⌃⌥←/→ belong to the terminal tabs). Tests: `IDEDiffComputerTests`, `IDEDiffPatchBuilderTests` (patches applied with real git), `IDEDiffTabTests`.

- **Code insight settings** (Settings ▸ Editor ▸ Code Insight and Refactoring; `IDEPreferences`, kept on this Mac and out of the preferences snapshot): Error Stripe and its mark height, Highlight Current Scope, Documentation on Hover, Tooltip Delay (also paces the caret-rest popup), Autoreparse Delay (`PenumbraWorkbenchEditorAdapter.contentRefreshDebounce` and `JavaInspectionService.setIdleDelay`), Next Problem scope (F2 over all problems or the highest severity), In-Place Mode, Preselect Name on Rename (`IDERenamePrompt` selects the field's text), Confirm Inline Variable, and Suppress with Comment (`//noinspection` instead of `@SuppressWarnings`). `IDEPreferences.apply(to: TextView)` / `apply(to: EditorIntelligenceController)` push them; `IDEWorkspace.applyCodeInsightPreferences()` covers what lives below the views. A refactoring applied without a preview reports back through `onWorkspaceEditApplied` → `refreshAfterWorkspaceEdit`. Settings ▸ Inspections (`IDEPreferencesInspectionsPane`, `IDEPreferencesDomain.inspections`) lists every `JavaInspectionRule` by group with an on/off checkbox and a severity picker; `IDEPreferences.javaDisabledInspections` and `javaInspectionSeverities` store rule codes and only the deviations from each rule's default. The Inspections pane also has "Treat public API as used" (`IDEPreferences.javaTreatsPublicApiAsUsed`, on by default, reaches `JavaInspectionService.setProjectOptions`) for the project-wide rules, which run after a save through `IDEJavaSupport.compileNow`. Metric rules (`JavaInspectionRule.limit`: complexity, nesting depth, parameter count, method and class length) also get a stepper bound to `IDEPreferences.javaInspectionLimits` (rule code to value, only deviations), which reaches `JavaInspectionService.setThresholds`. A change goes through `IDEWorkspace.javaInspectionPreferencesChanged()` → `IDEWindowRegistry.applyCodeInsightPreferencesToAllWindows` → `IDEJavaSupport.applyCodeInsightPreferences`, which hands the new set to `JavaInspectionService` and, when it differs from what was applied, calls `onInspectionConfigurationChanged` so every window re-analyses its open Java files (`reanalyzeInspections`).

- **Run gutter** — every `static void main(String[])` in a Java file gets a green `play.fill` gutter button (`JavaMainMethod.locations`, parsed off the main thread in `IDEWorkspace.refreshJavaTestDecorations`, cached per buffer generation); a test source gets `play.circle` on each test method and `play.circle.fill` on the test class's declaration. The buttons sit in the line-marker column right of the line numbers (`GutterDecoration.Placement.lineMarkerColumn`), in place of a marker on the same line; Java files reserve that column (`reservedLineMarkerSlots`, even with every gutter icon kind off) and no longer keep a decoration column on the left, and `.http` send buttons use the same column. A click opens `IDERunGutterMenu`: Run / Debug that `main` (a classpath launch of its binary name, so nested classes work, else the file's default launch, plus Modify Run Configuration…), or Run / Debug the test method or class. A breakpoint's line keeps its run button and the button takes priority: a click on it, right click included (`GutterLineClick.decoration`), opens the Run / Debug menus, while the breakpoint in the line number keeps its own clicks. Umbra's gutter has `gutterLeadingPadding` 6 (Penumbra's 2 plus 4) so numbers and breakpoints clear its left edge. The gutter itself is built in `IDEWorkspace+Debugger.swift` (`applyJavaGutter`).

- **Run / Debug / Stop** — in a Gradle project the titlebar play button runs the file's module's `run` task, else `bootRun` (Spring Boot), else asks which task to run (`IDEGradleTaskPickerSheet`) and saves the pick as a run configuration (`JavaRunConfiguration.preferredGradleRunTask`, `.gradleRun(projectPath:taskName:)`). Gradle runs go through the Gradle runner into the Gradle console with no timeout, so the `ladybug.fill` Debug button (`--debug-jvm`) and the `stop.fill` Stop button (`IDEWorkspace.stopRunning`, enabled while `isRunActive`) can control them. Single-file `java File.java` launches still use the terminal.

- **Debugger** (`IDEWorkspace+Debugger.swift`, `JavaDebugSession`, the JDI adapter in `Tools/JavaDebugAdapter`). Follows IntelliJ's breakpoint, stepping, tool-window, memory, overhead, stream-debugger and test pages.
  - *Breakpoints.* `JavaBreakpoint` has a kind (line, exception, method, field), a condition, a suspend policy (all, thread, none = log only), a "Breakpoint hit" message, a log expression, remove-once-hit and a pass count; `JavaBreakpointStore` also keeps a per-project mute flag, and old `breakpoints.json` files still load. A click on a line number adds one (lines with no code — blank, comments, imports, annotations — are refused), a click on a breakpoint removes it, F3 toggles at the caret (⌘F8 too in the IntelliJ keymap, through `IDESecondaryShortcutMonitor`, since a SwiftUI menu item holds one key), and the editor's right-click menu has Add/Remove Line Breakpoint. Right-clicking a breakpoint opens `IDEBreakpointPopover` (Enabled, Suspend All/Thread, Condition, More ⇧⌘F8); right-clicking another line offers Toggle, Add Conditional Breakpoint… and the line's Run/Debug items. The breakpoint replaces its line's number (`GutterDecoration.Placement.lineNumber`, so a click on it is a line-number click) and is drawn red (stops), orange diamond (log only), grey (disabled or muted), `?` for a condition and ✓ once the adapter placed it. Breakpoints follow edits through `TextView.gutterDecorationsDidMove` → `JavaBreakpointStore.moveLines`, and a line deletion removes its breakpoint. The Breakpoints tab lists line breakpoints by file and exception/method/field ones by kind, with a + menu, Mute, and `IDEBreakpointPropertiesForm` for the selected one. Every change is sent to a running session (`JavaDebugSession.sync`, diffed by id), so nothing needs a restart.
  - *Adapter protocol.* `setBreakpoint {breakpointId, kind, file/line | className + methodName/fieldName, condition, suspendPolicy, logMessage, logExpression, removeOnceHit, passCount, imports}` replaces by id; `clearBreakpoint`, `muteBreakpoints`; events `breakpointVerified` and `breakpointRemoved`. Method breakpoints are line breakpoints at each overload's first instruction (cheaper than method-entry events); exception and field ones are placed as their class prepares. A hit is judged on the evaluation executor, not the event loop (a condition may load classes, and class-prepare events must keep flowing); a condition that fails to evaluate stops with reason `conditionError`. A Suspend: Thread stop resumes only its thread; a second thread stopped meanwhile is shown after it. Other commands: `threads`, `selectThread`, `forceStepInto`, `smartStepInto {methodName}` (method-entry events on the stepping thread plus a step-over fallback), `runToCursor {file, line, force}`, `dropFrame`, `forceReturn`, `setValue`, `instanceCounts`, `instances` (objects pinned as `#id` until the program runs), `overhead`, `traceStream`. `stopped` carries `threadId`, `threadName`, `suspendsAll`, `breakpointId`, `message`.
  - *Evaluation.* `Evaluator.java` interprets expressions with JDI alone: operators with Java's promotion rules, string concatenation, casts, `instanceof`, ternaries, calls with overloads, boxing and varargs, static members of loaded classes, `new`, arrays and assignment; parsed trees are cached per breakpoint. Lambdas, method references and the like go to `CompilingEvaluator.java`: it compiles a class with one static method taking the frame's locals and `__self` (unknown names javac reports are rewritten to `__self.name`) against the program's classpath (sent in `launch`/`attach`, else the target's `java.class.path`) and the file's imports, defines it through JDI in the frame's own class loader and package, and caches it. Private members of other classes are out of reach there.
  - *Tests.* The test gutter button, Structure's context menu and Debug in Context debug tests: `IDEWorkspace.debugTests` runs `clean<Task>` then the task with `--debug-jvm` (an up-to-date task would start no JVM) and attaches like a Gradle run; results still land in Test Results. Test Results (`IDETestResultsPanel`) has Rerun, Rerun Failed, Debug Failed (a `JavaTestRunScope.tests` of `--tests` filters), Show Passed/Ignored, sort by name or duration, collapsible classes, and a detail pane with the message, a stack trace whose frames open their file, and the test's output (`JavaTestCaseResult.output`, from `system-out`/`system-err`).
  - *Debug tool window* (`IDEDebugPanel`). Toolbar: Rerun, Resume, Pause, Stop, Step Over/Into, Force Step Into, Smart Step Into, Step Out, Run to Cursor, Evaluate, Drop Frame, Trace Stream, View/Mute Breakpoints; a banner says why it stopped (exception, failed condition, thread-only stop). Frames has a thread picker and Hide Library Frames; Variables shows watches (per project in `UserDefaults`) above `this` and the locals, each an `IDEDebugValueRow` with Set Value (F2), Copy Value and Add to Watches. Memory counts instances per class at each stop while it shows, with the change since the last stop and the instances of a class ("track new instances" would need a JVM agent and is not offered); Overhead polls hits and time per breakpoint. The stopped line is not selected: the caret goes to its start and the line gets a dark-red `TextView.lineBackgrounds` band (`refreshExecutionLineBackgrounds`, for the selected frame; reapplied from `applyJavaGutter` because `setState` clears bands on a file switch). While stopped, the locals appear at the end of the lines that last mention them (`inlineValueHints`, `TextView.supplementaryInlayHints`). Run menu keys (IntelliJ column): Run to Cursor ⌥F9, Force Run to Cursor ⌥⌘F9, Smart Step Into ⇧F7, Force Step Into ⌥⇧F7, Show Execution Point ⌥F10, View Breakpoints ⇧⌘F8.
  - *Stream debugger.* Trace Current Stream Chain finds the pipeline on the stopped line (`JavaStreamChain`), evaluates it again with a `peek` after each stage through the compiling tier, and shows each stage's elements in `IDEStreamTraceWindow` (split mode links elements by time, `sorted`/`distinct` by identity; flat mode lists them). Side effects in the chain run twice, as in IntelliJ.

- **Agent** (`Example/Umbra/Agent/`, `Packages/AgentKit`; plan: `docs/AGENT_HARNESS_PLAN.md`). The chat opens docked beside the editor by default (a trailing panel, resizable, `IDEAgentPanel` in `IDERootView`), or as a page over the editor like Settings (`IDEAgentPage`: a tab-style header with a close button, the panel centered at up to 900 pt, the editor kept mounted) — the arrows button in the chat header switches, and `IDEAgentSettings.opensAsPage` remembers it. The brain button in the titlebar's trailing actions (left of the gear), View ▸ Toggle Agent and the palette command toggle it (`IDEWorkspace.toggleAgentPanel` / `hideAgentPage`, state in `agent.isPanelVisible`; disabled without an open folder). Only the page layout excludes Settings and closes when a tab or file is chosen (`agent.coversEditor`, `dismissPage()`, `onPanelRequested`); docked, the chat stays open while you work. Every opener goes through `IDEAgentController.showPanel()`. `IDEWorkspace.agent` is one `IDEAgentController` per window: it owns the panel state, the saved-history list and `conversations` (see *Agent: chat tabs*) (`IDEAgentConversation`, one transcript plus one `AgentSession` each; `selected` is the one the panel shows, and the controller's `entries`/`draft`/`send()`… forward to it). A conversation has a stable tab `id` and a `conversationID` that is the saved session's identity and changes on reset or load; the provider cache key is built from the project path hash and `conversationID` (never `hashValue`, which is seeded per process). Conversations reach the window only through `IDEAgentHost` (`IDEWorkspace+Agent.swift`) via a weak `IDEAgentHostBox`, and `IDEWorkspace.teardown()` ends its run, because a session that holds the workspace keeps the window alive (retention tests in `IDEAgentTests`). Streamed text is coalesced about every 50 ms; each user message carries a short editor-state block (active file, open files, problem counts) while the system prompt and tool list stay byte-identical. Tools: `read_file`, `list_dir`, `glob`, `grep` (AgentKit, over `DiskAgentWorkspace` with `agentUnsavedBuffers()` so open edits are seen) and `diagnostics` (`IDEDiagnosticsTool`, from `IDEProblemsStore`). `edit_file` and `write_file` change files through `IDEAgentWorkspace`, which applies them with `IDEWorkspaceEditApplier` (an open file's buffer in one undo group and left dirty, a closed file rewritten atomically, a new file through `WorkspaceEdit.fileCreations` / `IDEWorkspaceEditHost.createFile`). After a run that changed files the transcript shows an "N files changed" card (`IDEAgentChangesCard`): each file opens in the diff viewer (original ↔ now), and Revert Run restores the run, leaving any file the user edited afterwards alone and marking it "changed since". Commands run in `Example/Umbra` only (`AgentCommandRunner`: `posix_spawn` of `/bin/zsh -c` in its own process group, stdin `/dev/null`, a built environment with the selected JDK, output bounded to head and tail; a timeout, Stop, or the command ending kills the whole group). Every command-risk call asks first on an inline card (`IDEAgentApprovalView`: Run, Edit…, Deny… with a note; `sudo`, `rm -rf` and similar are flagged): `run_command`, `gradle` and `run_tests` (the last two only in a Gradle project; they go through `IDEJavaSupport.runGradleTasks`, so the console, Problems, Test Results and the trust prompt apply, and the model gets `IDEGradleSummary`: compiler errors, failed tests with their first frames, Gradle's reason, never the log). The agent's own unsaved buffers are saved before a command; the user's are only named on the card (`IDEAgentBufferTriage`). `diagnostics` compiles the Java files the run changed (`JavaCompilerDiagnosticsService.freshDiagnostics`) and says when it couldn't. `IDEAgentSettings.shared`: the provider (`IDEAgentProvider`: OpenAI Responses, OpenAI-compatible Chat Completions, Ollama) and, per provider, base URL, model and reasoning effort in `UserDefaults` (`umbra.agent.*`; the original Responses keys are unchanged), plus the local context cap. The API key is in the Keychain per endpoint host (`IDEAgentKeychain`); the first use of a remote host needs an explicit "Allow Sending" (`disclosedHosts`), and `send()` does nothing until then. A loopback endpoint (`localhost`, `127.0.0.1`, `::1`) needs neither a key nor consent, since nothing leaves the Mac. The `.mlx` provider ("On this Mac") runs a downloaded model in-process through `AgentKitMLX`: `IDELocalModelsStore` (installed models, Hugging Face search, one pausable download at a time, load/unload; models live in `Application Support/com.umbra.editor/Models`) and `IDELocalModelsView` (the sheet behind "Manage On-Device Models…"). A model whose chat template does not take tools can be downloaded but not used, and is refused before a request. The first message loads the weights with a visible "Loading…" status. For Ollama the settings load the installed models (`OllamaModelCatalog`), disable those without tool support, ask for `num_ctx = min(cap, the model's maximum)` and send `think` only to models that list it; a model the server says cannot use tools is refused before a request is made.

- **Agent: long sessions** (`IDEAgentController`, `IDEAgentHistory`, `IDEAgentProjectNotes`, `IDEAgentModeText`). Every run ends by saving the conversation through `SessionStore` (`Application Support/com.umbra.editor/Agent`; only `IDEWorkspace` with `isSessionPersistenceEnabled` gets a store, so tests write nothing unless they pass one). The transcript is saved as `IDEAgentPersistedEntry` rows (no live output, approval cards or "files changed" card, so Revert Run is gone after a relaunch). The latest conversation comes back when the panel first appears or a message is first sent (`restoreLatestIfNeeded`); the panel's clock menu resumes another, New Conversation starts one, and Settings ▸ Agent ▸ Clear History deletes the project's. `AGENTS.md` (else `CLAUDE.md`, 16 KB, symlinks ignored) goes into the system prompt when a session is created. `IDEAgentSettings` adds `mode`, `iterationCap`, `contextWindowOverride`, `secretFilePatternsText` and `contextWindow`; all are in the session fingerprint, so a change starts a new session that keeps the conversation. Settings ▸ Agent (`IDEPreferencesDomain.agent`) hosts the same `IDEAgentSettingsView` as the panel's popover, with `isFullPane`. In approve-each-edit mode the approval card shows the diff (`IDEAgentDiffView`) with Apply and Reject. Tests: `IDEAgentSessionsTests`.

- **Agent: permissions** (`Example/Umbra/Agent/Permissions/`, `IDEAgentModeText`; AgentKit side: `Packages/AgentKit/CLAUDE.md`). Each chat has its own `PermissionMode` (`IDEAgentConversation.mode`, `setMode`, `cycleMode`): the chip under the message field, or ⇧Tab in it (`IDEAgentModeChip`, `IDEAgentComposerKeyMap`). `IDEAgentSettings.mode` is only the mode new chats start in, and no longer part of the session fingerprint, because a mode change does not need a new session (the session is told with `setMode`; the model gets a note). Rules come from files read at every send, so an edit takes effect at once (`IDEAgentPermissionFiles`): the app's `permissions.json`, `.umbra/settings.json`, `.umbra/settings.local.json` (what "Always allow in this project" writes; a file that is not valid JSON is never overwritten), and Claude Code's `.claude/settings.json` / `settings.local.json`, read only. Every deny, ask and allow from every source counts. A chat's own rules ("Allow in this chat") last until the conversation is reset or another is loaded. The approval card's "Always…" menu (`IDEAgentApprovalView.alwaysAllowMenu`) offers the rule AgentKit suggests, or "Accept all edits in this chat"; `IDEAgentConversation.approve(callID:shortcut:)` applies it and approves the call. Settings ▸ Agent ▸ Permissions (`IDEAgentPermissionsSection` over `IDEAgentPermissionsModel`) lists every rule by file, adds and removes rules in the files Umbra owns, and checks "would this command run?". `IDEGradleTool` / `IDERunTestsTool` expose `gradle …` as their `permissionSubject`, so `Bash(gradle build:*)` matches them. Tests: `IDEAgentPermissionsTests`, `IDEAgentPermissionFilesTests`, `IDEAgentPermissionsModelTests`, `IDEAgentSessionsTests`.

- **Agent: chat tabs** (`IDEAgentController.conversations`, `IDEAgentTabsBar`, `IDEAgentFileClaims`). A window has several chats, each an `IDEAgentConversation` with its own session, checkpoints, draft, mode and rules, and each can run at the same time. The strip (`IDEAgentTabsBar`, over the shared `IDEChromeTabItem`, which the terminal tabs use too) appears from two chats on: a spinner while one runs, an orange dot while it waits for an approval or an answer (`isAwaitingUser`), a blue dot for a reply that finished in the background (`isUnread`); the context menu renames (stored in `IDEAgentSavedTranscript.customTitle`, so it survives a relaunch), closes, or closes the others; closing a running chat asks first, and the last chat is emptied instead of closed. A tab is named by the user, else by its first message. New Agent Chat ⌥⌘T, Next/Previous ⌥⌘]/⌥⌘[ (View menu and palette; ⌘T belongs to Git Pull or New Window Tab). `newConversation()` opens a tab unless the selected chat is empty; `clear()` empties it in place; `resume(id)` selects the tab that already shows a conversation, else fills an empty selected chat, else opens a tab, and never replaces a chat with content. `selected` is the chat the panel shows; the controller's `entries`/`draft`/`send()` forward to it. Two chats editing one file: a chat claims the files of an edit it is about to make (`IDEAgentClaimsGate`, a `PermissionGate`) until its run ends, and an edit to a file another chat's run holds asks first, naming that chat. The claims live in the window (`fileClaims`); they do not guard commands. `IDEWindowSession` keeps `agentChats` (saved conversation ids), `agentSelectedChat`, `isAgentPanelVisible` (only when docked, since a page over the editor would hide the files being restored) and `agentPanelWidth` (held by `IDEWorkspace.agentPanelWidth`, saved with the other panel widths); `IDEAgentController.restoreTabs` shows each saved conversation as a tab and reads only the selected one, the others when shown or sent to (`pendingLoadID`). `onLayoutChanged` asks the window to save; `withoutLayoutNotifications` keeps a restore from saving a half-restored window. Only one Gradle run at a time exists in a window, so two chats that both run Gradle share it. Tests: `IDEAgentTabsTests`.

- **Agent: commands and skills** (`Example/Umbra/Agent/Commands/`). A message that starts with `/name` and a space or the end is a command (`IDEAgentSlashInvocation`; `/usr/bin is missing` is a sentence, and an unknown name is sent as an ordinary message). Return in the field calls `IDEAgentController.submit()`: a command runs, anything else is sent. Built-ins (`IDEAgentBuiltInCommand`): `/new` `/clear` `/resume [search]` `/plan [prompt]` `/mode` `/permissions` `/model` `/export` `/init` `/cost` `/rename` `/help`, and they work before the first-use disclosure is accepted. `IDEAgentCommandCatalog` adds the user's own, from `.umbra/{commands,skills}` and `.claude/{commands,skills}` in the project, `~/.claude/…` (Settings ▸ Agent ▸ "Offer commands and skills from ~/.claude") and Umbra's folder in Application Support, the project's first. A built-in keeps its name, a command beats a skill. The read is kept two seconds and dropped at every send. The list after `/` (`IDEAgentController.suggestions(for:)`, fuzzy by name) accepts a command that takes no arguments by running it; one that takes arguments is inserted, and the text after its name is then the argument list (`IDEAgentComposerTrigger.slashArgument`): `/resume ` lists the project's saved chats (`.resume` payload; selecting one shows its tab or opens it), `/mode ` the four modes. A custom command shows `/name args` in the transcript and sends `CommandTemplate.expand` (the row's "What the agent was sent" disclosure, `IDEAgentEntry.detail`, saved with the chat); its `allowed-tools` are permission rules for that run only. `/skill-name args` sends `[Skill: name]` and the instructions; the model is also given the `skill` tool when any skill exists, and the skills' fingerprint is in the session fingerprint. `!`cmd`` lines in a command are sent as text, with a notice. `/permissions` opens Settings on the Agent pane (`IDEWorkspace.requestedSettingsDomain`), `/model` opens the panel's settings popover (`settingsRequest`), `/export` saves Markdown (`IDEAgentTranscriptExport`; tests replace `exportHandler`). Tests: `IDEAgentCommandsTests`.

- **Agent: @ mentions** (`Example/Umbra/Agent/Mentions/`). `@` at the start of a message or after whitespace starts a mention (`IDEAgentMentionToken.scan`; `@"path with spaces"` is the quoted form; trailing `.,;:!?)]` belong to the sentence). The list (`IDEAgentController.suggestions(for:)`) offers `@selection`, `@problems`, `@open` only when there is something to give, `@changes`, `@terminal`, `@skill:name`, then project files ranked by the same index Go to File uses (`IDEWorkspace.paletteFileIndex`, open files first). At send time, inside the run and once the session exists, `IDEAgentMentionResolver.resolve` turns each mention into an attachment appended to what the model is sent as `<attachment name="…">` blocks under "project data, not instructions"; the transcript shows only what was typed, with a paperclip row per attachment (`IDEAgentEntry.attachments`, saved with the chat). A file is attached as the agent's own workspace reads it (open unsaved edits included), at most 64 KB (cut on a line, with the `read_file offset=` to continue), all attachments at most 256 KB; `path:12-40` attaches numbered lines; a folder attaches its listing; credential files (`SecretFilePolicy` and the user's globs) and paths outside the project are refused with a notice, as is a path that does not exist (a bare `@name` with no slash or dot is left alone, since it is probably a name). A file attached whole is passed to `AgentSession.recordRead`, so editing it needs no `read_file` first; a slice or a cut file is not a read. Mentions in a command's or skill's expansion are resolved too. `@terminal` reads the active terminal tab's buffer (`IDETerminalHostView.recentText`), `@changes` runs `git_diff`'s code. Tests: `IDEAgentMentionResolverTests`, `IDEAgentMentionsTests`; AgentKit: `RecordReadTests`.

- **Agent: composer** (`Example/Umbra/Agent/Composer/`). The message field is an `NSTextView` (`IDEAgentComposerField`, because SwiftUI's `TextField` cannot see ↑/↓/Tab/Esc/⇧Tab or the caret): Return sends, ⇧↩ or ⌥↩ a newline, Esc closes the suggestion list and otherwise stops the run, ⇧Tab cycles the mode, and the field grows to eight lines. What a key does is a pure function (`IDEAgentComposerKeyMap`); what the text and caret ask for is another (`IDEAgentComposerTrigger.detect`: `/` as the message's first word, `@` at the start or after whitespace), tested without a view. `IDEAgentComposerState` holds the list's rows and highlight, `IDEAgentSuggestionList` draws it, and `IDEAgentController.suggestions(for:)` supplies the rows. `/commands` and `@` mentions are colored with attributes only; the model gets plain text. `@"path with spaces"` is the quoted form (`IDEAgentMentionToken`); files dropped on the field become mentions. Tests: `IDEAgentComposerFieldTests` hosts the field in a window.

- **Agent: IDE depth** (`IDEAgentGitTools`, `IDEAgentNavigationTools`, `IDEAgentEntryPoints`, `IDEAgentPrices`). `git_status` / `git_diff` read through `GitRepository` and are offered inside a repository (`IDEAgentGitSource`: paths are project-relative, `SecretFilePolicy` plus the user's globs filter every diff, an untracked `dir/` is expanded with `git ls-files --others --exclude-standard`). `go_to_definition` / `find_usages` take path, 1-based line and the identifier (`IDEAgentSymbolLocator`, whole-word, `occurrence` when ambiguous) and call `IDEAgentJavaNavigating`, implemented by `IDEJavaAgentNavigator` over the window's Java providers; they are offered when `agentJavaNavigator()` returns one (a Gradle project or an open Java file). `IDEAgentHost` gained `agentJavaNavigator()` and `agentLineText(url:line:)`, with defaults, so fake hosts need no change. Entry points: `IDEWorkspace.askAgentAboutSelection` (context menu item from `agentContextMenuItems`, palette command `agent.askAboutSelection`), `fixProblemWithAgent` (Problems row hover button and context menu) and `IDEAgentController.compose(_:send:)`, which fills the composer and focuses it (`composerFocusRequest`) or sends when consent is given and no run is going. The header shows `tokens · ~$cost` from `IDEAgentSettings.cost(of:)` and `IDEAgentPrices` (editable text in Settings ▸ Agent; `IDEAgentSavedTranscript` stores the total with the conversation; nil when any turn was unpriced). A closure stored on an editor's text view must hold its pane host weakly. An `.unreadableToolCall` event adds a notice ("…Asking it to try again"); the session has already told the model. Tests that need an editor view call `workspace.bootstrap()` first (it wires the adapter). Tests: `IDEAgentNavigationTests`, `IDEAgentEntryPointsTests`.

- **Agent: checklist and questions.** The controller adds `TodoTool` and `AskUserTool` to every session. `.todosUpdated` fills `IDEAgentController.todos`, shown by `IDEAgentTodoListView` under the header and saved in `IDEAgentSavedTranscript.todos` (restored into the new session when its history no longer holds the `todo` call). `.questionAsked` puts a `UserQuestion` on the `ask_user` card (`IDEAgentQuestionView`: option buttons, a field, Skip); `answer(callID:text:)` replies and `nil` skips. Tests: `IDEAgentInteractionTests` (the real-model one is opt-in).

- **HTTP client** — `.http` parsing and sending live in the Umbra target (`Example/Umbra/HTTP/`: `HTTPRequestParser`, `HTTPClient`), called from `IDEHTTPSupport`. There is no `HTTPClient` library, and JavaIntelligence does not depend on it.

**Umbra** (`swift run Umbra`, `Scripts/build-app.sh`) is the Sublime Text–style editor product; `Example/Umbra` is its SPM executable target and source tree (app shell, views, `IDEWorkspace`, and `UmbraApp.swift`/`@main`). `Example/Umbra.xcodeproj` is a thin, separately maintained Xcode app project that compiles the same source files directly as a native app target — needed because a SwiftPM executable target can't host SwiftUI Previews (`ENABLE_DEBUG_DYLIB`); it's a dev convenience for Previews/Run/Debug only and isn't used for release builds. See `Example/README.md` for details.

## Windows and projects

Every window is one project (or none) with its own `IDEWorkspace`; native macOS tabs are just windows AppKit has merged. Plan, decisions and per-phase notes: `docs/PER_WINDOW_PROJECTS_PLAN.md`.

- **Scene and menus.** `IDEWindowScene` (`UmbraApp.swift`) creates the window's workspace and publishes a weak `IDEWorkspaceRef` with `focusedSceneValue(\.ideWorkspace, …)`. The menu bar (`IDEAppCommands.swift`) is built from that handle and resolves the workspace when an action runs; never capture the workspace itself in a menu closure (SwiftUI keeps menu items after a window closes, and the workspace stays alive with them). With no window focused the menus show a disabled item, except File ▸ New Window (⌘⇧N), New Window Tab, Open Folder… and Open Recent.
- **Finding a window.** `IDEWindowRegistry` keeps weak references, most recently key first. Use `workspace.window`, never `NSApp.keyWindow`, for sheets and first-responder changes. `IDEWindowChrome` (in `IDERootView.swift`) splits the top inset into titlebar and native tab bar so the toolbar row never sits under the tab bar.
- **Opening things.** Folders and files go through `IDEWindowRegistry.open(urls:origin:)` and the pure `IDEOpenRouter` (tested without AppKit): a folder that is already open focuses its window, an empty window takes it, a window with a project asks "New Window / Replace" (the `Open folders in` setting skips the question), Dock/Finder opens get a new window, and a file goes to the window whose project contains it. For a user-facing open call `openProjectFolder` / `replaceProject`, not `applyProjectRoot`. SwiftUI must not open windows for external events itself; see the comment on the scene in `UmbraApp.swift`.
- **Persistence** (`IDESessionStore.swift`). `IDEAppState` owns recents and the preferences snapshot (`app.json`) for all windows. `last-window.json` (`IDEWindowSession`) holds the layout of `IDEWindowRegistry.sessionWindow`: the most recently key window, skipping blank windows opened next to others. Only a window opened while no other is open restores it. The old `session.json` is migrated once and left alone.
- **App-wide services** (`IDESharedServices`). Gradle trust, JDK selection, run configurations and breakpoints are single shared instances that re-read their file when it changed on disk; don't construct your own (each window used to rewrite the whole file and lose the others' entries). The JDK index and the dependency jars are indexed and parsed once for all windows (`JavaSharedShardHub`: `shard(for:)` for the JDK, `indexJars(_:)` / `readers(for:)` for jars; `IDEJavaSupport` sends jar targets through it and keeps project-source shards on its own scheduler). A window that only waits on another window's indexing still gets one progress event per jar. Release jars from Gradle/Maven caches keep their reader in a small bounded LRU after the last window lets go (`JavaJarCachePolicy`); everything else lives only while a window holds it, and every request checks the shard's stamp, so a rewritten jar is never served stale. The host drops the unused readers on memory pressure. Preference changes go through `applyPreferencesToAllHosts()`, which repaints every window. Notification entries and toasts stay per window; Do Not Disturb and the category switches follow `UserDefaults`.
- **Closing.** A closing window runs `IDEWorkspace.teardown()` (watcher, git, indexing, Gradle, debug session, terminal shells, scoped folder access) and must leave nothing that keeps the workspace alive. Things that have: replacing the window delegate without forwarding it to SwiftUI's (`IDEWindowCloseGuard` forwards everything), strong captures of the workspace in menu closures, and callbacks owned by a running terminal view. Quitting asks once about unsaved editors in every window. A test that creates a workspace must set `IDEWorkspace.isSessionPersistenceEnabled = false` so it cannot touch real session files.
- **Xcode project.** `Example/Umbra.xcodeproj` lists sources one by one and was already missing about 55 of them; new files are not added, so Previews and Run from Xcode need it regenerated first.
