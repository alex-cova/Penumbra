# Umbra (`Example/Umbra`)

Loaded when working under `Example/Umbra`. Moved out of the root CLAUDE.md. Per-area notes sit beside the code and load when you work there: `Agent/`, `Coverage/`, `Profiler/`, `Run/`, `Git/`, `Diff/`, `Diagrams/`, `HTTP/`, `Inspections/`, `LocalHistory/`, `Saving/`, `TextTools/`, `SwiftUIPreview/`, `Swift/`, `ProjectWizard/`, `Projects/`, `Languages/` (each a `CLAUDE.md`).

- **`Umbra`** (`Example/Umbra`) — the macOS editor app shipped with this repo, intended as a **Sublime Text alternative**: lightweight, fast editing with project folders, split panes, symbol-aware navigation, session restore, a Problems panel (⌘⇧M; `IDEProblemsStore`/`IDEProblemsPanel`, a bottom-panel tab selected through `IDEBottomPanelTab`), and Java completion with Gradle module and dependency sync, hover with Javadoc, go to implementation, quick fixes, and saved run configurations (Java menu: Run Last Configuration ⌃⌥R, Edit Configurations…, Reformat Code ⌥⌘L, Optimize Imports, Show Context Actions ⌥↩; Optimize Imports on Save and the other actions on save live in Settings ▸ Saving; see `Saving/CLAUDE.md`). Build Project runs through the active Java build (Gradle, or Maven for a Maven project) and asks for trust before a process starts, so its compiler errors land in the Problems panel (Sublime keymap by default). Find Usages results go to a Usages bottom-panel tab (`IDEUsagesPanel`, `IDEBottomPanelTab.usages`); Rename… (⇧F6 in the IntelliJ keymap) prompts for a name, shows a preview sheet (`IDERenamePreviewSheet`) and applies through `IDEWorkspaceEditApplier` (live buffers via `TextEditApplicator`, closed files written atomically inside the project folder). Finished Gradle syncs/builds and git actions are posted to `IDENotificationCenter` (`Example/Umbra/IDENotifications.swift`; the titlebar bell opens `IDENotificationPanel`, a toast announces each one — errors stay until dismissed — and live sync/indexing progress stays a separate `IDEStatusToast` card; Do Not Disturb and per-category switches persist in `UserDefaults`; `IDEWorkspace.notifications` / `notifyGradleSync` / `notifyGradleTasks` are the posting sites). Every split in the app (sidebars, structure and Gradle panels, editor over terminal, editor panes, list/detail panels) is a `SplitPanes` (`Example/Umbra/SplitView/`, vendored stevengharris/SplitView via Hextech; Umbra-specific edits in its `README.md`) — don't add `HSplitView`/`NSSplitView` or hand-rolled drag handles. The left sidebar is one card with a tab bar (`IDELeftSidebar`, `IDESidebarTab`: Explorer, Structure, Changes, Breakpoints, History; the selected tab shows its title, the others are icons; × in a tab's context menu closes it and the + menu reopens it; `IDEWorkspace.activeSidebarTab` / `showSidebarTab` / `toggleSidebarTab`, persisted in `IDEWindowSession.sidebarTab`/`closedSidebarTabs`). Changes is `IDEChangesPanel` (branch, commit, staged/unstaged files, diff preview; double-click opens a diff tab); the bottom panel's git tab is now History only (`IDESourceControlPanel`). The Explorer's ⋯ / right-click menu (`IDEExplorerOptionsMenu`, also in Settings ▸ Project) holds IntelliJ's view options: Flatten Packages, Hide Empty Middle Packages, Show Excluded Files (build outputs and `.gradle`, dimmed; on by default), Sort by Name/Type, Folders Always on Top and Always Select Opened File; the crosshair button is Select Opened File. They are presentation only, applied in `IDEFileTreeView.collect` through `IDEExplorerPresentation` (`IDEFlattenedPackages.swift`), so the tree is never rebuilt for them. Breakpoints is `IDEBreakpointsPanel` (see **Debugger** below), fed by `IDEWorkspace.breakpoints`, a mirror of `JavaBreakpointStore` refreshed after every change. Full-line completion (`Example/Umbra/Completion/IDEInlineCompletionService.swift`) runs a local MLX model on its own dedicated `LocalModelRuntime` (10-minute idle unload, lazy first load), builds the Qwen2.5-Coder FIM prompt (or prefix-only without a FIM format), and is registered in `IDEIntelligenceServices.makeController` with the Java validator; it is opt-in in Settings ▸ Editor ▸ Code Completion, where the chosen model can be loaded or unloaded, Qwen2.5-Coder 1.5B can be downloaded in one click, and another model can be found by searching Hugging Face. The model choice is machine-local in `IDEPreferences`. Built on `Penumbra`, `EditorIntelligence`, and `JavaIntelligence`.

- **Changed lines** (`IDEChangeMarkers.swift`). A stripe just to the right of the line numbers marks lines that differ from `HEAD`: green for added, blue for modified, a red triangle where committed lines are gone. On by default inside a repository (Git ▸ Hide Changed Lines / Highlight Changed Lines, `UserDefaults` key `umbra.editor.highlightChangedLines`); off, or outside a repository, the column takes no width. Staged and unsaved edits both count, and the bar stays until the change is committed. `IDEChangeMarkerController` diffs the live buffer (`exportDocumentText()`, materialized off the main actor) against a cached `HEAD` blob (`IDEGitStatusModel.headContents`) with `IDEDiffComputer.lineChunks` (no word refine; a differing middle longer than 20,000 lines is one span). Typing moves the spans immediately and the diff replaces that guess after a short pause. A click does nothing. Tests: `IDEChangeMarkerTests`.
- **CSV table preview** (`Example/Umbra/CSVPreview/`). A `.csv`, `.tsv` or `.tab` file (`LanguageIdentifier`: `csv`/`tsv`, no grammar, so plain text) gets the same titlebar play button as Markdown and JSON (⌘B, View ▸ CSV Table). It covers the editor with `IDECSVTableView`, a read-only virtualized `NSTableView` (row numbers, resizable columns, click a header to sort — natural order, numeric when the whole column is numbers —, ⌘C copies the selected rows, a double-click closes the table and puts the caret on the row's source line). A search field above the table (⌘F focuses it while the table shows, `IDEWorkspace.showFind`; Esc clears it, then returns to the table) hides rows with no cell containing the text (case- and diacritic-insensitive, 120 ms after typing stops), highlights the matches and reports "N of M rows match" in the footer; it keeps filtering across live re-parses. `IDEEditorPaneHost` owns it like the JSON diagram (`toggleCSVTable`, `noteCSVTableEdited` re-parses 200 ms after the last edit; the buffer is read after the pause and parsed off the main actor, a superseded result is dropped) and `IDEWorkspace.isCSVTableVisible` drives the button. `IDECSVTable.parse` is pure (RFC 4180 quoting, `\n`/`\r\n`/`\r`, blank lines skipped, ragged rows padded, first record is the header, at most `maximumRows` = 200,000 rows with a footer note) and `delimiter(forIdentifier:sample:)` picks comma, semicolon or tab from the first line. Tests: `IDECSVTableTests`.

- **File encoding** (status bar, `IDEStatusBarPanel.encodingPicker`; engine: `Sources/Penumbra/CLAUDE.md` ▸ Editing & input). The label left of `LF` is the active text document's `WorkbenchDocument.encoding` (`IDEWorkspace.statusEncoding`, set in `updateStatus`); clicking it opens two submenus over `TextFileEncoding.all`. **Reopen with Encoding** (`reopenActiveDocument(with:)` → `reloadTabFromDisk(_:in:encoding:)`) reads the file again in that encoding, asking first when the tab has unsaved edits and reporting bytes that do not fit (`IDEEncodingError`); **Save with Encoding** (`saveActiveDocument(with:)`) converts and saves, asking for a name when untitled, and keeps the old encoding when the save does not happen (a character the target cannot hold writes nothing). Opening auto-detects: a byte-order mark, else UTF-8, else a guess from the first megabyte (`TextFileEncoding.guess`, Windows-1252 for Western text). A known binary type, or unknown bytes that sniff as binary, opens in the hex editor; an explicit Reopen with Encoding that cannot decode the file still reports the error. Reloads after a git change try the encoding the tab already had (`loadDocument(from:preferring:)`). Not persisted in the saved session, so a relaunch detects again. Saving a file with a BOM keeps the BOM. Tests: `TextFileEncodingTests`, `DocumentWriterTests`, `DocumentLoaderTests`.

- **File watching** (`IDEProjectWatcher.swift`, `Example/Umbra/FileWatching/`). Umbra has **one** watching engine: `IDEProjectWatcher`, one per window, the only creator of an FSEvents stream (`IDEFSEventStream`). Do not add another watcher (no `DispatchSource` file sources, no second FSEvents stream, no polling): subscribe in `IDEWorkspace.subscribeToProjectWatcher()` or take paths from it, as the project systems do through `IDEProjectSystem.filesDidChange(_:)`. One stream covers the project root plus the parent directory of each open file outside it (`setOpenFiles`, fed from `refreshPresentation`); a change in that set starts the new stream before stopping the old. Batches are coalesced 150 ms: `paths` (inside the root, in the root's spelling, never `node_modules`/`.build`…: the Explorer, git, local history, indexes, languages and project systems read these), `openFilePaths` (open files outside the root or under an ignored folder) and `gitMetadataChanged`. Tests: `IDEFSEventStreamTests`, `IDEProjectWatcherTests`.
- **External changes to open files** (`IDEOpenDocumentDiskSync`, `IDEWorkspace+ExternalChanges.swift`, `IDEExternalChangeBanner`; plan: `docs/EXTERNAL_FILE_CHANGES_PLAN.md`). The sync watches nothing: it judges the watcher's paths for open text tabs by content (`DiskSnapshot`: size and SHA-256; above 2 MB only the first and last 64 KB are hashed, so the modification date must match too) against a baseline read on open, reload and save, so Umbra's own save, a `touch` or rewriting the same bytes does nothing. Settings ▸ Editor ▸ External Changes (`IDEPreferences.externalChangePolicy`, `com.umbra.editor.externalChangePolicy`, kept on this Mac): **Reload Automatically** (`always`, default: a clean tab reloads, keeping each pane's caret and scroll), **Ask** (`prompt`: every changed tab gets the banner) and **Never Reload** (`never`: a notification that opens the file, no banner; the same bytes notify once). A tab with unsaved edits always gets the banner (Reload · Keep Mine · Compare; Keep Mine silences those disk bytes), and a deleted file gets Close Tab · Keep Editing (the buffer turns unsaved). Every text reload goes through `reloadDocumentFromDisk` (external changes, git branch switches and reverts, Reload from Disk, Reopen with Encoding). Saving over a file that changed since it was loaded asks Cancel · Overwrite · Compare (`saveConflictResolver`, replaceable in tests) under every policy; the agent's `saveBuffer` never asks, it refuses and raises the banner. The diff viewer's editable side does the same check on save (`IDEDiffSession.confirmOverwrite`: the working tree as the diff last read or wrote it, Cancel · Overwrite). Compare opens the diff viewer with the disk on the left and the buffer on the right. Hex tabs keep their own handling (`noteExternalChange`), fed by the same batches. Tests: `ExternalFileChangesTests`.

- **Hex editor** (`Example/Umbra/HexEditor/`, model in `Sources/HexKit/`). Known binary types and files whose first 8 KB sniff as binary open as a hex tab (`WorkbenchDocumentContentKind.binary`) instead of an encoding error. The view is a viewport of byte rows on a virtual row index; opening does not map or copy the file. Reopen as Hex and Reopen as Text switch either way, including unsaved edits. Preferences stay in the on-Mac hex domain, outside the shared snapshot. A binary tab does not feed the agent, language services, or Markdown run. Finder may list Umbra for `public.data` at Alternate rank and does not become the default handler. Details: `Sources/HexKit/CLAUDE.md`. Plan: `docs/HEX_EDITOR_PLAN.md`.

- **Inlay hints** (Settings ▸ Java ▸ Editor: Parameter Name Hints, Variable Type Hints, Lambda Parameter Type Hints, Use Editor Font for Hints; `IDEPreferences.javaInlayHints` / `javaInlayVariableTypes` / `javaInlayLambdaTypes` / `inlayHintsUseEditorFont`, all off by default). The editor asks for hints when any kind is on (`areInlayHintsEnabled`, applied in `IDEWorkspace` and `javaInlayHintsPreferenceChanged()`, which also refreshes), and the Java provider reads which kinds to produce through `JavaInlayHintProvider.setOptionsSource` → `IDEPreferences.currentJavaInlayHintOptions()` (straight from `UserDefaults`, since the provider is an actor). Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Layout & display; provider: `Sources/JavaIntelligence/CLAUDE.md`.

- **Code vision** (Settings ▸ Java ▸ Editor: Code Vision: Usages / Implementations; `IDEPreferences.javaCodeVisionUsages` / `javaCodeVisionImplementations`, both off by default because every label is a search). `IDEPreferences.apply(to: EditorIntelligenceController)` turns the lenses on (`codeVisionEnabled`, `areCodeVisionLensesEnabled`) and passes which labels are wanted (`codeVisionConfiguration`, a change re-requests them); `IDEJavaSupport.codeVisionProvider` (a `JavaCodeVisionProvider` sharing the Gradle scope and JDK of the other providers; it reads its options from `UserDefaults` through `IDEPreferences.currentJavaCodeVisionOptions()`) is handed to the controller in `IDEIntelligenceServices`. A click on `usages` runs Find Usages and one on `implementations` Go to Implementation at the declaration's name (`EditorIntelligenceController.handleCodeVisionClick`). The provider has no open-buffer lookup, so implementation counts follow saved files. Engine: `Sources/Penumbra/CLAUDE.md` ▸ Layout & display.

- **Sticky lines** (Settings ▸ Editor ▸ Sticky Lines; `IDEPreferences.showStickyLines` on by default, `maximumStickyLines` 5, `stickyLinesDisabledLanguages`; kept on this Mac, out of the snapshot). `IDEPreferences.applyStickyLines(to:)` (called by `apply(to: TextView)`) sets `showsStickyLines` unless the editor's `languageIdentifier` is disabled and fills the pinned lines' right-click menu: Configure Sticky Lines… opens Settings ▸ Editor (`requestedSettingsDomain` + `showSettings()` on the active workspace), Disable Sticky Lines and Disable for <language> update the preferences and repaint every window. The per-language switch is read when preferences are applied, so a language change on an open editor follows the next `apply`. Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Layout & display.

- **Font ligatures** (Settings ▸ Editor ▸ Typography ▸ Font Ligatures; `IDEPreferences.fontLigatures`, off by default, in the preferences snapshot with older files decoding to off). `applyTheme()` passes it to `IDEEditorTheme.rebuild(…ligatures:)`, which builds the theme font with `NSFont.withLigatures(_:)`; editor only (consoles and terminal keep their fonts). Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Layout & display.

- **Smart Keys** (Settings ▸ Editor ▸ Smart Keys; `IDEPreferences.insertPairedBrackets` / `insertPairedQuotes` / `insertClosingBraceOnEnter` / `insertClosingTagOnTagCompletion` / `autoCloseTagOnSlash`, all on by default, in the preferences snapshot with older files decoding to on). `IDESmartKeysConfiguration.make(language:switches:)` (`IDESmartKeys.swift`, pure) is the per-language table: no pairs for plain text, CSV, TSV, diff and gitignore; `<>` only for languages with generics; `'` not in Rust or Markdown; a backtick for JavaScript, TypeScript, Go, shell and Markdown; the closing brace on Enter for braced languages; tag closing for `html` (HTML void elements) and `xml` (XML rules). `IDEPreferences.applySmartKeys(to:)` copies it onto the editor from `apply(to: TextView)` and from the language switch (`applyLanguageInferredFromURL`, `setLanguage`, which now also sets `textView.languageIdentifier`). JSP's `%>` on Enter is not offered: Umbra has no JSP language. Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Editing & input. Tests: `IDESmartKeysConfigurationTests`, `IDESmartKeysPreferenceTests`.

- **Caret settings** (Settings ▸ Editor ▸ Caret; `IDEPreferences`): shape, color, Blink Caret, Blink Interval (100–2000 ms, default 500), Smooth Blinking and Smooth Movement (both on by default). They are in the preferences snapshot (older files decode to the defaults) and reach the editor through `apply(to: TextView)`; `IDEPreferencesLiveUpdateModifier` repaints open windows. Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Selection.

- **Code insight settings** (Settings ▸ Editor ▸ Code Insight and Refactoring; `IDEPreferences`, kept on this Mac and out of the preferences snapshot): Error Stripe and its mark height, Highlight Current Scope, Documentation on Hover, Tooltip Delay (default 500 ms; also paces the caret-rest popup, the fold preview via `TextView.tooltipDelay`, and AppKit's own tooltips through the `NSInitialToolTipDelay` default that `IDEPreferences.applyNativeTooltipDelay()` writes — AppKit may read it only at launch), Autoreparse Delay (`PenumbraWorkbenchEditorAdapter.contentRefreshDebounce`, which is the only debounce inspections wait on, plus the cold-`javac` and auto-import idle waits), Next Problem scope (F2 over all problems or the highest severity), In-Place Mode, Preselect Name on Rename (`IDERenamePrompt` selects the field's text), Confirm Inline Variable, and Suppress with Comment (`//noinspection` instead of `@SuppressWarnings`). `IDEPreferences.apply(to: TextView)` / `apply(to: EditorIntelligenceController)` push them; `IDEWorkspace.applyCodeInsightPreferences()` covers what lives below the views. A refactoring applied without a preview reports back through `onWorkspaceEditApplied` → `refreshAfterWorkspaceEdit`. Settings ▸ Inspections (`IDEPreferencesInspectionsPane`, `IDEPreferencesDomain.inspections`) lists every `JavaInspectionRule` by group with an on/off checkbox and a severity picker; `IDEPreferences.javaDisabledInspections` and `javaInspectionSeverities` store rule codes and only the deviations from each rule's default. The Inspections pane also has "Treat public API as used" (`IDEPreferences.javaTreatsPublicApiAsUsed`, on by default, reaches `JavaInspectionService.setProjectOptions`) for the project-wide rules, which run after a save through `IDEJavaSupport.compileNow`. Metric rules (`JavaInspectionRule.limit`: complexity, nesting depth, parameter count, method and class length) also get a stepper bound to `IDEPreferences.javaInspectionLimits` (rule code to value, only deviations), which reaches `JavaInspectionService.setThresholds`. A change goes through `IDEWorkspace.javaInspectionPreferencesChanged()` → `IDEWindowRegistry.applyCodeInsightPreferencesToAllWindows` → `IDEJavaSupport.applyCodeInsightPreferences`, which hands the new set to `JavaInspectionService` and, when it differs from what was applied, calls `onInspectionConfigurationChanged` so every window re-analyses its open Java files (`reanalyzeInspections`).

- **Debugger** (`IDEWorkspace+Debugger.swift`, `JavaDebugSession`, the JDI adapter in `Tools/JavaDebugAdapter`). Follows IntelliJ's breakpoint, stepping, tool-window, memory, overhead, stream-debugger and test pages. A Swift executable uses the same tool window through `DAPDebugSession` (`lldb-dap`: breakpoints, frames, variables, evaluate, step). A JavaScript or TypeScript file uses that session with js-debug: the server listens on a port, `startDebugging` opens the child connection, and that connection is the one that stops. `JavaDebugSessionBridge` is the thin `IDEDebugSession` wrapper; Java's own session API is unchanged.
  - *Breakpoints.* `JavaBreakpoint` has a kind (line, exception, method, field), a condition, a suspend policy (all, thread, none = log only), a "Breakpoint hit" message, a log expression, remove-once-hit and a pass count; `JavaBreakpointStore` also keeps a per-project mute flag, and old `breakpoints.json` files still load. A click on a line number adds one (lines with no code — blank, comments, imports, annotations — are refused), a click on a breakpoint removes it, F3 toggles at the caret (⌘F8 too in the IntelliJ keymap, through `IDESecondaryShortcutMonitor`, since a SwiftUI menu item holds one key), and the editor's right-click menu has Add/Remove Line Breakpoint. Right-clicking a breakpoint opens `IDEBreakpointPopover` (Enabled, Suspend All/Thread, Condition, More ⇧⌘F8); right-clicking another line offers Toggle, Add Conditional Breakpoint… and the line's Run/Debug items. The breakpoint replaces its line's number (`GutterDecoration.Placement.lineNumber`, so a click on it is a line-number click) and is drawn red (stops), orange diamond (log only), grey (disabled or muted), `?` for a condition and ✓ once the adapter placed it. Breakpoints follow edits through `TextView.gutterDecorationsDidMove` → `JavaBreakpointStore.moveLines`, and a line deletion removes its breakpoint. The Breakpoints tab lists line breakpoints by file and exception/method/field ones by kind, with a + menu, Mute, and `IDEBreakpointPropertiesForm` for the selected one. Every change is sent to a running session (`JavaDebugSession.sync`, diffed by id), so nothing needs a restart.
  - *Adapter protocol.* `setBreakpoint {breakpointId, kind, file/line | className + methodName/fieldName, condition, suspendPolicy, logMessage, logExpression, removeOnceHit, passCount, imports}` replaces by id; `clearBreakpoint`, `muteBreakpoints`; events `breakpointVerified` and `breakpointRemoved`. Method breakpoints are line breakpoints at each overload's first instruction (cheaper than method-entry events); exception and field ones are placed as their class prepares. A hit is judged on the evaluation executor, not the event loop (a condition may load classes, and class-prepare events must keep flowing); a condition that fails to evaluate stops with reason `conditionError`. A Suspend: Thread stop resumes only its thread; a second thread stopped meanwhile is shown after it. Other commands: `threads`, `selectThread`, `forceStepInto`, `smartStepInto {methodName}` (method-entry events on the stepping thread plus a step-over fallback), `runToCursor {file, line, force}`, `dropFrame`, `forceReturn`, `setValue`, `instanceCounts`, `instances` (objects pinned as `#id` until the program runs), `overhead`, `traceStream`. `stopped` carries `threadId`, `threadName`, `suspendsAll`, `breakpointId`, `message`.
  - *Evaluation.* `Evaluator.java` interprets expressions with JDI alone: operators with Java's promotion rules, string concatenation, casts, `instanceof`, ternaries, calls with overloads, boxing and varargs, static members of loaded classes, `new`, arrays and assignment; parsed trees are cached per breakpoint. Lambdas, method references and the like go to `CompilingEvaluator.java`: it compiles a class with one static method taking the frame's locals and `__self` (unknown names javac reports are rewritten to `__self.name`) against the program's classpath (sent in `launch`/`attach`, else the target's `java.class.path`) and the file's imports, defines it through JDI in the frame's own class loader and package, and caches it. Private members of other classes are out of reach there.
  - *Tests.* The test gutter button, Structure's context menu and Debug in Context debug tests: `IDEWorkspace.debugTests` runs `clean<Task>` then the task with `--debug-jvm` (an up-to-date task would start no JVM) and attaches like a Gradle run. A Maven project runs `mvn test` with Surefire's debug agent and attaches the same way. Results still land in Test Results. Test Results (`IDETestResultsPanel`) has Rerun, Rerun Failed, Debug Failed (a `JavaTestRunScope.tests` of `--tests` filters), Show Passed/Ignored, sort by name or duration, collapsible classes, and a detail pane with the message, a stack trace whose frames open their file, and the test's output (`JavaTestCaseResult.output`, from `system-out`/`system-err`).
  - *Debug tool window* (`IDEDebugPanel`). Toolbar: Rerun, Resume, Pause, Stop, Step Over/Into, Force Step Into, Smart Step Into, Step Out, Run to Cursor, Evaluate, Drop Frame, Trace Stream, View/Mute Breakpoints; a banner says why it stopped (exception, failed condition, thread-only stop). Frames has a thread picker and Hide Library Frames; Variables shows watches (per project in `UserDefaults`) above `this` and the locals, each an `IDEDebugValueRow` with Set Value (F2), Copy Value and Add to Watches. Memory counts instances per class at each stop while it shows, with the change since the last stop and the instances of a class ("track new instances" would need a JVM agent and is not offered); Overhead polls hits and time per breakpoint. The stopped line is not selected: the caret goes to its start and the line gets a dark-red `TextView.lineBackgrounds` band (`refreshExecutionLineBackgrounds`, for the selected frame; reapplied from `applyJavaGutter` because `setState` clears bands on a file switch). While stopped, the locals appear at the end of the lines that last mention them (`inlineValueHints`, `TextView.supplementaryInlayHints`). Run menu keys (IntelliJ column): Run to Cursor ⌥F9, Force Run to Cursor ⌥⌘F9, Smart Step Into ⇧F7, Force Step Into ⌥⇧F7, Show Execution Point ⌥F10, View Breakpoints ⇧⌘F8.
  - *Stream debugger.* Trace Current Stream Chain finds the pipeline on the stopped line (`JavaStreamChain`), evaluates it again with a `peek` after each stage through the compiling tier, and shows each stage's elements in `IDEStreamTraceWindow` (split mode links elements by time, `sorted`/`distinct` by identity; flat mode lists them). Side effects in the chain run twice, as in IntelliJ.

**Umbra** (`swift run Umbra`, `Scripts/build-app.sh`) is the Sublime Text–style editor product; `Example/Umbra` is its SPM executable target and source tree (app shell, views, `IDEWorkspace`, and `UmbraApp.swift`/`@main`). `Example/Umbra.xcodeproj` is a thin, separately maintained Xcode app project that compiles the same source files directly as a native app target — needed because a SwiftPM executable target can't host SwiftUI Previews (`ENABLE_DEBUG_DYLIB`); it's a dev convenience for Previews/Run/Debug only and isn't used for release builds. See `Example/README.md` for details.

## Windows and projects

Every window is one project (or none) with its own `IDEWorkspace`; native macOS tabs are just windows AppKit has merged. Plan, decisions and per-phase notes: `docs/PER_WINDOW_PROJECTS_PLAN.md`.

- **Scene and menus.** `IDEWindowScene` (`UmbraApp.swift`) creates the window's workspace and publishes a weak `IDEWorkspaceRef` with `focusedSceneValue(\.ideWorkspace, …)`. The menu bar (`IDEAppCommands.swift`) is built from that handle and resolves the workspace when an action runs; never capture the workspace itself in a menu closure (SwiftUI keeps menu items after a window closes, and the workspace stays alive with them). With no window focused the menus show a disabled item, except File ▸ New Window (⌘⇧N), New Window Tab, Open Folder… and Open Recent.
- **Finding a window.** `IDEWindowRegistry` keeps weak references, most recently key first. Use `workspace.window`, never `NSApp.keyWindow`, for sheets and first-responder changes. `IDEWindowChrome` (in `IDERootView.swift`) splits the top inset into titlebar and native tab bar so the toolbar row never sits under the tab bar.
- **Opening things.** Folders and files go through `IDEWindowRegistry.open(urls:origin:)` and the pure `IDEOpenRouter` (tested without AppKit): a folder that is already open focuses its window, an empty window takes it, a window with a project asks "New Window / Replace" (the `Open folders in` setting skips the question), Dock/Finder opens get a new window, and a file goes to the window whose project contains it. For a user-facing open call `openProjectFolder` / `replaceProject`, not `applyProjectRoot`. SwiftUI must not open windows for external events itself; see the comment on the scene in `UmbraApp.swift`.
- **Persistence** (`IDESessionStore.swift`). `IDEAppState` owns recents and the preferences snapshot (`app.json`) for all windows. `last-window.json` (`IDEWindowSession`) holds the layout of `IDEWindowRegistry.sessionWindow`: the most recently key window, skipping blank windows opened next to others. Only a window opened while no other is open restores it. Closing that window, and quitting, stores it with the folder closed: no project and no editor tabs, and any terminals in the home directory, so a Dock click opens the Welcome screen. A remaining window that still has a project saves its own layout instead. The old `session.json` is migrated once and left alone.
- **App-wide services** (`IDESharedServices`). Gradle trust, Maven trust (`maven-trust.json`), npm trust (npm-trust.json, separate from Gradle's), JDK selection, run configurations and breakpoints are single shared instances that re-read their file when it changed on disk; don't construct your own (each window used to rewrite the whole file and lose the others' entries). The JDK index and the dependency jars are indexed and parsed once for all windows (`JavaSharedShardHub`: `shard(for:)` for the JDK, `indexJars(_:)` / `readers(for:)` for jars; `IDEJavaSupport` sends jar targets through it and keeps project-source shards on its own scheduler). A window that only waits on another window's indexing still gets one progress event per jar. Release jars from Gradle/Maven caches keep their reader in a small bounded LRU after the last window lets go (`JavaJarCachePolicy`); everything else lives only while a window holds it, and every request checks the shard's stamp, so a rewritten jar is never served stale. The host drops the unused readers on memory pressure. Preference changes go through `applyPreferencesToAllHosts()`, which repaints every window. Notification entries and toasts stay per window; Do Not Disturb and the category switches follow `UserDefaults`.
- **Closing.** A closing window runs `IDEWorkspace.teardown()` (watcher, git, indexing, Gradle, debug session, terminal shells, scoped folder access) and must leave nothing that keeps the workspace alive. Things that have: replacing the window delegate without forwarding it to SwiftUI's (`IDEWindowCloseGuard` forwards everything), strong captures of the workspace in menu closures, and callbacks owned by a running terminal view. Quitting asks once about unsaved editors in every window. File ▸ Close Folder asks Save, Don't Save or Cancel when an editor has unsaved changes, then points every terminal at the home directory. A test that creates a workspace must set `IDEWorkspace.isSessionPersistenceEnabled = false` so it cannot touch real session files.
- **Xcode project.** `Example/Umbra.xcodeproj` compiles `Example/Umbra` through a file-system-synchronized group, so new, renamed and deleted Swift files need no project edit. It declares the same packages as the `Umbra` target (the root package, `GitIntelligence`, `SubprocessKit`, `AgentKit`, `AgentKitMLX`, SwiftTerm, DiagramKit); a new package dependency of the target must be added to the project too (Xcode: target ▸ Frameworks ▸ +, or edit `project.pbxproj`). Xcode cannot exclude a folder from a target, so what `Package.swift` excludes from `Umbra` (this file, `SplitView/LICENSE`/`README.md`, the debug adapter's sources and `.class` files) is listed file by file, and `java-debug-adapter.jar` is copied through an explicit Resources reference (a synchronized group skips file types it does not know). `Scripts/sync-umbra-xcodeproj.py` rewrites that list from disk: run it after `Tools/JavaDebugAdapter/build.sh` or when the `exclude:` list changes, `--check` verifies it. Build it with `xcodebuild -project Example/Umbra.xcodeproj -scheme "Umbra (Umbra project)" -destination 'platform=macOS' build` (xcodebuild names it that way because the root package has an `Umbra` scheme too; Xcode's own scheme menu shows both). The project's `Package.resolved` should agree with the root `Package.resolved`; compare them if a dependency moves.
