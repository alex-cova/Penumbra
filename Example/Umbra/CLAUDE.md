# Umbra (`Example/Umbra`)

Loaded when working under `Example/Umbra`. Moved out of the root CLAUDE.md.

- **`Umbra`** (`Example/Umbra`) — the macOS editor app shipped with this repo, intended as a **Sublime Text alternative**: lightweight, fast editing with project folders, split panes, symbol-aware navigation, session restore, a Problems panel (⌘⇧M; `IDEProblemsStore`/`IDEProblemsPanel`, a bottom-panel tab selected through `IDEBottomPanelTab`), and Java completion with Gradle module and dependency sync, hover with Javadoc, go to implementation, quick fixes, and saved run configurations (Java menu: Run Last Configuration ⌃⌥R, Edit Configurations…, Reformat Code ⌥⌘L, Optimize Imports, Show Context Actions ⌥↩; an "Optimize Imports on Save" preference, off by default). Build Project runs through the Gradle runner (asking for trust first) so its compiler errors land in the Problems panel (Sublime keymap by default). Find Usages results go to a Usages bottom-panel tab (`IDEUsagesPanel`, `IDEBottomPanelTab.usages`); Rename… (⇧F6 in the IntelliJ keymap) prompts for a name, shows a preview sheet (`IDERenamePreviewSheet`) and applies through `IDEWorkspaceEditApplier` (live buffers via `TextEditApplicator`, closed files written atomically inside the project folder). Finished Gradle syncs/builds and git actions are posted to `IDENotificationCenter` (`Example/Umbra/IDENotifications.swift`; the titlebar bell opens `IDENotificationPanel`, a toast announces each one — errors stay until dismissed — and live sync/indexing progress stays a separate `IDEStatusToast` card; Do Not Disturb and per-category switches persist in `UserDefaults`; `IDEWorkspace.notifications` / `notifyGradleSync` / `notifyGradleTasks` are the posting sites). Every split in the app (sidebars, structure and Gradle panels, editor over terminal, editor panes, list/detail panels) is a `SplitPanes` (`Example/Umbra/SplitView/`, vendored stevengharris/SplitView via Hextech; Umbra-specific edits in its `README.md`) — don't add `HSplitView`/`NSSplitView` or hand-rolled drag handles. The left sidebar is one card with a tab bar (`IDELeftSidebar`, `IDESidebarTab`: Explorer, Structure, Changes, Breakpoints, History; the selected tab shows its title, the others are icons; × in a tab's context menu closes it and the + menu reopens it; `IDEWorkspace.activeSidebarTab` / `showSidebarTab` / `toggleSidebarTab`, persisted in `IDEWindowSession.sidebarTab`/`closedSidebarTabs`). Changes is `IDEChangesPanel` (branch, commit, staged/unstaged files, diff preview; double-click opens a diff tab); the bottom panel's git tab is now History only (`IDESourceControlPanel`). The Explorer's ⋯ / right-click menu (`IDEExplorerOptionsMenu`, also in Settings ▸ Project) holds IntelliJ's view options: Flatten Packages, Hide Empty Middle Packages, Show Excluded Files (build outputs and `.gradle`, dimmed; on by default), Sort by Name/Type, Folders Always on Top and Always Select Opened File; the crosshair button is Select Opened File. They are presentation only, applied in `IDEFileTreeView.collect` through `IDEExplorerPresentation` (`IDEFlattenedPackages.swift`), so the tree is never rebuilt for them. Breakpoints is `IDEBreakpointsPanel` (see **Debugger** below), fed by `IDEWorkspace.breakpoints`, a mirror of `JavaBreakpointStore` refreshed after every change. Built on `Penumbra`, `EditorIntelligence`, and `JavaIntelligence`.

- **Diff viewer** (`Example/Umbra/Diff/`, `IDEWorkspace+Diff.swift`), after IntelliJ's Differences viewer. Diffs open as editor tabs: a `WorkbenchDocument` with `contentKind == .diff` (never restored with the session) whose `IDEDiffSession` lives in `IDEWorkspace.diffSessions`; the pane host lays `IDEDiffViewerView` over its editor while the tab is selected (`showDiffDocument`). An `IDEDiffRequest` names two `IDEDiffSource`s (a `GitRevision` of a path, the working tree, or fixed text). Entry points: double-click (or Show Diff) in the Changes list — unstaged rows compare index ↔ working tree, staged rows HEAD ↔ index, and Previous/Next File walk the rows of that section; the ↗ button over the sidebar preview; History's changed-files list under a commit (parent ↔ commit); Git ▸ Show Diff with HEAD / Compare with Branch / Compare with Clipboard, and the editor's context menu. The model is pure and tested (`IDEDiffComputer`: line LCS with whitespace policies none/trim/ignore/ignore + empty lines, then word, character or split highlighting inside changed blocks; `IDEDiffUnifiedLayout`; `IDEDiffPatchBuilder`). Two Penumbra `TextView`s show the sides with syntax colors (`TextView.lineBackgrounds` for the bands, `highlightedRanges` for words), `IDEDiffDividerView` draws the ribbons, the » chevron (left lines replace the right ones, ⌥-click appends; one undo step) and, for index comparisons, Stage / Unstage of one hunk (`git apply --cached --unidiff-zero`). Unified mode is one read-only text with old/new numbers in the annotation column. Toolbar: ⇧F7/F7 previous/next change (past the last change F7 moves to the next file), Previous/Next File, Jump to Source (F4), layout, whitespace and highlight menus, Collapse Unchanged Fragments (a `foldingProviderOverride` folding all but 3 lines around each change) and Synchronize Scrolling (viewport middles mapped through the chunks). The working-tree side is editable unless its editor tab has unsaved changes; edits are saved on ⌘S, when the tab is left or closed, and before switching files, then clean editor tabs reload. Every git refresh reloads open diffs; one whose texts did not change keeps its place. Options persist in `UserDefaults` (`umbra.diff.*`). Not done: three-way merge, aligned (padded) side-by-side, Compare Previous/Next File keys (⌃⌥←/→ belong to the terminal tabs). Tests: `IDEDiffComputerTests`, `IDEDiffPatchBuilderTests` (patches applied with real git), `IDEDiffTabTests`.
- **Changed lines** (`IDEChangeMarkers.swift`). A stripe just to the right of the line numbers marks lines that differ from `HEAD`: green for added, blue for modified, a red triangle where committed lines are gone. On by default inside a repository (Git ▸ Hide Changed Lines / Highlight Changed Lines, `UserDefaults` key `umbra.editor.highlightChangedLines`); off, or outside a repository, the column takes no width. Staged and unsaved edits both count, and the bar stays until the change is committed. `IDEChangeMarkerController` diffs the live buffer (`exportDocumentText()`, materialized off the main actor) against a cached `HEAD` blob (`IDEGitStatusModel.headContents`) with `IDEDiffComputer.lineChunks` (no word refine; a differing middle longer than 20,000 lines is one span). Typing moves the spans immediately and the diff replaces that guess after a short pause. A click does nothing. Tests: `IDEChangeMarkerTests`.
- **Diagrams** (`Example/Umbra/Diagrams/`, `IDEWorkspace+Diagram.swift`), built on [DiagramKit](https://github.com/alex-cova/DiagramKit) (the `Umbra` target's only user; import it only in `Diagrams/` and the workspace extension, since its names are short). UML class diagrams of Java code and Gradle dependency diagrams open as editor tabs the way diffs do: a `WorkbenchDocument` with `contentKind == .diagram` (never restored) whose `IDEDiagramSession` lives in `IDEWorkspace.diagramSessions`; the pane host lays `IDEDiagramViewerView` (an `NSHostingView` of `IDEDiagramRootView`) over its editor (`showDiagramDocument`), and `openDiagram(_:)` reuses the tab whose `IDEDiagramRequest.id` matches. Requests: `.classes(JavaClassGraphScope)` (file, package, types, project), `.gradleModules`, `.gradleLibraries(projectPath:configuration:)`. The graphs come from pure JavaIntelligence types (`JavaClassGraphBuilder`, `GradleDependencyGraph`; see its CLAUDE.md), `IDEDiagramDocumentBuilder` turns them into an `IDEDiagramDocument` (boxes keep content-derived ids, so selection and the viewport survive a reload) and `IDEDiagramLayoutEngine` places them (DiagramKit layouts; supertype edges are fed reversed so parents sit above). The session loads and lays out off the main actor and drops a result when a newer load started; the loaders are closures the workspace sets (index plus open buffers; the module graph from the synced model; the library graph from `IDEGradleProjectSystem.resolveDependencyGraph`, which shares `isBusy`, the trust prompt and the Gradle console with the other Gradle actions and caches by build-file fingerprint until Reload). A request is a value with an id. A language module or a project system implements `loadDiagram` and returns nil when the id is not its own; the workspace tries Java and Gradle first, then each module and each system. The npm dependency diagram and the one-file TypeScript class diagram are built that way. The canvas is `DiagramCanvasView` with Umbra's editor colour as background, SwiftUI boxes (`IDEDiagramNodeView`, above 200 boxes `DiagramSceneRenderer` draws them) and edges drawn by `IDEDiagramEdgeDrawing` with UML markers from `IDEDiagramEdgeMarkers` (hollow triangle for inheritance and realization, hollow diamond at the owner for aggregation, open arrow for association and dependency, filled arrow for Gradle links); Metal edges and partial scene rebuilds are not used. A JSON file uses the same titlebar play button as Markdown preview (⌘B): it covers the editor with a diagram of the value (`JSONDiagramBuilder`, source key order, 400 boxes) and is not a diagram tab. Double-click opens the source, the context menu offers Open Source, Show Diagram Around Type, Show Dependencies of Module and Copy Name. Toolbar: layout, edge routing, what is shown (members, private members, external types, neighbour depth, or the Gradle configuration), reload, export (PNG, PDF, SVG through `IDEDiagramExporter`) and zoom. Options persist in `UserDefaults` (`umbra.diagram.*`, `IDEDiagramSettings`). Entry points: Java ▸ Diagrams, the editor's context menu (Show Class Diagram), the Explorer's Show Class Diagram for a Java file or package folder, the Gradle sidebar (module diagram button, Show Dependency Diagram on a module), and palette commands. A Gradle module diagram reloads when a sync finishes. Tests: `IDEDiagramDocumentTests`, `IDEDiagramTabTests`, `JSONDiagramBuilderTests`.

- **CSV table preview** (`Example/Umbra/CSVPreview/`). A `.csv`, `.tsv` or `.tab` file (`LanguageIdentifier`: `csv`/`tsv`, no grammar, so plain text) gets the same titlebar play button as Markdown and JSON (⌘B, View ▸ CSV Table). It covers the editor with `IDECSVTableView`, a read-only virtualized `NSTableView` (row numbers, resizable columns, click a header to sort — natural order, numeric when the whole column is numbers —, ⌘C copies the selected rows, a double-click closes the table and puts the caret on the row's source line). A search field above the table (⌘F focuses it while the table shows, `IDEWorkspace.showFind`; Esc clears it, then returns to the table) hides rows with no cell containing the text (case- and diacritic-insensitive, 120 ms after typing stops), highlights the matches and reports "N of M rows match" in the footer; it keeps filtering across live re-parses. `IDEEditorPaneHost` owns it like the JSON diagram (`toggleCSVTable`, `noteCSVTableEdited` re-parses 200 ms after the last edit; the buffer is read after the pause and parsed off the main actor, a superseded result is dropped) and `IDEWorkspace.isCSVTableVisible` drives the button. `IDECSVTable.parse` is pure (RFC 4180 quoting, `\n`/`\r\n`/`\r`, blank lines skipped, ragged rows padded, first record is the header, at most `maximumRows` = 200,000 rows with a footer note) and `delimiter(forIdentifier:sample:)` picks comma, semicolon or tab from the first line. Tests: `IDECSVTableTests`.

- **File encoding** (status bar, `IDEStatusBarPanel.encodingPicker`; engine: `Sources/Penumbra/CLAUDE.md` ▸ Editing & input). The label left of `LF` is the active text document's `WorkbenchDocument.encoding` (`IDEWorkspace.statusEncoding`, set in `updateStatus`); clicking it opens two submenus over `TextFileEncoding.all`. **Reopen with Encoding** (`reopenActiveDocument(with:)` → `reloadTabFromDisk(_:in:encoding:)`) reads the file again in that encoding, asking first when the tab has unsaved edits and reporting bytes that do not fit (`IDEEncodingError`); **Save with Encoding** (`saveActiveDocument(with:)`) converts and saves, asking for a name when untitled, and keeps the old encoding when the save does not happen (a character the target cannot hold writes nothing). Opening auto-detects: a byte-order mark, else UTF-8, else a guess from the first megabyte (`TextFileEncoding.guess`, Windows-1252 for Western text, binary data still refuses to open). Reloads after a git change try the encoding the tab already had (`loadDocument(from:preferring:)`). Not persisted in the saved session, so a relaunch detects again. Saving a file with a BOM keeps the BOM. Tests: `TextFileEncodingTests`, `DocumentWriterTests`, `DocumentLoaderTests`.

- **Inlay hints** (Settings ▸ Java ▸ Editor: Parameter Name Hints, Variable Type Hints, Lambda Parameter Type Hints, Use Editor Font for Hints; `IDEPreferences.javaInlayHints` / `javaInlayVariableTypes` / `javaInlayLambdaTypes` / `inlayHintsUseEditorFont`, all off by default). The editor asks for hints when any kind is on (`areInlayHintsEnabled`, applied in `IDEWorkspace` and `javaInlayHintsPreferenceChanged()`, which also refreshes), and the Java provider reads which kinds to produce through `JavaInlayHintProvider.setOptionsSource` → `IDEPreferences.currentJavaInlayHintOptions()` (straight from `UserDefaults`, since the provider is an actor). Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Layout & display; provider: `Sources/JavaIntelligence/CLAUDE.md`.

- **Code vision** (Settings ▸ Java ▸ Editor: Code Vision: Usages / Implementations; `IDEPreferences.javaCodeVisionUsages` / `javaCodeVisionImplementations`, both off by default because every label is a search). `IDEPreferences.apply(to: EditorIntelligenceController)` turns the lenses on (`codeVisionEnabled`, `areCodeVisionLensesEnabled`) and passes which labels are wanted (`codeVisionConfiguration`, a change re-requests them); `IDEJavaSupport.codeVisionProvider` (a `JavaCodeVisionProvider` sharing the Gradle scope and JDK of the other providers; it reads its options from `UserDefaults` through `IDEPreferences.currentJavaCodeVisionOptions()`) is handed to the controller in `IDEIntelligenceServices`. A click on `usages` runs Find Usages and one on `implementations` Go to Implementation at the declaration's name (`EditorIntelligenceController.handleCodeVisionClick`). The provider has no open-buffer lookup, so implementation counts follow saved files. Engine: `Sources/Penumbra/CLAUDE.md` ▸ Layout & display.

- **Sticky lines** (Settings ▸ Editor ▸ Sticky Lines; `IDEPreferences.showStickyLines` on by default, `maximumStickyLines` 5, `stickyLinesDisabledLanguages`; kept on this Mac, out of the snapshot). `IDEPreferences.applyStickyLines(to:)` (called by `apply(to: TextView)`) sets `showsStickyLines` unless the editor's `languageIdentifier` is disabled and fills the pinned lines' right-click menu: Configure Sticky Lines… opens Settings ▸ Editor (`requestedSettingsDomain` + `showSettings()` on the active workspace), Disable Sticky Lines and Disable for <language> update the preferences and repaint every window. The per-language switch is read when preferences are applied, so a language change on an open editor follows the next `apply`. Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Layout & display.

- **Font ligatures** (Settings ▸ Editor ▸ Typography ▸ Font Ligatures; `IDEPreferences.fontLigatures`, off by default, in the preferences snapshot with older files decoding to off). `applyTheme()` passes it to `IDEEditorTheme.rebuild(…ligatures:)`, which builds the theme font with `NSFont.withLigatures(_:)`; editor only (consoles and terminal keep their fonts). Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Layout & display.

- **Caret settings** (Settings ▸ Editor ▸ Caret; `IDEPreferences`): shape, color, Blink Caret, Blink Interval (100–2000 ms, default 500), Smooth Blinking and Smooth Movement (both on by default). They are in the preferences snapshot (older files decode to the defaults) and reach the editor through `apply(to: TextView)`; `IDEPreferencesLiveUpdateModifier` repaints open windows. Engine side: `Sources/Penumbra/CLAUDE.md` ▸ Selection.

- **Code insight settings** (Settings ▸ Editor ▸ Code Insight and Refactoring; `IDEPreferences`, kept on this Mac and out of the preferences snapshot): Error Stripe and its mark height, Highlight Current Scope, Documentation on Hover, Tooltip Delay (default 500 ms; also paces the caret-rest popup, the fold preview via `TextView.tooltipDelay`, and AppKit's own tooltips through the `NSInitialToolTipDelay` default that `IDEPreferences.applyNativeTooltipDelay()` writes — AppKit may read it only at launch), Autoreparse Delay (`PenumbraWorkbenchEditorAdapter.contentRefreshDebounce` and `JavaInspectionService.setIdleDelay`), Next Problem scope (F2 over all problems or the highest severity), In-Place Mode, Preselect Name on Rename (`IDERenamePrompt` selects the field's text), Confirm Inline Variable, and Suppress with Comment (`//noinspection` instead of `@SuppressWarnings`). `IDEPreferences.apply(to: TextView)` / `apply(to: EditorIntelligenceController)` push them; `IDEWorkspace.applyCodeInsightPreferences()` covers what lives below the views. A refactoring applied without a preview reports back through `onWorkspaceEditApplied` → `refreshAfterWorkspaceEdit`. Settings ▸ Inspections (`IDEPreferencesInspectionsPane`, `IDEPreferencesDomain.inspections`) lists every `JavaInspectionRule` by group with an on/off checkbox and a severity picker; `IDEPreferences.javaDisabledInspections` and `javaInspectionSeverities` store rule codes and only the deviations from each rule's default. The Inspections pane also has "Treat public API as used" (`IDEPreferences.javaTreatsPublicApiAsUsed`, on by default, reaches `JavaInspectionService.setProjectOptions`) for the project-wide rules, which run after a save through `IDEJavaSupport.compileNow`. Metric rules (`JavaInspectionRule.limit`: complexity, nesting depth, parameter count, method and class length) also get a stepper bound to `IDEPreferences.javaInspectionLimits` (rule code to value, only deviations), which reaches `JavaInspectionService.setThresholds`. A change goes through `IDEWorkspace.javaInspectionPreferencesChanged()` → `IDEWindowRegistry.applyCodeInsightPreferencesToAllWindows` → `IDEJavaSupport.applyCodeInsightPreferences`, which hands the new set to `JavaInspectionService` and, when it differs from what was applied, calls `onInspectionConfigurationChanged` so every window re-analyses its open Java files (`reanalyzeInspections`).

- **Run gutter** — every `static void main(String[])` in a Java file gets a green `play.fill` gutter button (`JavaMainMethod.locations`, parsed off the main thread in `IDEWorkspace.refreshJavaTestDecorations`, cached per buffer generation); a test source gets `play.circle` on each test method and `play.circle.fill` on the test class's declaration. Runnable places in a file of another language come from that language's `IDERunProvider` as `IDERunnableLocation`s, started with `run(_:location:mode:)`. The buttons sit in the line-marker column right of the line numbers (`GutterDecoration.Placement.lineMarkerColumn`), in place of a marker on the same line; Java files reserve that column (`reservedLineMarkerSlots`, even with every gutter icon kind off) and no longer keep a decoration column on the left, and `.http` send buttons use the same column. A click opens `IDERunGutterMenu`: Run / Debug that `main` (a classpath launch of its binary name, so nested classes work, else the file's default launch, plus Modify Run Configuration…), or Run / Debug the test method or class. A breakpoint's line keeps its run button and the button takes priority: a click on it, right click included (`GutterLineClick.decoration`), opens the Run / Debug menus, while the breakpoint in the line number keeps its own clicks. Umbra's gutter has `gutterLeadingPadding` 6 (Penumbra's 2 plus 4) so numbers and breakpoints clear its left edge. The gutter itself is built in `IDEWorkspace+Debugger.swift` (`applyJavaGutter`).

- **Run / Debug / Stop** — in a Gradle project the titlebar play button runs the file's module's `run` task, else `bootRun` (Spring Boot), else asks which task to run (`IDEGradleTaskPickerSheet`) and saves the pick as a run configuration (`JavaRunConfiguration.preferredGradleRunTask`, `.gradleRun(projectPath:taskName:)`). Gradle runs go through the Gradle runner into the Gradle console with no timeout, so the `ladybug.fill` Debug button (`--debug-jvm`) and the `stop.fill` Stop button (`IDEWorkspace.stopRunning`, enabled while `isRunActive`) can control them. Classes and single files no longer use the terminal: see **Run tool window** below. A TypeScript or JavaScript file in a folder with a package.json runs the preferred npm script (`start`, otherwise the last script the user ran in that folder, otherwise the first). Debugging is not available for that language.

- **Run tool window and run configurations** (`Example/Umbra/Run/`, `IDEWorkspace+Run.swift`, `Languages/IDEJavaRunProvider*.swift`; model: `Sources/JavaIntelligence/CLAUDE.md`; the provider layer is described under **Project systems and run providers** below). The start/validate/pipeline code below is `IDEJavaRunProvider`'s (`startRunSession`, `runPipeline`, `prepareLaunch`); the window keeps the tab, the picker and the sheets. A class (`.classpathMain`) or single file (`.singleFile`) runs as an `IDERunSession` in the bottom panel's **Run** tab (`IDEBottomPanelTab.run`, `IDEWorkspace.runs`, one `IDERunSessions` per window): its own process group through `SubprocessRunner.start` with an interactive stdin, output coalesced every ~30 ms into an `IDERunConsoleLog` (chunks, so a prompt without a newline shows), stderr red, typed input echoed and sent (Return; ⌃D closes stdin), `at pkg.Cls.m(File.java:12)` frames as links (`IDEStackFrameReference`, `openStackFrame`). Stop is SIGTERM to the group, SIGKILL after 2 s (shutdown hooks run; exit 143 is shown as "stopped"); Rerun takes the same tab and waits for the old run to end (a port stays held until then) unless the configuration allows multiple instances. Gradle runs and tests keep the Gradle console and Test Results. `startRunSession` validates (`JavaRunConfigurationValidator`; a problem opens the dialog on it), then `runPipeline`: before-launch steps (`prepareLaunch`: Gradle tasks, or another configuration run to its end, cycle-guarded), the module's `classes` task when **Build before run** is on (or classes are missing), the JDK (`resolveRunJDK`: the configuration's `jdkHome`, else the project's), then `JavaLaunchCommand.makeProcessLaunch` (a program and arguments, never a shell string; `@argfile` for a long classpath on Java 9+). Debug of a classpath launch uses the same `prepareLaunch`, then `JavaManagedLaunch` (working directory, input file and argument lists go to the adapter). Gradle and test configurations run their before-launch steps through `runBeforeLaunchSteps`. Stop bumps `launchEpoch`, which a debug launch still preparing checks. Java 21+'s instance `main`, `main()` and compact source files are located by `JavaMainMethod.locations(in:fileName:)` and run with `--enable-preview` on Java 21 to 24 (plus `--source` for `java File.java`), plain on 25+, refused below 21 (`usesNewLaunchProtocol`).
  - *Configurations.* Running something (gutter button, Run in Context, ⌥↩, a test) records a **temporary** configuration (faded in the picker; the newest `Settings ▸ Java ▸ Run ▸ Temporary Configurations` (default 5) are kept, `JavaRunConfigurationCatalog.temporaryLimit`); Save Configuration (picker, Run ▸ Save Temporary Configuration, the dialog) or editing it keeps it. Tests are `.gradleTest` configurations (`JavaRunConfiguration.makeTestLaunch`, `recordTestRun`), so ⌃⌥R repeats a test. **Edit Configurations…** (`IDERunConfigurationsWindow`, a sheet from `IDERootView`): the list by kind and folder, the four kinds' templates, and a form (`IDERunConfigurationForm`); everything is edited in an `IDERunConfigurationsEditor` working copy and written by OK/Apply through `applyRunConfigurationEdits`. `runConfigurationDraft` is a request to open the dialog on a configuration (not saved yet → a new entry). A red ✕ in the picker and the list is `JavaRunConfigurationValidator` (file gone, unknown Gradle project or task, deleted before-launch step, JDK gone). **Store as project file** writes `.umbra/runConfigurations/<name>.json` (paths relative to the project, no JDK path; environment values are committed, which the dialog says); the project watcher refreshes the picker when those files change.
  - *⌥↩.* `IDERunCodeActionProvider` (the `umbra.run` language service for `java`, registered after Java's, so its actions follow `JavaCodeActionProvider`'s) offers Run / Debug / Modify Run Configuration on a `main`, a test method or a test class line as `CodeAction`s carrying a `CodeActionCommand`; `EditorIntelligenceController.onCodeActionCommand` → `performRunCodeAction`.
  - Tests: `IDERunSessionTests` (a fake `java` script), `IDERunWorkspaceTests` (a real JDK, skipped without one), `IDERunConfigurationsEditorTests`, `IDERunCodeActionTests`, `IDERunViewsSmokeTests` (renders the views; `UMBRA_VIEW_SNAPSHOTS=<dir>` keeps the PNGs).

- **Debugger** (`IDEWorkspace+Debugger.swift`, `JavaDebugSession`, the JDI adapter in `Tools/JavaDebugAdapter`). Follows IntelliJ's breakpoint, stepping, tool-window, memory, overhead, stream-debugger and test pages.
  - *Breakpoints.* `JavaBreakpoint` has a kind (line, exception, method, field), a condition, a suspend policy (all, thread, none = log only), a "Breakpoint hit" message, a log expression, remove-once-hit and a pass count; `JavaBreakpointStore` also keeps a per-project mute flag, and old `breakpoints.json` files still load. A click on a line number adds one (lines with no code — blank, comments, imports, annotations — are refused), a click on a breakpoint removes it, F3 toggles at the caret (⌘F8 too in the IntelliJ keymap, through `IDESecondaryShortcutMonitor`, since a SwiftUI menu item holds one key), and the editor's right-click menu has Add/Remove Line Breakpoint. Right-clicking a breakpoint opens `IDEBreakpointPopover` (Enabled, Suspend All/Thread, Condition, More ⇧⌘F8); right-clicking another line offers Toggle, Add Conditional Breakpoint… and the line's Run/Debug items. The breakpoint replaces its line's number (`GutterDecoration.Placement.lineNumber`, so a click on it is a line-number click) and is drawn red (stops), orange diamond (log only), grey (disabled or muted), `?` for a condition and ✓ once the adapter placed it. Breakpoints follow edits through `TextView.gutterDecorationsDidMove` → `JavaBreakpointStore.moveLines`, and a line deletion removes its breakpoint. The Breakpoints tab lists line breakpoints by file and exception/method/field ones by kind, with a + menu, Mute, and `IDEBreakpointPropertiesForm` for the selected one. Every change is sent to a running session (`JavaDebugSession.sync`, diffed by id), so nothing needs a restart.
  - *Adapter protocol.* `setBreakpoint {breakpointId, kind, file/line | className + methodName/fieldName, condition, suspendPolicy, logMessage, logExpression, removeOnceHit, passCount, imports}` replaces by id; `clearBreakpoint`, `muteBreakpoints`; events `breakpointVerified` and `breakpointRemoved`. Method breakpoints are line breakpoints at each overload's first instruction (cheaper than method-entry events); exception and field ones are placed as their class prepares. A hit is judged on the evaluation executor, not the event loop (a condition may load classes, and class-prepare events must keep flowing); a condition that fails to evaluate stops with reason `conditionError`. A Suspend: Thread stop resumes only its thread; a second thread stopped meanwhile is shown after it. Other commands: `threads`, `selectThread`, `forceStepInto`, `smartStepInto {methodName}` (method-entry events on the stepping thread plus a step-over fallback), `runToCursor {file, line, force}`, `dropFrame`, `forceReturn`, `setValue`, `instanceCounts`, `instances` (objects pinned as `#id` until the program runs), `overhead`, `traceStream`. `stopped` carries `threadId`, `threadName`, `suspendsAll`, `breakpointId`, `message`.
  - *Evaluation.* `Evaluator.java` interprets expressions with JDI alone: operators with Java's promotion rules, string concatenation, casts, `instanceof`, ternaries, calls with overloads, boxing and varargs, static members of loaded classes, `new`, arrays and assignment; parsed trees are cached per breakpoint. Lambdas, method references and the like go to `CompilingEvaluator.java`: it compiles a class with one static method taking the frame's locals and `__self` (unknown names javac reports are rewritten to `__self.name`) against the program's classpath (sent in `launch`/`attach`, else the target's `java.class.path`) and the file's imports, defines it through JDI in the frame's own class loader and package, and caches it. Private members of other classes are out of reach there.
  - *Tests.* The test gutter button, Structure's context menu and Debug in Context debug tests: `IDEWorkspace.debugTests` runs `clean<Task>` then the task with `--debug-jvm` (an up-to-date task would start no JVM) and attaches like a Gradle run; results still land in Test Results. Test Results (`IDETestResultsPanel`) has Rerun, Rerun Failed, Debug Failed (a `JavaTestRunScope.tests` of `--tests` filters), Show Passed/Ignored, sort by name or duration, collapsible classes, and a detail pane with the message, a stack trace whose frames open their file, and the test's output (`JavaTestCaseResult.output`, from `system-out`/`system-err`).
  - *Debug tool window* (`IDEDebugPanel`). Toolbar: Rerun, Resume, Pause, Stop, Step Over/Into, Force Step Into, Smart Step Into, Step Out, Run to Cursor, Evaluate, Drop Frame, Trace Stream, View/Mute Breakpoints; a banner says why it stopped (exception, failed condition, thread-only stop). Frames has a thread picker and Hide Library Frames; Variables shows watches (per project in `UserDefaults`) above `this` and the locals, each an `IDEDebugValueRow` with Set Value (F2), Copy Value and Add to Watches. Memory counts instances per class at each stop while it shows, with the change since the last stop and the instances of a class ("track new instances" would need a JVM agent and is not offered); Overhead polls hits and time per breakpoint. - **Local History** (`Example/Umbra/LocalHistory/`), after IntelliJ's. What a key does is a pure function (`IDEAgentComposerKeyMap`); what the text and caret ask for is another (`IDEAgentComposerTrigger.detect`: `/` as the message's first word, `@` at the start or after whitespace), tested without a view. `IDEAgentComposerState` holds the list's rows and highlight, `IDEAgentSuggestionList` draws it, and `IDEAgentController.suggestions(for:)` supplies the rows. `/commands` and `@` mentions are colored with attributes only; the model gets plain text. `@"path with spaces"` is the quoted form (`IDEAgentMentionToken`); files dropped on the field become mentions. Tests: `IDEAgentComposerFieldTests` hosts the field in a window.

- **Agent: IDE depth** (`IDEAgentGitTools`, `IDEAgentNavigationTools`, `IDEAgentEntryPoints`, `IDEAgentPrices`). `git_status` / `git_diff` read through `GitRepository` and are offered inside a repository (`IDEAgentGitSource`: paths are project-relative, `SecretFilePolicy` plus the user's globs filter every diff, an untracked `dir/` is expanded with `git ls-files --others --exclude-standard`). `go_to_definition` / `find_usages` take path, 1-based line and the identifier (`IDEAgentSymbolLocator`, whole-word, `occurrence` when ambiguous) and call `IDEAgentJavaNavigating`, implemented by `IDEJavaAgentNavigator` over the window's Java providers; they are offered when `agentJavaNavigator()` returns one (a Gradle project or an open Java file). `IDEAgentHost` gained `agentJavaNavigator()` and `agentLineText(url:line:)`, with defaults, so fake hosts need no change. Entry points: `IDEWorkspace.askAgentAboutSelection` (context menu item from `agentContextMenuItems`, palette command `agent.askAboutSelection`), `fixProblemWithAgent` (Problems row hover button and context menu) and `IDEAgentController.compose(_:send:)`, which fills the composer and focuses it (`composerFocusRequest`) or sends when consent is given and no run is going. The header shows `tokens · ~$cost` from `IDEAgentSettings.cost(of:)` and `IDEAgentPrices` (editable text in Settings ▸ Agent; `IDEAgentSavedTranscript` stores the total with the conversation; nil when any turn was unpriced). A closure stored on an editor's text view must hold its pane host weakly. An `.unreadableToolCall` event adds a notice ("…Asking it to try again"); the session has already told the model. Tests that need an editor view call `workspace.bootstrap()` first (it wires the adapter). Tests: `IDEAgentNavigationTests`, `IDEAgentEntryPointsTests`.

- **Agent: checklist and questions.** The controller adds `TodoTool` and `AskUserTool` to every session. `.todosUpdated` fills `IDEAgentController.todos`, shown by `IDEAgentTodoListView` under the header and saved in `IDEAgentSavedTranscript.todos` (restored into the new session when its history no longer holds the `todo` call). `.questionAsked` puts a `UserQuestion` on the `ask_user` card (`IDEAgentQuestionView`: option buttons, a field, Skip); `answer(callID:text:)` replies and `nil` skips. Tests: `IDEAgentInteractionTests` (the real-model one is opt-in).

- **Agent: web search** (`IDEAgentWebSearch`, AgentKit `WebSearchTool`). Off unless the Web search toggle is on (Agent Settings, and Settings ▸ Agent) and a Brave Search API key is saved under the Keychain account `api.search.brave.com`, separate from the model key. Both are in the session fingerprint, so a change starts a new session that keeps the conversation. The tool is `web_search`, placed after `show_file` and before the edit tools; it is read-only, so Plan mode keeps it. The query is sent to `api.search.brave.com` and the model gets titles, URLs and short snippets, marked untrusted. Nothing is fetched from those pages. A deny rule `web_search` blocks a call. Tests: `IDEAgentWebSearchTests`.

- **HTTP client** — `.http` parsing and sending live in the Umbra target (`Example/Umbra/HTTP/`: `HTTPRequestParser`, `HTTPTemplate`, `HTTPClient`, `HTTPCompletionProvider`), called from `IDEHTTPSupport`. File variables (`@name = value`, used as `{{name}}`; a later line wins and overrides an in-memory global), `> {% client.global.set("name", response.body.field); %}` (kept in memory for the window, not written to disk, and the log names the variable without its value), and dynamic `{{$random.uuid}}` / `{{$random.integer()}}` / `{{$timestamp}}` functions are substituted before the request is sent. Completion in `.http` files offers those names, methods, headers, `Basic` / `Bearer` / `Digest`, and the `# @no-redirect` / `@no-cookie-jar` / `@no-auto-encoding` flags; it is primary only at those sites, and a dot is part of the token only inside `{{ }}`. `Authorization: Basic user pass` is encoded, `Digest user pass` retries the 401 challenge, and `>>` / `>>!` save the response under the request's folder or `Application Support/com.umbra.editor/HTTPHistory`. A response that is not text (`HTTPResponseDownload.isText`: the declared type, else UTF-8 validity) and has no `>>` is saved to `HTTPHistory` automatically, named from `Content-Disposition` (else the URL, with an extension from the content type), never overwriting, and the log names the file. A protobuf response (`HTTPProtobuf.isProtobuf`: `application/x-protobuf`, `application/grpc*`, `application/connect+proto`…) is shown decoded without a schema, `protoc --decode_raw` style (fields by number, a trailing comment with the other readings of a value, gRPC/Connect envelopes split into messages), and the raw bytes are still saved as above. A `GRAPHQL` request line is sent as a `POST`, with `Content-Type: application/graphql` unless the file sets one. The log shows the request as sent (`HTTPClient.formatRequest`, dimmed) above the response. Cookies stay in the window's jar. There is no `HTTPClient` library, and JavaIntelligence does not depend on it.

- **Text tools** (`Example/Umbra/TextTools/`). The editor's right-click menu has a **Tools** submenu while text is selected, with one nested submenu per group (Encode / Decode, JSON, Case, Lines, Hash, Convert), and the command palette has the same commands (group "Tools"; with no selection they convert the whole document). Both are built from `IDETextTransforms.all` (`IDETextTransform.swift`): a registry of pure `(String, IDETextTransformContext) -> String?` transforms in six groups, so a new tool is one registry entry plus a pure function and its tests. Encoding: Base64, URL, HTML entities, hex, string escapes and Unicode escapes (`IDEBase64Text`, `IDEURLText`, `IDEHTMLText`, `IDEHexText`, `IDEStringEscapeText`, `IDEUnicodeEscapeText`). Base64 decoding accepts wrapped lines, the URL-safe alphabet and missing padding; URL encoding is `encodeURIComponent`'s, `+` is kept on decode; HTML decoding knows a small named table plus numeric entities and leaves an unknown one as written, one level only; hex is the UTF-8 bytes, decoding ignores whitespace, `:` and a leading `0x`; Escape String writes Java/JSON escapes (`\\ \" \n \r \t \b \f`, `\u00XX` for other control characters, non-ASCII untouched) and Unescape String also reads `\'`, `\/` and `\uXXXX` and refuses an unknown or unfinished escape; Unicode Escape turns every non-ASCII UTF-16 unit into `\uXXXX` and Unicode Unescape replaces well-formed ones and leaves the rest. JSON: Format and Minify (`IDEJSONText`) re-flow the characters as written instead of serializing again, so key order, number spelling and string escapes are kept; formatting uses the editor's indent strategy and keeps the line's own indentation on the following lines. Reformat Code (⌥⌘L) in a JSON file runs the same formatter through `IDEJSONFormattingProvider` (selection or whole file; invalid JSON is left alone), registered as the `umbra.json` language service next to Java's (`IDEIntelligenceServices.languages`; formatting is routed by the document's language). Case: UPPERCASE, lowercase, Title Case, and camelCase, PascalCase, snake_case, kebab-case and SCREAMING_SNAKE_CASE (`IDECaseText`; per line, acronyms and digits stay with their word). `IDEWorkspace.applyTextTransform` replaces every selection in one undo step through `TextView.replaceText(in: BatchReplaceSet)` and keeps the results selected; a transform that returns `nil` (not Base64, bytes not UTF-8, invalid JSON, a bad `%` escape) beeps and changes nothing. Lines: Sort Lines Ascending/Descending (natural, case-insensitive order), Remove Duplicate Lines (keeps the first), Reverse Lines, Remove Blank Lines and Trim Trailing Whitespace (`IDELineText`; `\n` or `\r\n` endings and a final line break are kept). Hash: MD5, SHA-1, SHA-256 and SHA-512 of the selection's UTF-8 bytes as lowercase hex (`IDEHashText`, CryptoKit; the selection is replaced by the digest). Convert (`IDEConversionText`, line by line, blank lines kept, one bad line refuses the whole selection): Unix Time to Date (12 or more digits are milliseconds; ISO 8601 UTC), Date to Unix Time (ISO 8601 with `Z` or an offset, a bare date, `yyyy-MM-dd HH:mm[:ss]`, times without a zone are UTC; each format must match the whole text, because `ISO8601DateFormatter` ignores trailing text) and Number to Hex / Binary / Decimal (`0x`, `0b`, `0o`, Java `_` separators and a trailing `L`). **Decode JWT…** (Encode / Decode submenu, palette "Decode JWT", which falls back to the clipboard) does not replace anything: `IDEJWTText` splits a token (a `Bearer ` prefix, quotes and whitespace are ignored; an encrypted five-part JWE is refused) and `IDEWorkspace.jwtDecoding` opens `IDEJWTSheet`, a read-only sheet in `IDERootView` with the formatted header and payload, `iat`/`nbf`/`exp` with relative times, a valid/expired/not-yet-valid status and the signature, which is shown and never verified; Copy, and Insert as Comment (the decoded text goes on the lines after the token and `TextView.toggleComment()` comments it with the file's own syntax, when it has one). Palette-only insertions (`IDETextInsertions`: Insert UUID, ISO 8601 timestamp, Unix timestamp) put a fresh value at every caret or over every selection in one undo step. Tests: `IDEBase64TextTests`, `IDETextTransformTests`.

**Umbra** (`swift run Umbra`, `Scripts/build-app.sh`) is the Sublime Text–style editor product; `Example/Umbra` is its SPM executable target and source tree (app shell, views, `IDEWorkspace`, and `UmbraApp.swift`/`@main`). `Example/Umbra.xcodeproj` is a thin, separately maintained Xcode app project that compiles the same source files directly as a native app target — needed because a SwiftPM executable target can't host SwiftUI Previews (`ENABLE_DEBUG_DYLIB`); it's a dev convenience for Previews/Run/Debug only and isn't used for release builds. See `Example/README.md` for details.

## Windows and projects

Every window is one project (or none) with its own `IDEWorkspace`; native macOS tabs are just windows AppKit has merged. Plan, decisions and per-phase notes: `docs/PER_WINDOW_PROJECTS_PLAN.md`.

- **Scene and menus.** `IDEWindowScene` (`UmbraApp.swift`) creates the window's workspace and publishes a weak `IDEWorkspaceRef` with `focusedSceneValue(\.ideWorkspace, …)`. The menu bar (`IDEAppCommands.swift`) is built from that handle and resolves the workspace when an action runs; never capture the workspace itself in a menu closure (SwiftUI keeps menu items after a window closes, and the workspace stays alive with them). With no window focused the menus show a disabled item, except File ▸ New Window (⌘⇧N), New Window Tab, Open Folder… and Open Recent.
- **Finding a window.** `IDEWindowRegistry` keeps weak references, most recently key first. Use `workspace.window`, never `NSApp.keyWindow`, for sheets and first-responder changes. `IDEWindowChrome` (in `IDERootView.swift`) splits the top inset into titlebar and native tab bar so the toolbar row never sits under the tab bar.
- **Opening things.** Folders and files go through `IDEWindowRegistry.open(urls:origin:)` and the pure `IDEOpenRouter` (tested without AppKit): a folder that is already open focuses its window, an empty window takes it, a window with a project asks "New Window / Replace" (the `Open folders in` setting skips the question), Dock/Finder opens get a new window, and a file goes to the window whose project contains it. For a user-facing open call `openProjectFolder` / `replaceProject`, not `applyProjectRoot`. SwiftUI must not open windows for external events itself; see the comment on the scene in `UmbraApp.swift`.
- **Persistence** (`IDESessionStore.swift`). `IDEAppState` owns recents and the preferences snapshot (`app.json`) for all windows. `last-window.json` (`IDEWindowSession`) holds the layout of `IDEWindowRegistry.sessionWindow`: the most recently key window, skipping blank windows opened next to others. Only a window opened while no other is open restores it. The old `session.json` is migrated once and left alone.
- **App-wide services** (`IDESharedServices`). Gradle trust, npm trust (npm-trust.json, separate from Gradle's), JDK selection, run configurations and breakpoints are single shared instances that re-read their file when it changed on disk; don't construct your own (each window used to rewrite the whole file and lose the others' entries). The JDK index and the dependency jars are indexed and parsed once for all windows (`JavaSharedShardHub`: `shard(for:)` for the JDK, `indexJars(_:)` / `readers(for:)` for jars; `IDEJavaSupport` sends jar targets through it and keeps project-source shards on its own scheduler). A window that only waits on another window's indexing still gets one progress event per jar. Release jars from Gradle/Maven caches keep their reader in a small bounded LRU after the last window lets go (`JavaJarCachePolicy`); everything else lives only while a window holds it, and every request checks the shard's stamp, so a rewritten jar is never served stale. The host drops the unused readers on memory pressure. Preference changes go through `applyPreferencesToAllHosts()`, which repaints every window. Notification entries and toasts stay per window; Do Not Disturb and the category switches follow `UserDefaults`.
- **Closing.** A closing window runs `IDEWorkspace.teardown()` (watcher, git, indexing, Gradle, debug session, terminal shells, scoped folder access) and must leave nothing that keeps the workspace alive. Things that have: replacing the window delegate without forwarding it to SwiftUI's (`IDEWindowCloseGuard` forwards everything), strong captures of the workspace in menu closures, and callbacks owned by a running terminal view. Quitting asks once about unsaved editors in every window. A test that creates a workspace must set `IDEWorkspace.isSessionPersistenceEnabled = false` so it cannot touch real session files.
- **Xcode project.** `Example/Umbra.xcodeproj` compiles `Example/Umbra` through a file-system-synchronized group, so new, renamed and deleted Swift files need no project edit. It declares the same packages as the `Umbra` target (the root package, `GitIntelligence`, `SubprocessKit`, `AgentKit`, `AgentKitMLX`, SwiftTerm, DiagramKit); a new package dependency of the target must be added to the project too (Xcode: target ▸ Frameworks ▸ +, or edit `project.pbxproj`). Xcode cannot exclude a folder from a target, so what `Package.swift` excludes from `Umbra` (this file, `SplitView/LICENSE`/`README.md`, the debug adapter's sources and `.class` files) is listed file by file, and `java-debug-adapter.jar` is copied through an explicit Resources reference (a synchronized group skips file types it does not know). `Scripts/sync-umbra-xcodeproj.py` rewrites that list from disk: run it after `Tools/JavaDebugAdapter/build.sh` or when the `exclude:` list changes, `--check` verifies it. Build it with `xcodebuild -project Example/Umbra.xcodeproj -scheme "Umbra (Umbra project)" -destination 'platform=macOS' build` (xcodebuild names it that way because the root package has an `Umbra` scheme too; Xcode's own scheme menu shows both). The project's `Package.resolved` should agree with the root `Package.resolved`; compare them if a dependency moves.

## Language modules

`Example/Umbra/Languages/` holds the chrome a language adds to Umbra, beside the intelligence its `LanguageService` provides (`Sources/EditorIntelligence/CLAUDE.md`). TypeScript intelligence lives in `Example/Umbra/TypeScript/` (`IDETypeScriptLanguageService` in `Languages/`). It is syntactic: a tree-sitter document parse through JavaIntelligence's `JavaSyntaxParser` / `JavaDocumentParseCache` (language `typescript`) plus a project index of `.ts`, `.mts`, `.cts` and `.tsx`. Relative imports resolve to indexed files, and member completion and go-to-definition follow a type annotation, `new`, or an import. It does not run `tsc` or `tsserver`, does not index `node_modules`, and does not parse JSX. `IDETypeScriptModule` contributes the npm run provider for TypeScript and JavaScript, the one-file class diagram, and a symbol-palette source from the in-memory `TypeScriptIndex`. An `IDELanguageModule` is a stateless value (`IDEJavaModule`, `IDEHTTPModule`, `IDETypeScriptModule`, and the chrome-only `IDEMarkdownModule`, `IDEJSONModule`, `IDECSVModule` in `IDEPreviewModules.swift`; listed in `IDELanguageModules.shipped`, with `register(_:)` / `unregister(id:)` for another) that contributes palette commands, a menu-bar menu, Settings pages, tool-window stripe entries, toolbar buttons (`IDEToolbarItem`, drawn by `IDEToolbarActionCluster`), status-bar items (`IDEStatusItem`) and View menu items (`IDEViewMenuContribution`); it takes the workspace as an argument and never keeps it. `IDEWorkspace.configurePalette` registers the commands where Java's used to start, `IDEAppCommands` shows `languageModuleMenu(for:)` (one line per built-in module: SwiftUI cannot build a menu bar from a list), `IDEPreferencesDomain` is a value type whose built-in pages are static members and whose module pages go between Project and Agent, and `IDEWorkspace.toolWindows` merges built-in and module entries by `IDEToolWindow.order` (`IDEToolWindow.Order`). `IDEBottomPanelTab` is a value (an id); a module's bottom tabs are `IDEBottomTabContribution`s (strip item, panel and `IDEBottomPanelTab.Order` position), merged into `IDETerminalTabsBar` and `IDETerminalPanel` (a contribution can bring its header `controls` and `staysWhenLastShellCloses`); select any bottom tab with `showBottomTab(_:)`, read it with `isBottomTabSelected(_:)`. `IDESidebarTab` is a `RawRepresentable` string (saved in sessions, so an id must never change) and each tab is an `IDESidebarTabDescriptor` (built-in ones in `IDESidebarTabs.builtIn`, Breakpoints from the Java module). Plan: `docs/LANGUAGE_SUPPORT_PLAN.md` (phase 4); guide: `docs/ADDING_A_LANGUAGE.md` §3. Tests: `IDELanguageModuleTests`, `IDEModuleContributionTests` (toolbar, status bar, View menu, bottom tabs, and a fake Ruby module registered end to end).

## Project systems and run providers

Plan: `docs/LANGUAGE_SUPPORT_PLAN.md` (phase 5). Both are per-window values made with the window's services, so a second language adds one of each without editing `IDEWorkspace`.

- **`IDEProjectSystem`** (`Example/Umbra/Projects/IDEProjectSystem.swift`): recognizes the open folder (`isActive`), syncs the project model after asking for trust (`syncState`: `IDEProjectSyncState`, generalized from the old `GradleSyncState`), keeps a console log (`IDEProjectConsoleLog`, rendered by `IDEProjectConsoleView`), lists its `tasks`, runs tasks and a build, reports `sourceRootPaths` and whether its build files changed (`hasConfigurationChanges`, the reload banner), and contributes its tool window (`toolWindows`, `bottomTabs`, `makeSidebar`). What it asks of the host (the trust prompt, "a sync failed", "a sync ended", "a task run ended") is an `IDEProjectEnvironment` of closures the window sets in `bootstrap()`; nothing in it retains the window. `IDEProjectSystems` (`IDEIntelligenceServices.projectSystems`) holds the window's systems in the order they claim a folder; `IDEWorkspace.projectSystems.active` is the first that recognized the folder and owns the right-hand sidebar; every match stays in `activeSystems`. The shared status line ("Indexing JDK 24…", "Resolving Gradle project…") is `IDEProjectStatus`, written by a project system and by Java's indexing; each writer clears only a message it set.
- **`IDEGradleProjectSystem`** is the first (`Projects/IDEGradleProjectSystem.swift`, split out of `IDEJavaSupport`): detection, the trust gate, `GradleProjectModelExtractor` sync with the cached-model fast path, `runGradleTasks`, the dependency graphs, the build-file watcher and the Gradle tool window (`IDEGradleSidebarPanel`, the console tab). `IDEJavaSupport` keeps the Java index and providers and is the Gradle system's `IDEGradleModelConsumer` (weak): it indexes every model the sync produces and clears what came from it. The two know each other because Gradle produces the model Java indexes; a Maven system would feed the same consumer. `IDEJDKSelection` is made by `IDEIntelligenceServices` and given to both.
- **`IDENpmProjectSystem`** (`Projects/IDENpmProjectSystem.swift`) is the second. It reads the root `package.json` (scripts and declared dependency names; parsing does not install packages and does not use the network), lists scripts as tasks, and runs `npm run <name>` through SubprocessKit. Trust is `npm-trust.json` and its own sheet. A decline on Reload is stored, and a decline while running a script is not; the script list stays. The last chosen script is remembered per folder, except the Build button, which runs `npm run build` only when that script exists. Its console and, when it is the active system, its sidebar are its own. The dependency diagram is the declared names.
- **Order on a folder change.** `applyProjectRoot` calls `projectSystems.projectDidChange(root:)` and then `languages.projectDidChange(root:)`, both synchronous, so Java sees what Gradle decided (`gradle.isActive`, `isLoadingCachedModel`: with a cached model the whole-tree index is skipped). `LanguageService` has `@MainActor projectDidChange(root:)` and `filesDidChange(_:)` hooks for this (default no-ops, `LanguageServiceRegistry` runs them in registration order); Umbra's Java service is `IDEJavaLanguageService`, which wraps `JavaLanguageService` and forwards both to `IDEJavaSupport`.
- **`IDERunProvider`** (`Run/IDERunProvider.swift`): what a language adds so Run, Debug, Run in Context and Stop work on its files — `canRun`/`canDebug`/help strings for the toolbar, `runnableLocations(in:)`, `run`, `runInContext`, `rerun`, `hasActiveWork`, `stop`, `projectTasksDidFinish`. A language module returns it from `makeRunProvider(for:)`; `IDEWorkspace.runProviders` builds them once per window and `activeRunProvider` picks by the active document's language. The process side is generic: `IDEProcessLaunch` (a program, arguments, directory, environment, optional input file), `IDERunRequest` (id, title, provider, payload, `prepare`) and `IDERunSessions.start(_:replacing:)`, which owns the "a rerun takes the tab, waits for the old process" rule; `IDERunSession` keeps a title, a provider id and an opaque payload instead of a `JavaRunConfiguration`.
- **`IDEJavaRunProvider`** (`Languages/IDEJavaRunProvider.swift`, `+Pipeline`, `+Tests`) is Java's: the run configuration derivation for the active file, validation, before-launch steps, the build, the JDK, Gradle run and test tasks, Run in Context, the ⌥↩ actions, and the compiler errors, test results and "build finished" notification a Gradle task leaves behind. It reaches the window only through `IDEJavaRunHost` (conformed to by `IDEWorkspace` in `IDEWorkspace+JavaRunHost.swift`), weakly. The debugger stays in the window (`IDEWorkspace+Debugger.swift`, Java-only) and asks the provider for the launch, the classpath, the JDK and `launchEpoch` (Stop bumps it).
- **Not generic yet**: debugging (it stays Java's; another language's gutter run buttons are `IDERunnableLocation`s), the run configuration picker and editor (all `JavaRunConfiguration`), and `javaFileCanTest` (test discovery is Java's). The run flags are generic now (`runFileCanRun`, `runFileCanDebug`, `runFileURL`, `runActiveFile`, `debugActiveFile`). The right-hand tool window is saved as `projectSidebarWidth` / `isProjectSidebarVisible` (an older `last-window.json` with `gradleSidebarWidth` / `isGradleSidebarVisible` still restores). The notification category is still `.gradle`: it is the user-facing name of a switch in Settings and belongs to the Gradle project system.
- Tests: `IDENpmProjectSystemTests` (manifest order, trust, a fake `npm`, the run provider, the class diagram, the symbol index, and Gradle staying active beside npm), `IDEGradleProjectSystemTests` (a fake `gradlew`; detection, trust, sync, cached start, cancel, task runs, the banner, the task list), `IDEProjectAndRunProviderTests` (the containers with fakes, `IDERunSessions.start`, the Java provider's answers, the folder reaching Java through the registry, and that none of it retains the workspace), `IDERunSessionTests`, `IDERunWorkspaceTests`.
