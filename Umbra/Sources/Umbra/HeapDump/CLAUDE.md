# Heap dump analyzer (`Umbra/Sources/Umbra/HeapDump/`)

Loaded when working here. Plan and later phases: `docs/HEAP_DUMP_PLAN.md`. Model: `Sources/JavaIntelligence/HeapDump/` (`HprofFormat`, `HprofByteReader`, `HeapDumpCensus`, `HeapObjectLayout`, `HeapDumpOverview`/`HeapHistogram`).

- **Phase 1 (shipped): summary and class histogram.** A `.hprof` opens as a heap dump tab (`WorkbenchDocumentContentKind.heapDump`, restored with the session when the file still exists, tab icon `memorychip`). `openDocument(from:)` routes by the `JAVA PROFILE 1.0.` magic (`HprofDetector.isHeapDump(at:)`) before `loadDocument`, right after the Flight Recorder check, so Reopen as Hex (`reopenHeapDumpAsHex`, the tab's ⋯ menu and its failure view) still reaches the bytes. Also File ▸ Open Heap Dump… and the palette's "Java: Open Heap Dump…" (`chooseHeapDump`).
- **Reading.** `IDEHeapDumpSession.load()` runs `HeapDumpCensus.read` in a detached task it stores and cancels itself (closing the tab, Cancel, Reload), because awaiting a detached task from another task would not pass the cancellation on. A newer load drops an older one's results by ticket; progress only moves forward (workers finish out of order). The census never maps the file: `pread` into one buffer per worker, segments in parallel, memory bounded by classes and strings (the 6.5 GB, 99 M-object IntelliJ dump: 0.6–1 s warm, under 300 MB peak, `swift run -c release PerfHarness heap-dump-census <file>`).
- **The tab** (`IDEHeapDumpView`): Summary (heap counts, GC roots by kind, file facts, the object layout with its evidence and an override picker, the ten largest classes, each a link into the histogram) and Histogram (a sortable `Table`: class or package, objects, shallow size, % of heap; filter by substring, or a `JavaClassPattern` when the text has `*`; double-click or Jump to Source opens a class through `openProfileFrame`, a package row filters to its classes; Copy Name / Copy N Rows as TSV). `visibleRows` is recomputed only when the grouping, filter, sort or layout changes, never in `body`.
- **Phase 2 (shipped): object graph.** The Histogram is a `SplitPanes` with `IDEHeapObjectsPane` trailing it, driven by `IDEHeapObjectExplorer` (`session.objects`, `@Observable`): the index's state (`checking`, `absent` with the disk estimate, `building` with progress and Cancel, `ready`, `failed`), the selected class row's instances (`showInstances(of:)`, the 1,000 largest; a package row or package grouping shows none, and changing the grouping clears the selection because row ids of one grouping name other rows in the other) over `IDEHeapInspectorView` (Fields: fields, statics with `<superclass>`/`<class loader>`, or the first 1,000 elements; Referrers: the first 200 with the field they come through, weak ones marked; double-click follows a reference, back and forward keep the path; Jump to Source). Building is the user's choice ("Build Object Index", also on the Summary's Object Index card with Delete Index), because it writes about as much as the dump to `Caches/com.umbra.editor/HeapDumpIndexes` (`IDEWorkspace.heapIndexStore`); an index that is already there and current opens by itself when the census finishes (`checkExisting`). The folder name follows the dump (path, size, mtime, inode), so an index whose dump moved, changed or went would never be opened again: `HeapIndexStore.sweep` removes those, indexes of an older format and builds that died (no `complete`, untouched six hours), then the least recently used (`last-used`, touched on every open) while all of them pass 30 GB, never the open tab's. It runs when a tab looks for its index and after every build. The build and every query run off the main actor: the build is a detached task the explorer stores and cancels (closing the tab), and instance pages and inspected objects are dropped by ticket when a newer pick overtook them; picking a new object clears the old fields at once (`isLoadingObject`) rather than showing them under the new title. Library side: `Sources/JavaIntelligence/HeapDump/` (`HeapIndexBuilder`, `HeapIndex`, `HeapIndexStore`, `HeapValueFormatter`). Release numbers on the 6.5 GB IntelliJ dump (`PerfHarness heap-dump-index <file>`): 99 M objects, 175 M references, built in 3.5–3.8 s warm with a 352 MB peak footprint, 4.9 GB on disk, reopened in 38 ms, an instance page or a referrer page in ~0.1 ms, a class's instances in the app in 0.14 s. A **debug** build (`./run.sh`) of the same index takes about three minutes.
- **Phase 3 (shipped): who keeps what alive.** Every index (format 2, 3 since the weak bucket) carries a dominator tree over strong references, rooted at the super-root (number 0, parent of the GC roots), so the views gain: a **Retained** column in the histogram (class grouping only: `IDEHeapDumpSession.retainedByRow`, filled once per index through `IDEHeapObjectExplorer.onIndexChanged`; a package's classes can dominate one another, so package rows have none) and in the instance list (which now lists the 1,000 that retain most); the **Dominators** mode (`IDEHeapDominatorsView`: the tree flattened into rows, `toggle` loads a node's children 100 at a time with a "Show N more" line, then the "Unreachable objects" row, expandable by class; the inspector beside it); inspector tabs **Path to Root** (the shortest strong path, each step with the field that holds the one below and the root's kinds) and **Retains** (the dominator subtree by class, loaded only when the tab shows); **Merge Shortest Paths to GC Roots** on a histogram row (a sheet; the 10,000 instances that retain most); the Summary's Reachable/Unreachable lines and Biggest Objects card. **Only weakly reachable** objects (a root reaches them only through a `Reference.referent`: weak, soft, phantom; caches live here) are their own bucket, never mixed with garbage: a second breadth-first pass over every reference, seeded in strong breadth-first order, finds them (index format 3; `HeapIndex.reachability(of:)` is `.strong`, `.weak` or `.unreachable`, `pathToRoot(of:includingWeak:)`, `weaklyReachableClasses`). The Summary has an "Only weakly reachable" line, Dominators an "Only weakly reachable objects" row above "Unreachable objects", the inspector says which of the three an object is, and Path to Root shows the weak path with the referent step marked "(weak)" (from the edge's own flag). Dominators, retained sizes and merged paths stay strong-only, since a referent keeps nothing alive. On the IntelliJ dump: 5,191 objects, 176 KB, mostly method-handle caches; 498 K objects, 29 MB of garbage. Shortest paths and merged paths use flat arrays, never a tree of objects that own each other: releasing a path thousands deep one level per stack frame overflowed a background thread's stack (`SIGBUS`, found on the real dump; `HeapDominatorTests.testDeepPathsDoNotRecurse`). Release numbers on the IntelliJ dump: the whole index in 11 s (the dominator pass 8.2 s, single-threaded), 350 MB peak footprint, 7.1 GB on disk, reopened in 43 ms; Retains of the 2.2 GB holder 1.4 s; merged paths of 10,000 instances 0.1 s. It shows the leak: `BuildConsoleViewHandler$1` retains 53 % of the live heap, through a `ConcurrentHashMap` of `ArrayList`s of `OutputBuildEventImpl` under `MultipleBuildsViewImpl` → `BuildView` → `BuildTextConsoleView`.
- **Phase 4 (shipped): reports and threads.** Modes **Reports** (`IDEHeapReportsView`) and **Threads** (`IDEHeapThreadsView`), each with the inspector beside it. *Leak suspects* (`HeapLeakSuspects.find`, threshold 10 % of the live heap): top-level dominators over the threshold, then classes whose many top-level instances add up past it; for one object the accumulation point is found by going down the heaviest dominator child while it keeps 80 % of its parent, with the most common class among what it keeps directly; the sentence follows MAT's (loader, share, accumulation, path to the root with repeats collapsed, `SemaphoreSegment ×18,974`, and a long chain cut to its ends). A class group has no accumulation point (its memory is spread), so it says what its largest instance keeps. Suspects load as soon as an index opens (`IDEHeapObjectExplorer.loadSuspects`), so the Summary shows a red strip with Show Report. *Inspections* (`HeapInspections`, run when Reports first shows, saved as `report-*.json` beside the index): duplicate strings (one flat array of hash/array/string entries sorted twice: no set or dictionary per group, since ten million strings would make millions), empty and sparse collections (`ArrayList`, `HashMap`, `LinkedHashMap`, `Hashtable`, `ConcurrentHashMap` without counter cells, `Vector`, `ArrayDeque`), and live primitive arrays of 1 KB or more that are all zeros. *Threads* come from the dump's STACK_TRACE/STACK_FRAME records and the thread-object, Java-frame and JNI-local roots (`HeapThreadBuilder` writes `threads.json` at build time, index format 4); names and states (`threadStatus` on `Thread` or its `holder`) are read at display; a frame's locals are listed under it and open in the inspector. Release numbers on the IntelliJ dump (`PerfHarness heap-dump-reports <file>`): suspects 1.4 s, duplicate strings 2.5 s (9.86 M live strings, 998 K distinct, 2.1 GB wasted on repeated Gradle test output), collections 0.2 s, zero arrays 0.16 s, threads 6 ms, peak footprint 477 MB. Findings: `BuildConsoleViewHandler$1` (53 %, accumulated in a `ConcurrentHashMap$Node[]`) and 921,481 `CancellableContinuationImpl` (22 %) queued on a coroutine `SemaphoreImpl`.
- **Phase 5 (shipped): getting dumps in.** *Live profiler:* Capture Heap Dump (a menu: live objects, after the full GC `jcmd GC.heap_dump` runs, or all objects with `-all`) writes `heap-<date-time>-pid<N>.hprof` to the heap dump folder and opens it (`IDEProfilerLiveMonitor.captureHeapDump`, `heapDumpDirectory`, `IDEProfilerSession.openHeapDump`; ten-minute timeout for big heaps). **Dumps Umbra makes go to `Application Support/com.umbra.editor/HeapDumps` (`IDEWorkspace.heapDumpFolder`)**: never the run's `snapshots/` (run folders are pruned at 500 MB per project, and one dump would both evict older profiles and be evicted itself) and never Caches (the system may empty it when the disk is low). Nothing prunes that folder; the dumps are the user's. *Out of memory:* a plain Java run whose VM options turn on `HeapDumpOnOutOfMemoryError` with no `HeapDumpPath` gets `-XX:HeapDumpPath=` that same folder (`JavaVMOptions.heapDumpPathArguments`, `IDEWorkspace.outOfMemoryHeapDumpFolder`, Settings switch). The Run console turns HotSpot's `Dumping heap to <path> ...` into a link (`umbra-heapdump:`, `IDERunConsoleView.Coordinator.linkHeapDumps`) that opens it, a relative path against the run's folder (`IDERunSession.workingDirectory`, `openPrintedHeapDump`). *Compressed dumps:* a `.hprof.gz` opens as a heap dump tab in phase `.compressed` with Decompress and Open (a stored, cancellable detached task; `HprofGzip.decompress` to `Caches/com.umbra.editor/DecompressedHeapDumps/<name>.hprof` (Caches: the archive can make it again) through a `.partial` file; the decompressed dump then replaces the tab, `replaceHeapDumpTab`); a decompressed copy newer than the archive opens at once. *Settings ▸ Java ▸ Heap Dumps:* index cache cap (default 30 GB, passed to every sweep), leak suspect threshold (10 %), the out-of-memory folder switch, disk use with Show Dumps in Finder and Clear Object Indexes (a sweep to 0 keeping this window's open indexes); kept on this Mac (`UserDefaults`), outside the preferences snapshot. Release: the IntelliJ dump gzip'd (1.3 GB) decompresses in 3.9 s with a 5 MB peak footprint, byte-identical; an autorelease pool per 1 MB piece is what keeps it flat (without it, 1.26 GB).
- **What the numbers mean.** Histogram counts and shallow sizes cover every object in the file, reachable or not (an OOM dump is not collected first; MAT drops garbage on open, so its totals are smaller). Retained sizes and the Dominators view count only what a strong path from a root reaches; the Summary's note says which applies. Shallow sizes come from the detected `HeapObjectLayout` (header and reference size inferred from address gaps between neighbours, since HPROF does not record it); the summary shows the share of gaps it predicts.
