- **Agent providers** (`Agent/ACP/IDEACPRegistry.swift`, `IDEACPProviderMenu`, `IDEACPSettingsSection`). Cursor Plan ↔ `plan`/`agent`, keeping a mode the user picked on Cursor's chip; Kiro has none). `acpProviderEntry` looks the entry up by `presetID`, so a row pointed at the user's own copy keeps these rules. **Model, effort and speed are one control**, `IDEACPModelPicker` (Codex-style: the chip reads ⚡ model · effort ›, its popover has the speed bolt and an effort slider with one stop per advertised level on top, the model list with the agent's descriptions below; While a run waits on the start, the status names the step (`IDEACPStartupStep`: "Starting <agent>…", "Loading the <agent> session…", "Starting a <agent> session…"), then "Thinking…". When a run ends, a tool card that never got a result is settled with an error outcome (`IDEAgentEntry.settlingUnfinishedCalls`; also when a saved chat loads), so nothing spins after a disconnect. A send waits for a start in progress (`acpPrepareTask`) instead of launching a second process, and a failed start leaves a notice with the reason. A chat with messages keeps its agent (`acpPin`, saved on the transcript); switching during a run leaves that run going and opens another chat. **Handoff after a lost session** (`IDEACPHandoff`, `IDEAgentConversation.acpPrompt`, `docs/harness/agent-harness-10.md`): when a chat with a transcript gets a new remote session (the agent cannot `session/load`, the saved session is gone, or no id was saved), the next prompt carries the earlier messages as an `<earlier-conversation>` text block before the message, once (`acpOwesHandoff`); a successful load clears it. A notice says how many were sent when some were left out. Switching agents from the header menu still opens another chat, but an idle chat's conversation goes with it (`carriedTurns`, "…continues “title”" notice) and rides with that chat's first message, on an ACP agent or Umbra Native. Native model controls stay for Umbra Native. An external agent's model or other select options appear only when that agent advertises them (`session/set_config_option`). Tests: `IDEACPRegistryTests`, `IDEACPTests`. `UMBRA_ACP_RECORD_DIR=<folder>` (environment only) records each agent process's ACP traffic, scrubbed, as `.jsonl` for replay tests (`IDEACPRecorder`; `docs/harness/agent-harness-11.md` item 3).

- **ACP adapters** (`Agent/ACP/Adapters/`, `Agent/Panel/IDEACPAdaptersSection.swift`; Settings ▸ Agent ▸ Adapters). Umbra installs, verifies, versions, updates, rolls back and removes the Codex and Claude Code adapters itself, in its own folder, with the user's approval. *Catalog* (`IDEACPAdapterCatalog`, code, not a downloaded manifest): `codex-acp` and `claude-agent-acp` are npm packages (`@agentclientprotocol/…`) with a pinned expected repository and publisher type; Gemini CLI and OpenCode are native CLIs that are only detected; versions are never listed, they come from the registry. *Layout* (`IDEACPAdapterStore`, `Application Support/com.umbra.editor/ACP`, 0700, owner-checked): `adapters/<id>/versions/<v>/` (a complete npm prefix plus `install.json`: integrity, registry key id, publisher, node path and version, sha-256 of the entry script, warnings), `staging/<uuid>/`, `active.json` (active and previous version), `npm/` (private cache, `HOME` and `npmrc`, cleared after each operation), `diagnostics/<id>.log` (scrubbed, 64 KB), `catalog.json` (a display cache of the last check, never trusted for an install). Activation moves the verified staging folder into `versions/` (an existing version is replaced by `renamex_np(RENAME_SWAP)`, so a launch never sees it missing) and writes `active.json` last, under a `flock`; `recover` removes interrupted staging and version folders without a valid `install.json` and repairs a damaged `active.json` from the newest verified version. *Pipeline* (`IDEACPAdapterInstaller`, an actor; states in `IDEACPAdapterMachine`: not installed, resolving, downloading, verifying, installing, ready, update available, updating, failed, disabled): `propose` fetches registry metadata and runs the trust checks **before anything is downloaded** and shows the approval sheet; `install` re-checks it against the approved integrity, checks Node and disk, runs `npm install --prefix <staging> <pkg>@<exact version> --ignore-scripts --no-audit --no-fund --omit=dev` as an argument array with a built environment, a private `HOME` and `npmrc`, then audits the tree (no symlink out of the prefix, no set-id, world-writable or special files; group/other write bits removed), checks `package-lock.json` (every package from `registry.npmjs.org` with an integrity, the adapter equal to the verified checksum), runs `npm audit signatures --json`, hashes the entry script, **starts the adapter once for an ACP `initialize`** (`IDEACPConnectionTest`, in a temp folder, only after verification), and only then activates. Any failure or cancellation removes staging and leaves the working version active. One install per adapter at a time; different adapters run together. *Trust policy* (`IDEACPTrustPolicy`): name, `_npmUser.trustedPublisher` and repository must match the catalog; the registry's ECDSA signature over `name@version:integrity` is verified with CryptoKit against a key **pinned in the source** (an unknown key id means "authenticity cannot be established" and nothing is installed; a rotated key needs an Umbra update); the SLSA provenance must name this package, this sha-512 and the catalog's repository. The DSSE envelope and certificate chain of the provenance bundle are checked by npm (`npm audit signatures`), not re-implemented. Install scripts are never run; any dependency that declares one is listed as a warning on the version. *Launch* (`IDEACPLaunchResolver`, pure): 1) the row's custom command, 2) the active managed adapter run as `<node> <entry>` with the node path recorded at install (falling back to `node` on `PATH`), 3) a system `codex-acp`/`claude-agent-acp` **whose `package.json` is the expected package**, 4) a native CLI's documented ACP mode. A provider CLI (`codex`, `claude`) is never treated as an adapter. `IDEACPTransport` re-verifies a managed entry right before spawn (`verifyEntryAllowingReinstall`: owner, no group/other write, regular file inside the version, sha-256 as recorded; tolerates only a same-version reinstall that happened between reading the manifest and launching) and holds an `IDEACPAdapterLeases` lease on that version until the process exits, taken before the check. *Across Umbra processes* the locks are `flock`s under `adapters/<id>/locks/` (`IDEACPFileLock`; the kernel drops them when a process dies): a lease also holds a shared lock on `version-<v>`, which removing or replacing that version takes exclusively and non-blocking (`withVersionUnused`), and an install holds `staging-<uuid>` exclusively (`makeHeldStaging`), so `recover` in another process skips a staging folder still being written and removes only crashed ones. Tests: the "Two Umbra processes" cases in `IDEACPAdapterStoreTests` (two stores on one folder, since `flock` conflicts per open file). *Updates* (`IDEACPAdapterManager`, `@MainActor @Observable`, `IDEACPAdapterManager.shared`): checks read the registry's `latest` and bulk advisories for the installed version only (a security update is one whose installed version has an advisory), at most every 6 h when Settings opens, daily, or only on request (`umbra.agent.acpAdapterUpdateCheck`); nothing installs without the approval sheet. Activating a new version never moves a running chat: the conversation fingerprint uses the row's launch identity (`adapter:<id>`), not the version, a process keeps its version for its lifetime, `removeVersion`/`remove`/replace refuse a leased version, and the next process start on a different version adds a notice ("… adapter is now X. This chat used Y before."). Restore Previous and Make Active only move `active.json`, after checking the target's manifest and entry hash. After an install the manager calls `IDEAgentSettings.adoptManagedAdapter` (creates the catalog row if absent, allows it, keeps every existing setting, secret and workspace default; a row on a custom command stays the user's). The App Store build (`APP_SANDBOX_CONTAINER_ID`) cannot run npm: managed installs are off there, with an explanation, and custom/system/native agents work as before. Limits: Node.js 22+ must be on the login `PATH` (Umbra does not manage a runtime); a full install is several hundred MB because the CLI engine binary comes with it; the hash covers the entry script and the folder's ownership, not every file; the pinned registry key must be updated by an Umbra release if npm rotates it. Tests: `IDEACPAdapterCatalogTests`, `IDEACPAdapterStateTests`, `IDEACPNodeRuntimeTests`, `IDEACPTrustPolicyTests` (real captured signatures and provenance in `Tests/UmbraTests/Fixtures/ACPAdapters`), `IDEACPAdapterStoreTests`, `IDEACPLaunchResolverTests`, `IDEACPAdapterInstallerTests` (fixture registry and a fake npm that lays down a tree), `IDEACPAdapterManagerTests`, `IDEACPManagedAdapterConversationTests` (real chats and processes over a fake managed adapter).
