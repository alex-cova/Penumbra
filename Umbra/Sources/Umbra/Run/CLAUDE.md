# Run, run configurations and tool window (`Umbra/Sources/Umbra/Run`)

Loaded when working under `Umbra/Sources/Umbra/Run`. Split out of `Umbra/CLAUDE.md`.

- **Run gutter** — every `static void main(String[])` in a Java file gets a green `play.fill` gutter button (`JavaMainMethod.locations`, parsed off the main thread in `IDEWorkspace.refreshJavaTestDecorations`, cached per buffer generation); a test source gets `play.circle` on each test method and `play.circle.fill` on the test class's declaration. Runnable places in a file of another language come from that language's `IDERunProvider` as `IDERunnableLocation`s, started with `run(_:location:mode:)`. The buttons sit in the line-marker column right of the line numbers (`GutterDecoration.Placement.lineMarkerColumn`), in place of a marker on the same line; Java files reserve that column (`reservedLineMarkerSlots`, even with every gutter icon kind off) and no longer keep a decoration column on the left, and `.http` send buttons use the same column. A click opens `IDERunGutterMenu`: Run / Debug that `main` (a classpath launch of its binary name, so nested classes work, else the file's default launch, plus Modify Run Configuration…), or Run / Debug the test method or class. A breakpoint's line keeps its run button and the button takes priority: a click on it, right click included (`GutterLineClick.decoration`), opens the Run / Debug menus, while the breakpoint in the line number keeps its own clicks. Umbra's gutter has `gutterLeadingPadding` 6 (Penumbra's 2 plus 4) so numbers and breakpoints clear its left edge. The gutter itself is built in `IDEWorkspace+Debugger.swift` (`applyJavaGutter`).

- **Run / Debug / Stop** — in a Gradle project the titlebar play button runs the file's module's `run` task, else `bootRun` (Spring Boot), else asks which task to run (`IDEGradleTaskPickerSheet`) and saves the pick as a run configuration (`JavaRunConfiguration.preferredGradleRunTask`, `.gradleRun(projectPath:taskName:)`). Gradle runs go through the Gradle runner into the Gradle console with no timeout, so the `ladybug.fill` Debug button (`--debug-jvm`) and the `stop.fill` Stop button (`IDEWorkspace.stopRunning`, enabled while `isRunActive`) can control them. Classes and single files no longer use the terminal: see **Run tool window** below. A TypeScript or JavaScript file in a folder with a package.json runs the preferred npm script (`start`, otherwise the last script the user ran in that folder, otherwise the first). Debug runs that file under node through js-debug (`dapDebugServer.js`, `UMBRA_JS_DEBUG_PATH` or `umbra.jsDebugPath`). A Swift file in a SwiftPM package runs its target's executable, or the package's only one (`IDESwiftRunProvider`: `swift build --product` through the SwiftPM project system, so compiler problems reach Problems, then `swift run --skip-build` as a Run-tab session); a file of a test target runs its tests, and the gutter runs one class or method. An executable target debugs through `lldb-dap` (`DAPDebugSession`, the Debug tool window). Tests do not.

- **Run tool window and run configurations** (`Umbra/Sources/Umbra/Run/`, `IDEWorkspace+Run.swift`, `Languages/IDEJavaRunProvider*.swift`; model: `Sources/JavaIntelligence/CLAUDE.md`; the provider layer is described under **Project systems and run providers** below). The start/validate/pipeline code below is `IDEJavaRunProvider`'s (`startRunSession`, `runPipeline`, `prepareLaunch`); the window keeps the tab, the picker and the sheets. A class (`.classpathMain`) or single file (`.singleFile`) runs as an `IDERunSession` in the bottom panel's **Run** tab (`IDEBottomPanelTab.run`, `IDEWorkspace.runs`, one `IDERunSessions` per window): its own process group through `SubprocessRunner.start` with an interactive stdin, output coalesced every ~30 ms into an `IDERunConsoleLog` (chunks, so a prompt without a newline shows), stderr red, typed input echoed and sent (Return; ⌃D closes stdin), `at pkg.Cls.m(File.java:12)` frames as links (`IDEStackFrameReference`, `openStackFrame`). Stop is SIGTERM to the group, SIGKILL after 2 s (shutdown hooks run; exit 143 is shown as "stopped"); Rerun takes the same tab and waits for the old run to end (a port stays held until then) unless the configuration allows multiple instances. Gradle runs and tests keep the Gradle console and Test Results. `startRunSession` validates (`JavaRunConfigurationValidator`; a problem opens the dialog on it), then `runPipeline`: before-launch steps (`prepareLaunch`: Gradle tasks, or another configuration run to its end, cycle-guarded), the module's `classes` task when **Build before run** is on (or classes are missing), the JDK (`resolveRunJDK`: the configuration's `jdkHome`, else the project's), then `JavaLaunchCommand.makeProcessLaunch` (a program and arguments, never a shell string; `@argfile` for a long classpath on Java 9+). Debug of a classpath launch uses the same `prepareLaunch`, then `JavaManagedLaunch` (working directory, input file and argument lists go to the adapter). Gradle and test configurations run their before-launch steps through `runBeforeLaunchSteps`. Stop bumps `launchEpoch`, which a debug launch still preparing checks. Java 21+'s instance `main`, `main()` and compact source files are located by `JavaMainMethod.locations(in:fileName:)` and run with `--enable-preview` on Java 21 to 24 (plus `--source` for `java File.java`), plain on 25+, refused below 21 (`usesNewLaunchProtocol`).
  - *Configurations.* Running something (gutter button, Run in Context, ⌥↩, a test) records a **temporary** configuration (faded in the picker; the newest `Settings ▸ Java ▸ Run ▸ Temporary Configurations` (default 5) are kept, `JavaRunConfigurationCatalog.temporaryLimit`); Save Configuration (picker, Run ▸ Save Temporary Configuration, the dialog) or editing it keeps it. Tests are `.gradleTest` configurations (`JavaRunConfiguration.makeTestLaunch`, `recordTestRun`), so ⌃⌥R repeats a test. **Edit Configurations…** (`IDERunConfigurationsWindow`, a sheet from `IDERootView`): the list by kind and folder, the four kinds' templates, and a form (`IDERunConfigurationForm`; its VM options field has a Common Options popover, `IDEVMOptionsPicker`, over `JavaVMOptions`); everything is edited in an `IDERunConfigurationsEditor` working copy and written by OK/Apply through `applyRunConfigurationEdits`. `runConfigurationDraft` is a request to open the dialog on a configuration (not saved yet → a new entry). A red ✕ in the picker and the list is `JavaRunConfigurationValidator` (file gone, unknown Gradle project or task, deleted before-launch step, JDK gone). **Store as project file** writes `.umbra/runConfigurations/<name>.json` (paths relative to the project, no JDK path; environment values are committed, which the dialog says); the project watcher refreshes the picker when those files change.
  - *⌥↩.* `IDERunCodeActionProvider` (the `umbra.run` language service for `java`, registered after Java's, so its actions follow `JavaCodeActionProvider`'s) offers Run / Debug / Modify Run Configuration on a `main`, a test method or a test class line as `CodeAction`s carrying a `CodeActionCommand`; `EditorIntelligenceController.onCodeActionCommand` → `performRunCodeAction`.
  - Tests: `IDERunSessionTests` (a fake `java` script), `IDERunWorkspaceTests` (a real JDK, skipped without one), `IDERunConfigurationsEditorTests`, `IDERunCodeActionTests`, `IDERunViewsSmokeTests` (renders the views; `UMBRA_VIEW_SNAPSHOTS=<dir>` keeps the PNGs).
