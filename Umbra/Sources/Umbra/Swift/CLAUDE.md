# Swift intelligence and SwiftPM (`Umbra/Sources/Umbra/Swift`)

Loaded when working under `Umbra/Sources/Umbra/Swift`. Split out of `Umbra/CLAUDE.md`.

- **Swift intelligence and SwiftPM** (`Sources/SwiftIntelligence/`, `Umbra/Sources/Umbra/Swift/IDESwiftSupport.swift`, `Languages/IDESwiftLanguageService.swift`, `IDESwiftModule.swift`, `IDESwiftRunProvider.swift`, `Projects/IDESwiftPM*.swift`; roadmap: `docs/SWIFT_INTELLIGENCE_ROADMAP.md`; scorecard: `docs/SWIFT_PARITY.md` once generated). Native and syntactic, like TypeScript, with no server process: `SwiftAnalysis.parse` runs JavaIntelligence's `JavaSyntaxParser(language: tree_sitter_swift())` on the original text. The grammar is tree-sitter-swift 0.7.4 (`Sources/TreeSitterSwift/VERSION`). It reads `nonisolated(unsafe)`, `#expect`, `#Preview` with `@available` in front of it, `await` on a call or a property in `if` / `while` / `where`, expression-valued `switch`/`if`, regex literals that include `\/` or start with an operator character, multi-pattern `case … where`, a leading `^` or `*`, an empty tuple `()`, `didSet` on an initialized property, a `///**` comment after an expression, `/*` and `*/` inside a line string, a raw string nested in another raw string's interpolation, and `(T?, Array<U>).self` (`SwiftModelTests.testModernSyntaxParsesAtTheOriginalOffsets`). Syntax problems are **warnings** (valid Swift outside this repository can still be rejected), and the compiler's errors come from the build. `SwiftModelTests.testRepositorySwiftFilesStayWithinTheSyntaxProblemCeiling` fails if a `.swift` file in this repository starts producing one. `SwiftModelWalker` is one iterative pass (explicit stack, depth cap: the index parses on a 512 KB cooperative-pool stack) producing `SwiftFileModel`: declarations (a `class_declaration` is class, struct, enum, actor or extension by its anonymous keyword), byte-range scoped bindings (`guard let` lives to the end of the block, `if let` in its body, `for`, closures, `catch`, `switch` patterns), uses with their receiver `SwiftChain`, imports and syntax problems. swift-syntax (`SwiftSyntaxDocument`, `SwiftSyntaxParseCache`, `SwiftSyntaxScopes`; only `SwiftIntelligence` links it, `ModuleBoundaryTests`) is the exact parse for work that runs after a pause, a save or on demand, never on a keystroke or in a completion/hover request (it is not incremental: 3 ms for 2,000 lines, 28 ms for 20,000, plus ~8 µs per reference for a scope lookup; `PerfHarness swift-syntax-parse`). `SwiftSyntaxScopeParityTests` keeps `SwiftFileModel.bindings` honest against `SwiftLexicalLookup` on this repository's Swift (13,411 references, all agree); the resolver itself stays on tree-sitter. `SwiftIndex` (actor) keeps the project's files, merges extensions across files and inheritance into `members(ofType:)`, filters by module (a `moduleResolver` the SwiftPM system supplies from its target directories; without one the folder is one module), and replaces a file's entry from the open buffer (`noteOpenDocument`, `LanguageEnvironment.openBufferText`) without a save. `SwiftResolver` types a chain from what the text states (annotations, constructor calls, written return types, casts, literals, `for` elements) and finds the declaration a name refers to, choosing the overload by call labels. It does not infer through generics or overloads, and the standard library and SDK are not indexed: `SwiftStandardLibrary` is a hand-written table of the commonest `String`, array, dictionary and number members so `name.` is not empty. Providers (all primary for `swift`, policy disables the generic snippets, duplicate-symbol warnings and name-based hover and navigation): completion (members with extensions, static members and enum cases, implicit `.case` from an annotation, argument label, return or `==`, scope, auto-`import`), hover, definition / usages / implementations / super method / type definition, rename (resolved uses only), syntax warnings, semantic colours, structure and breadcrumbs, signature help (`SwiftCallSite` reads the argument list from the text), line markers, type and call hierarchy, and Generate (memberwise `init`, `description`, `CodingKeys`). A call or dangling dot being typed is read from bytes first (`SwiftSite.textChain`, `SwiftCallSite`), because error recovery often leaves no node for it. `IDESwiftPMProjectSystem` is registered after npm; `Package.swift` is read with the Swift grammar on open (nothing runs), and `swift package dump-package` replaces that model only for a folder the user trusted (`swiftpm-trust.json`, `IDESharedServices.swiftPMTrust`, its own sheet). Commands run through SubprocessKit (`build`, `test`, `run:<exe>`, `resolve`, `update`, `clean`); their output is read by `SwiftBuildOutputParser` and goes to `onBuildDiagnostics` → `IDEProblemsStore.setBuildDiagnostics(_:source: "swiftpm")` (a bucket of its own, so a Gradle build never replaces it; it does not go through `environment.tasksFinished`, which Java's Gradle handling would read as a Gradle build). Tests run as `swift test --filter Module.Class/method --xunit-output …/TEST-swift.xml`, read by `JUnitXMLReportParser` into Test Results; `IDETestResultsStore.rerunHandler` is how Rerun and Rerun Failed repeat a run that has no Gradle scope. Parity: `SwiftParityCorpusTests` (`SWIFT_PARITY=1`; mutated valid sources labelled by `swiftc -emit-sil`, ratcheted in `Tests/PenumbraTests/Fixtures/SwiftParityCorpus/baseline.json`, regenerates `docs/SWIFT_PARITY.md` with `UPDATE_SWIFT_PARITY_BASELINE=1`) and the completion corpus (`Fixtures/SwiftCorpus/cases`; a `//! gap: <tag>` line marks a known failure that never fails the test). `SwiftSourceKitCeilingTests` (`SWIFT_PARITY=1`, skips without `sourcekit-lsp`) runs the same cases through a real server, in a folder with no `Package.swift`, and records `sourcekit-baseline.json`; a case that misses a name while the server's 200-item page is full is reported as inconclusive, not failed. The same file holds the real-server checks for the client: background-indexing progress in a SwiftPM package and a compiler fix-it as a quick fix through `LSPLanguageService`. SourceKit-LSP facts the client depends on: it answers nothing about a file it was never sent, so `LSPWorkspaceDocumentSync` (started by `IDELanguageServerHost` from the window's `Workspace`, full text per change, `swift` documents with a file URL only) is what makes any of the rest work, and `LanguageServerClient` resends a document's text before any request when its length differs from what the server holds (the editor's debounce lags the keystroke); `requestCompletionList` carries `isIncomplete` (a page of 200); the Symbols section is `IDEServerSymbolSource` (`workspace/symbol` while connected and answering, else the native index); it returns no code actions unless the client advertises `codeActionLiteralSupport`; it matches a fix-it's context diagnostic on range, message, severity and source, so `LanguageServerClient.requestCodeActions` sends its own published diagnostics at the position; An Xcode project (no `Package.swift`) gets the server through a compilation database that `IDEXcodeIndexDatabase` generates from `xcodebuild -showBuildSettingsForIndex` into `~/Library/Caches/com.umbra.editor/sourcekit/<hash>` (response files, one entry per file under every spelling of the folder) and names to the server by a *relative* search path counted between real paths (an absolute one outside the workspace is ignored, and the server resolves symlinks before the `..`); `IDEServerPreparation` stops the server from starting when it cannot be made (status "project not indexed"); Reload restarts it; `IDEXcodeProjectModel.moduleResolver()` gives the native index its module boundaries. Go to Definition on an SDK symbol returns a plain `file://` path to a generated interface (`<tmp>/sourcekit-lsp/GeneratedInterfaces/<hash>/*.swiftinterface`); `DependencySourceLocation.isGeneratedInterface` makes it a read-only dependency source with Swift highlighting, and the sync sends it so hover works inside. The status bar shows the server's work-done progress (`IDELanguageServerHost.serverWork`, `LSPWorkProgressTracker`). Tests: `SwiftModelTests`, `SwiftIndexTests`, `SwiftIntelligenceTests`, `IDESwiftPMProjectSystemTests`, `IDESwiftRunProviderTests`, `IDEProblemsStoreTests`.

- **Swift inspections** (`Sources/SwiftIntelligence/Inspections/`, `Umbra/Sources/Umbra/Settings/IDESwiftInspectionSettings.swift`; roadmap Phase 4). 28 rules over swift-syntax, run by `SwiftInspectionService` (one per window, owned by `IDESwiftSupport`) and shown as `swift-inspection` diagnostics next to the native `SwiftDiagnosticProvider`'s; the ⌥↩ fixes and the suppression comment come from `SwiftCodeActionProvider(inspections:)`. The parse is not incremental, so an analysis happens after the editor's content-refresh debounce, never on a keystroke, and a text over 1.5 MB is skipped. The choices are a `SwiftInspectionProfile` (`Sources/SwiftIntelligence/Inspections/Profiles/`: deviations from each rule's default plus ordered scopes for tests or a path glob, first match wins), kept in the `swift` section of the same profile files Java's use (`JavaInspectionProfile.sections` passes it through untouched; `JavaInspectionProfile.swift` in `Inspections/IDESwiftInspectionProfile.swift` reads and writes it; Default keeps it in the `com.umbra.editor.swiftInspectionProfile` key, seeded from the four flat keys Settings ▸ Swift used before profiles). The editor's analysis asks `IDESwiftInspectionResolver` (`IDESwiftSupport.inspectionResolver`: the active profile and the project root behind a lock) for the options of each file; `IDEWorkspace.applyCodeInsightPreferences()` hands it the active profile and, when that changed, asks every open editor for its diagnostics again. The "No highlighting (fix available)" severity draws nothing and lists nothing in the editor but keeps the fix on ⌥↩; Inspect Code still reports it. A rule reports only what the syntax proves; where a fix could be wrong for some type it is off by default (`count-is-zero`) or absent. A new rule needs a positive and a quiet test, its fix (if any) must pass `SwiftInspectionRepositoryTests`, and after adding one apply every fix to a copy of the repository (`SWIFT_INSPECTION_APPLY_FIXES_TO`) and build it. **Inspect Code** (Explorer, editor context menu, palette) runs `SwiftBatchInspector` into the same `IDEInspectionRun` as Java's, over `IDEInspectionFinding`; see `Umbra/Sources/Umbra/Inspections/CLAUDE.md`. `unused-declaration` is project-wide (`SwiftProjectNameLookup`, answered by `SwiftIndex`; Inspect Code behind "Include project-wide inspections", and in the editor from a save, an open or a profile change: `SwiftInspectionService` keeps the findings per file by text hash and merges them when the hash matches, so the next edit drops them, never on a keystroke). `unused-import` asks the index for each module's surface (`SwiftModuleSurface`, built from the indexed models; `nil` for the SDK and dependencies) and reports only a plain import nothing in the file mentions — code, comments or strings; its Remove import fix deletes the line, batched from Inspect Code. The commit check ("Analyze Code Before Commit") and the editor's problem-count badge cover Swift. A "Swift" menu (`IDESwiftCommands`) shows while a Swift file is selected. Tests: `SwiftInspectionTests`, `SwiftBatchInspectionTests`, `SwiftInspectionRepositoryTests` (root), `SwiftInspectionProfileTests`, `IDESwiftInspectionSettingsTests`, `IDESwiftInspectCodeTests`, `IDESwiftInspectionViewsSmokeTests`.

- **Swift refactorings** (`Sources/SwiftIntelligence/Refactoring/`; roadmap Phase 5). Syntax-only rewrites over swift-syntax, one file per refactoring, each returning byte-range edits or a reason it refuses: introduce variable, inline variable, `if let` ↔ `guard let`, add explicit type, move to extension, and change signature (reorder, relabel, rename, add and remove parameters through `IDESwiftSignaturePrompt`; calls found through `SwiftRenameProvider` and matched to the old parameters, an unsure one is left and reported). `SwiftRefactoringProvider` is registered in `IDESwiftSupport` as the language's `RefactoringProviding`, so the editor's own flow (name prompt, preview, apply) runs them; `IDEWorkspace.performRefactoring(_:)` and the `Swift: …` palette commands start one by id; `SwiftCodeActionProvider` offers the input-free ones at ⌥↩. A refactoring must refuse anything whose meaning or compile status it cannot guarantee (short-circuits, loop conditions, context-typed literals, closures of unknown result) and a file with a syntax error; a new one needs a case in `SwiftRefactoringCompileTests` (compiled before and after with `swiftc`) as well as exact-text tests. SourceKit-LSP's code actions cover the semantic ones. SourceKit-LSP's own refactorings (Extract Method, Extract Expression…) arrive as command-based code actions that `LanguageServerClient` resolves through `workspace/applyEdit`. Tests: `SwiftRefactoringTests`, `SwiftRefactoringProviderTests`, `SwiftRefactoringCompileTests`, `SwiftRefactoringRepositoryTests` (root), `LanguageCapabilityMatrixTests`.
