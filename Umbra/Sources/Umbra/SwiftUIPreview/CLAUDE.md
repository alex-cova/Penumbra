# SwiftUI preview (`Umbra/Sources/Umbra/SwiftUIPreview`)

Loaded when working under `Umbra/Sources/Umbra/SwiftUIPreview`. Split out of `Umbra/CLAUDE.md`.

- **SwiftUI preview** (`Umbra/Sources/Umbra/SwiftUIPreview/`, `IDEWorkspace+SwiftUIPreview.swift`; recipe and extractor in `Sources/SwiftIntelligence/SwiftPreview*.swift`; plan and measurements: `docs/SWIFTUI_PREVIEW_PLAN.md`, spike: `Tools/PreviewSpike/`). A Swift file in a SwiftPM code target gets the titlebar play button and ⌘B (View ▸ SwiftUI Preview; `toggleMarkdownPreview` routes there when `statusLanguage == "swift"`), which docks `IDESwiftUIPreviewPanel` beside the editor (a panel of `IDERootView`, left of the agent panel). `IDESwiftUIPreviewSession` (one per window, `IDEWorkspace.swiftUIPreview`) runs `SwiftPreviewBuildPlan`'s commands through SubprocessKit: `swift build --target <T>` in a scratch path of its own under `Caches/com.umbra.editor/SwiftUIPreviews/<hash>` (with `-enable-testing`, `-enable-implicit-dynamic`, `-enable-private-imports`, so the project's own `.build` is never touched and an unrelated target that does not compile does not matter), the host linked with every `.o` of the bin dir by one `swiftc` call, and the chosen `#Preview`'s thunk compiled to a dylib. The host (`SwiftPreviewHostSource`, a process of its own, a Unix socket with JSON lines: `load`, `render`, `mouse`, `quit`; client `IDESwiftUIPreviewHostConnection`) loads the thunk, draws it in an offscreen window and writes PNG frames (`CALayer.render(in:)`; the window has an explicit appearance). Every run has a generation and a socket path of its own; a result a newer run overtook is dropped. Trust is the SwiftPM folder trust (`IDESwiftPMProjectSystem.ensureTrusted()`, since the build runs the package's code). Compiler problems go to Problems under `IDEProblemsStore.swiftUIPreviewBuildSource`, with columns mapped through `#sourceLocation` to the user's own file. A save of the active Swift file refreshes (`noteSwiftUIPreviewDocumentSaved`): while the host runs and no other Swift file of the package changed, the file's current text is compiled as a thunk (`SwiftPreviewBuildPlan.ThunkMode.copy`: a copy of the file with its `#Preview` blocks blanked, so its types are new ones) and loaded into the host, about 0.75 s; the refresh button, another changed file or a host that stopped build the package. A replaced `body` in place was tried and dropped: SwiftUI aborts on the next state change when its type differs (see the plan, P2). A reload starts `@State` over. Switching tabs to another Swift file of a code target builds that file's preview after 300 ms (`noteSwiftUIPreviewActiveDocumentMayHaveChanged`, from `refreshPresentation`); a file that is not Swift leaves the canvas as it is. Each `#Preview` and `PreviewProvider` gets a blue eye in the gutter's marker column (`IDERunnableLocation.Kind.preview(index:)`, listed by `IDESwiftRunProvider.runnableLocations`; a click shows that preview, the right-click menu offers Show Preview; Run in Context ignores them). A view in an executable target works (`IDESwiftUIPreviewArtifacts` finds the per-file objects and leaves out the one that defines `main`). Input: `IDESwiftUIPreviewInputView` (an `NSView` over the frame, focus ring when it has the keyboard) sends mouse down/dragged/up, scroll-wheel and key events to the session, which turns them into host commands (`mouse`, `scroll`, `key`). The host does not synthesize scroll-wheel events: it finds the innermost `NSScrollView` under the point that can move that way and moves its clip view; text goes to the focused `NSTextInputClient` with `insertText`, editing keys are `doCommand(by:)` selectors (`IDESwiftUIPreviewInputView.keyAction` maps key codes), and ⌘C/⌘X/⌘V/⌘A are actions down the host's responder chain. Everything said to the host goes through one queue in the session (replies are matched by order) and only the newest frame is drawn. Input is followed by one more frame `IDESwiftUIPreviewSession.settleDelay` (450 ms) later, since a sheet attaches about 290 ms after the click and an animation runs on after the first frame. A sheet or alert is a window of its own: the host puts its window back offscreen whenever AppKit pulls it onto a screen (`NSWindow.didMoveNotification`), draws the sheets over the frame (dimmed window, rounded rect, shadow; they take the window's explicit appearance) and sends mouse, scroll and keys to the topmost sheet. Popovers and menus are not handled. Measurements: `docs/SWIFTUI_PREVIEW_PLAN.md`, P3. **Zoom and devices** (`IDESwiftUIPreviewDevices.swift`, pure and tested in `IDESwiftUIPreviewLayoutTests`): the canvas has Xcode's controls (− / level menu / +, and pinch; Fit or 25–400%). In the canvas size a zoom other than Fit changes the window (the panel divided by the zoom, so zooming out shows more of a layout that fills its window, and a view cropped by its own `.frame` comes into view) and the render scale follows, which keeps the bitmap at the panel's resolution; in any other size it only scales the frame (Fit never enlarges). The Size menu adds **Content Size** (the host measures the hosting view's ideal size with `sizingOptions = [.intrinsicContentSize]` for that render only, since the thunk turns sizing off, and replies `pointWidth`/`pointHeight`; at least 44 pt, at most 4096) and **iPhone** presets (`IDESwiftUIPreviewDevice.all`: logical sizes of the 16e, 16 through 17 and Air, and the SE) with a bezel, notch or Dynamic Island drawn by `IDESwiftUIPreviewDeviceFrame` (Device Frame toggle). A device is a size and a drawing: the host renders macOS SwiftUI, so controls, safe areas and fonts are not iOS's. Corner radii and bezels are approximations. Input points and scroll deltas are mapped back through the zoom (`IDESwiftUIPreviewLayout.framePoint`). **A device or window size replaces the preview's own frame**: when the body of the `#Preview` ends in a fixed `.frame(width:height:)` (`SwiftPreviewBuildPlan.outerFixedFrame`: only the last modifier, only numeric `width`/`height`/`alignment`), the thunk's copy of the body is generated without it (`Job.dropsOuterFrame`, blanked so lines and columns stay; the file is not touched), the canvas says "Ignoring .frame(…)" and the Size menu's "Keep the Preview's Own Frame" brings it back. Changing that decision loads a new thunk (`applyFrameChange`, the hot-reload path, about a second). A device also keeps the content inside its safe area (`safeTop`/`safeBottom`, render parameters the support module applies as plain padding: `safeAreaPadding` is ignored by `NavigationSplitView`), so nothing sits under the island. A `List` in a split view's sidebar is captured blank at every size (not caused by this). The panel's slider menu is the environment bar: Text Size (all twelve `DynamicTypeSize` cases), Language (a short list; the right-to-left ones turn Right to Left on), Right to Left, and Size (the canvas, or a fixed window from 320 × 240 to 1024 × 768; a `.fixedLayout` trait wins). They are render parameters (`dynamicType`, `locale`, `rightToLeft`) the host puts in `UmbraEnvironment` of the support module, which `UmbraPreviewRoot` applies with `.environment`, so a change re-renders without creating the views again. `Bundle.module` resources and asset catalogs work in the built preview and after a reload (`testBundleModuleResourcesAreFoundBeforeAndAfterAReload`: the copy thunk sees the module's accessor through `@testable import`). An Xcode project works too (`IDEXcodeProjectModel.targets(containing:)` maps a file to its non-test target through folder membership in `project.xcproj`, synchronized groups and Sources phases in `project.pbxproj`; `ensureTrusted()` is the Xcode trust): the build is `xcodebuild -target T -sdk macosx` for the host's architecture with `SYMROOT`/`OBJROOT` under the preview scratch directory (always the macOS SDK, since the host is a macOS process: an iOS app template built for `iphoneos` leaves iOS objects that fail to link and products in `Debug-iphoneos`; code that only exists on iOS then fails to compile, and the panel says the target is an iOS one, from `-showBuildSettings`' `PLATFORM_NAME`, ahead of the compiler errors; an `iphoneos` target is previewed in the iOS Simulator instead, see **iOS Simulator previews** below) (`SwiftPreviewBuildPlan.BuildSystem.xcode`), and every `Objects-normal/arm64/*.o` below it is linked (`IDESwiftUIPreviewArtifacts.locateXcode`; the `@main` object is left out as for SwiftPM). Dependencies the project builds as frameworks or packages are untested. Tests: `IDESwiftUIPreviewSessionTests` (a fake runner for the failure paths; with `UMBRA_PREVIEW_INTEGRATION=1`, a real package, host and frames); engine side: `SwiftPreviewExtractorTests`, `SwiftPreviewBuildPlanTests` (also the opt-in pipeline test).

- **iOS Simulator previews** (`IDESimulatorService.swift`, `IDESwiftUIPreviewHostBundle.swift`, `Sources/SwiftIntelligence/SwiftPreviewIOSHostSource.swift`; plan: `docs/SWIFTUI_PREVIEW_PLAN.md` §9, remaining work: `docs/SWIFTUI_PREVIEW_IOS_PLAN.md`, spike: `Tools/PreviewSpike/ios-simulator/`). A file of an Xcode target whose own platform (`xcodebuild -showBuildSettings`, `PLATFORM_NAME`) is `iphoneos` or `iphonesimulator` is not built for the Mac: `SwiftPreviewBuildPlan.Platform.iOSSimulator` builds it with `-sdk iphonesimulator` (scratch and work directories `…-ios`, so the two platforms' objects are never linked together), links the host into `UmbraPreviewHost.app` (a UIKit host with the macOS host's protocol; it must adopt the scene lifecycle or the iOS 27 SDK traps at launch), copies the built app's resources into that bundle, signs it ad hoc and runs it on a simulator device. `IDESimulatorService` is the only code that runs `simctl`: it finds or creates a device of its own named `Umbra Preview - <device type>` (never a device of the user's) on the newest runtime that meets the project's deployment target, boots it while the project builds, and shuts down only what it booted; the app is launched with `simctl launch --console` and `terminate()` also asks the device to end it. The session's connection, queue, generations and copy-thunk reload are the macOS host's. Environment: dark mode is the window's `overrideUserInterfaceStyle`; text size and layout direction are trait overrides on the window (UIKit and SwiftUI both follow); the locale is the support module's. The Size menu becomes a **Device** picker of the runtime's iPhone and iPad types (`session.simulatorDeviceTypes`); `setSimulatorDeviceType` on a running preview installs the host on that device (same runtime, at most two of the service's devices booted) and loads the thunk it had, with no build. Sizes, windows and "Keep the Preview's Own Frame" do not apply to a device window. Input (built, not yet run on a device; `testTapsScrollsAndTypingReachTheAppOnARealSimulator`) is public API from inside the app: `IDESimulatorService.boot` turns on the device's `ApplicationAccessibilityEnabled` preference (SwiftUI publishes its accessibility tree only to an app that launched with it on), and the host taps through an open menu's item (`UIButton.menu` → `UIAction.performWithSender`), a text field's focus, a `UISlider`/`UIStepper` value, then `accessibilityActivate()` of the smallest element under the point, then the `UIControl` there; scroll and drag move the innermost `UIScrollView` (a pull past the top runs the refresh control; a sideways drag on a row with custom actions offers them as a menu); keys go to the first responder. Every `ack` has a `route`, and a tap that came back `none` shows a hint. Drag and long-press gestures, `onTapGesture`, alert buttons and context menus have no public route, and the panel says "Limited input". Lifecycle: every session has an identity of its own (`IDESwiftUIPreviewSession.identity`) in its work directory (`work-<identity>` / `work-ios-<identity>` beside the project's shared scratch path), its socket and so its simulator app's bundle identifier; builds of one scratch path take turns (`IDESwiftUIPreviewBuildGate`); `work*` directories untouched for two days are removed by the next build in that project. The service keeps a lease count per device, shuts down a device it booted ten minutes after the last lease goes and at quit (`shutdownBootedByUsBlocking`), and uninstalls `com.umbra.preview.*` apps no work directory accounts for after a boot. A host that exits or is closed in Simulator is noticed at once (`IDESwiftUIPreviewHostConnection.onHostClosed`) and Refresh starts it again from what was built, with no build (`relaunch`). The service records the devices it boots with its process in a ledger, so a crash does not strand a device (the next launch adopts it and shuts it down when idle), and it sweeps stale apps just before an idle or quit-time shutdown as well as after a boot. The host answers `elements` (labelled accessibility elements and frames) for tests and has `UITabBarController`/`UINavigationController` fallbacks for the tab bar and back button. Settings ▸ SwiftUI Preview (`IDESwiftUIPreviewSettingsPage`, `IDESwiftUIPreviewSettings`): idle minutes for both hosts (an unused preview pauses with its last frame and Refresh starts it again; its device is shut down after the same time), when the simulator starts, which device families the menu offers, and the devices Umbra created with Remove. A failure in the panel can offer *Download iOS Runtime* (`xcodebuild -downloadPlatform iOS`), *Open Xcode* or *Get Xcode* (`IDESimulatorError.remedy`); `simctl` failures are classified (no Xcode, disk full, service gone with one retry), and a compiler and SDK from different Xcodes are flagged. SwiftPM packages work on the simulator too: a package that declares only iOS goes there, one that supports both stays on the Mac until the Device menu's choice (remembered per package root; the menu has a Mac entry), and it is cross-built with `--sdk`/`--triple` in `scratch-ios`; the products folder's `*.bundle` directories are copied into the host app (`Bundle.module` traps otherwise) and the donor app's carried `Info.plist` keys are merged. A build that fails for a missing module beside a workspace or Podfile says that `xcodebuild -target` ignores them. Not tried: a framework or library target of an Xcode project, packages inside one, embedded dynamic frameworks. Tests: `IDESimulatorServiceTests` (opt-in real device with `UMBRA_PREVIEW_INTEGRATION=1`).
