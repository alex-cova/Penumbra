# HTTP client (`Umbra/Sources/Umbra/HTTP`)

Loaded when working under `Umbra/Sources/Umbra/HTTP`. Split out of `Umbra/CLAUDE.md`.

- **HTTP client** — `.http` parsing and sending live in the Umbra target (`Umbra/Sources/Umbra/HTTP/`: `HTTPRequestParser`, `HTTPTemplate`, `HTTPClient`, `HTTPCompletionProvider`), called from `IDEHTTPSupport`. File variables (`@name = value`, used as `{{name}}`; a later line wins and overrides an in-memory global), `> {% client.global.set("name", response.body.field); %}` (kept in memory for the window, not written to disk, and the log names the variable without its value), and dynamic `{{$random.uuid}}` / `{{$random.integer()}}` / `{{$timestamp}}` functions are substituted before the request is sent. Completion in `.http` files offers those names, methods, headers, `Basic` / `Bearer` / `Digest`, and the `# @no-redirect` / `@no-cookie-jar` / `@no-auto-encoding` flags; it is primary only at those sites, and a dot is part of the token only inside `{{ }}`. `Authorization: Basic user pass` is encoded, `Digest user pass` retries the 401 challenge, and `>>` / `>>!` save the response under the request's folder or `Application Support/com.umbra.editor/HTTPHistory`. A response that is not text (`HTTPResponseDownload.isText`: the declared type, else UTF-8 validity) and has no `>>` is saved to `HTTPHistory` automatically, named from `Content-Disposition` (else the URL, with an extension from the content type), never overwriting, and the log names the file. A protobuf response (`HTTPProtobuf.isProtobuf`: `application/x-protobuf`, `application/grpc*`, `application/connect+proto`…) is shown decoded without a schema, `protoc --decode_raw` style (fields by number, a trailing comment with the other readings of a value, gRPC/Connect envelopes split into messages), and the raw bytes are still saved as above. A `GRAPHQL` request line is sent as a `POST`, with `Content-Type: application/graphql` unless the file sets one. The log shows the request as sent (`HTTPClient.formatRequest`, dimmed) above the response. Cookies stay in the window's jar. Sending a request (the gutter button, ⌃↩ / ⇧⌘R) first saves the file's unsaved edits (`IDEWorkspace.saveHTTPFileBeforeSending`; an untitled buffer is sent as it is, and the request is read from the buffer, so a cancelled or failed save does not stop it). There is no `HTTPClient` library, and JavaIntelligence does not depend on it.
  - *Bodies and templates.* A JSON or GraphQL body is highlighted by injection (`Sources/TreeSitterHTTPQueries/injections.scm`). Each pattern sets `injection.exclude` (an ICU regex, `Sources/Penumbra/CLAUDE.md` ▸ Syntax highlighting), so a `{{name}}` in a body is left out of the injected parse and the colors around it survive. `HTTPSemanticTokenProvider` (the `umbra.http` service's `semanticTokens`, one linear scan, off the main actor) colors `{{`, `}}` and the name inside, and splits a `###@scheme:` line into `@scheme` (keyword) and the URL.
  - *GraphQL schema* (`Umbra/Sources/Umbra/HTTP/GraphQL/`; tests `GraphQLSchemaTests`, `GraphQLCompletionContextTests`, `GraphQLSchemaStoreTests`, `HTTPGraphQLCompletionTests`, `HTTPSemanticTokenTests`). `###@scheme:<url>` (any number of `#`, at least three) names the schema for the requests below it, until the next such line, so one at the top covers the file (`HTTPGraphQLDirective`). The URL may use `{{variables}}` and may be an SDL file (`.graphql`, `.graphqls`, `.gql`, `.sdl`: GET), a `.json` introspection result (GET), a path or `file:` URL (relative to the `.http` file), or a GraphQL endpoint (POST of the standard introspection query, then a GET read as SDL or JSON when that fails). `GraphQLSchemaResolver` expands it and takes the headers of the first request below the line **only when that request goes to the schema's own scheme, host and port**, so an `Authorization` header is never sent to another server. `GraphQLSchemaStore` (an actor, `IDEHTTPSupport.graphQLSchemas`) never makes a completion wait: `schema(for:)` returns what is loaded and starts a load when there is none. A result is kept in memory and in `Caches/com.umbra.editor/GraphQLSchemas/<sha256 of the URL>.json`, a relaunch answers from that copy while a fresh one loads, a failure is remembered for 60 s and keeps the schema that was loaded, and the answer is capped at 20 MB / 15 s. It fetches by itself only `https`, `file:` and servers on this Mac (`GraphQLSchemaRequest.isAutomaticallyFetchable`); a plain `http` address elsewhere is read when the user runs **HTTP: Refresh GraphQL Schema** (palette and HTTP menu; it also reports the type count or the error in the HTTP Response tab). Loading starts from `refreshHTTPGutter` (once per buffer generation), the first completion and a hover. Hovering the directive line says whether the schema is loaded, loading or why not (`HTTPSchemaHoverProvider`). Completion (`HTTPCompletion.Site.graphQL`, primary only in a GraphQL body of a file that has a directive: a `GRAPHQL` request, or a body that starts with `query`/`mutation`/`subscription`/`fragment` or `{` not followed by a string) is `GraphQLCompletionContext`: the lexer's tokens before the caret and a stack of what is open, giving fields of the type being selected (aliases and inline fragments followed), argument names minus the ones given, enum values, `true`/`false`/`null`, `$variables` defined in the operation header, input object fields, type conditions, variable types and directives. A JSON object after the operation is the variables and gets nothing. The request-region scan behind it (`HTTPCompletion.scan`) counts brackets, so a `}` that closes something nested no longer ends the body. A provider reads the file through `Document.httpText`, never `Document.text`: a file-backed buffer keeps `text` empty and is read through its ranged reader (`HTTPGraphQLCompletionTests.testFileBackedBuffersCompleteFromTheirRangedReader`). Not done: validation against the schema, hover on query fields, and GraphQL inside a JSON `"query"` string.
