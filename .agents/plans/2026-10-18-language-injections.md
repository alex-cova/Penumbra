## Goal

Bring IntelliJ-style language injections to Umbra in scoped phases: persistent `// language=ID` comments plus a temporary Inject-language action first, highlighting only; intelligence inside injected fragments and a Settings rules UI later.

## Success Criteria

- A `language=ID` comment in the host language's comment syntax, on the line above a string literal or on the same line before it, highlights the literal's content with the named language: e.g. SQL keywords inside a JS string produce SQL captures, and the host `string` capture no longer paints the content range.
- A caret-in-string code action offers Inject language, applying a temporary highlight until the document closes.
- Auto `injections.scm` behavior (HTML/JS/Markdown/HTTP/C++) is unchanged when no manual injection exists; manual wins on overlap.
- No typing-latency regression per `docs/PERFORMANCE_RULES.md`; work stays bounded by visible rows/edit size.
- Intelligence (completion, diagnostics) in injected fragments is explicitly out of v1; fragments get colors only.

## Approach

Reuse the existing child-layer engine rather than adding a second highlighter. `TreeSitterLanguageLayer` (`Sources/Penumbra/TextView/SyntaxHighlighting/Internal/TreeSitter/TreeSitterLanguageLayer.swift`) already parses `@injection.content` ranges into child layers resolved through `TreeSitterLanguageProvider`, and Umbra already wires `BundledLanguageProvider` into every `TreeSitterLanguageMode` (`Example/Umbra/IDEWorkspace.swift`, `Self.languageProvider`). The missing pieces are range discovery (comments, temporary overrides), a manual-layer identity, and overlap suppression.

Key decisions and why:

- **Highlighting first, intelligence later.** Routing in `LanguageServiceRegistry` keys everything off `document.languageIdentifier`; serving completion/hover for a fragment needs synthetic fragment-documents and position mapping. That is a separate project from coloring ranges, so v1 stops at `TreeSitterLanguageLayer` child layers.
- **Pull, don't push, for temporary ranges; comments are discovered internally.** Add a `ManualInjectionProviding` protocol next to `TreeSitterLanguageProvider`: the root layer asks it for temporary ranges during `parseUsingReader()` and `updateChildLayers(applying:)`, exactly where it already asks for automatic injections, and merges them with comment ranges it discovers itself (step 3) at precedence temporary > comment > automatic. This keeps `TreeSitterLanguageMode`'s initializer additive (new optional parameter, default `nil`, so existing call sites and tutorials compile unchanged) and avoids threading a mutable store through three initializers.
- **Manual layers need their own identity.** `TreeSitterLanguageLayerStore` is keyed by `UnsafeRawPointer` taken from `capture.node.rawValue.id!` in `TreeSitterInjectedLanguageMapper` — a manual range has no tree-sitter node, so it cannot reuse that key. Give manual layers a separate store in the root layer keyed by a stable manual ID (document-scoped counter + language identifier), never mixed into the node-keyed store.
- **"Manual wins" means suppress, not stack.** `TreeSitterQuerySnapshot.captures(in:stringView:)` merges parent and child captures and sorts them; two layers over the same bytes would interleave unpredictably. Rule: an automatic injected language whose `textRange` overlaps a manual range (byte-range overlap, any intersection) is not created/kept for that node. Partial overlap suppresses the whole automatic node — splitting an automatic fragment around a manual one is out of v1.
- **No new storage for persistence.** IntelliJ's persistent form is the `// language=ID [prefix=.. suffix=..]` comment itself, so Umbra needs no settings file or per-document sidecar in v1. The parser accepts and ignores `prefix=`/`suffix=` (tokenize on whitespace/`=` the way `FenceLanguageName.normalize` already does) so later evaluation is additive.
- **Temporary injections live in Umbra, keyed by document.** One in-memory `[DocumentID: [ManualInjection]]`-equivalent store owned alongside `IDEWorkspace`'s other per-document state, passed to each pane's mode via the provider. It survives `setLanguage` mode reconstruction (same provider instance), and Umbra clears the entry when the document closes. Ranges are UTF-16 `ByteRange`s (the layer's native unit — `TreeSitterTextRange` bytes are UTF-16 code units × 2). Between full parses the root layer shifts its last-known manual ranges with each `TreeSitterInputEdit`, the same way `excludedIncludedRanges` is shifted in `applyEditPreservingIncludedRange`; the provider is only re-asked on a full parse or an explicit temporary-store mutation.
- **Unescape via the existing exclude machinery.** String literals carry quotes and escapes the injected grammar must not see. `TreeSitterInjectedLanguageMapper.ranges(of:excluding:)` already carves ranges out with `injection.exclude` (the HTTP `{{...}}` handling is the template). Extract that helper so manual fragments reuse it: fragment = string-content range, with host interpolation spans (`${...}` in JS templates, `\(...)` in Swift, `{...}` in Python f-strings) excluded by a small per-host pattern table. Accept imperfect edges beyond that table in v1.
- **One generic code action, picker in the host.** `RoutedCodeActions` only reaches languages that have a `LanguageService` claiming them, and most bundled grammars (Python, JS in plain files, …) have none in Umbra's registry — a per-language provider like `JavaCodeActionProvider` would silently never fire there. Follow the `umbra.run` precedent instead: register one `BasicLanguageService(name: "umbra.language-injection", languageIdentifiers: <all selectable grammar IDs>, providers: …)` in `IDEIntelligenceServices`, whose provider emits a single `Inject language…` action carrying a `CodeActionCommand(id: "umbra.injectLanguage")`. `CodeAction` has no submenu, so one action per language would flood ⌥↩; `IDEWorkspace.performCodeActionCommand` gains a case **before** its fall-through to `performRunCodeAction`, shows the existing `IDELanguageSupport.selectableSyntaxes` picker, writes the temporary store, and rebuilds the pane's language mode (explicit user action — a full reparse is acceptable, and it is not a keystroke path). Caret-in-string detection in the provider is a bounded scan of the caret's line(s) in `Document.text` (the EIP has no syntax tree); false negatives just hide the action.
- **Defer Settings UI, `@Language` annotations, prefix/suffix evaluation, and reference injections.** They are the long tail (persistence model, Java/Kotlin PSI-equivalent analysis, reference targets).

## Steps

1. **Override model in `Penumbra`.** Add a public `Sendable` value type for one manual injection (content `ByteRange`, normalized language identifier, source: comment vs temporary) and the `ManualInjectionProviding` protocol beside `TreeSitterLanguageProvider`. Thread the optional provider through `TreeSitterLanguageMode` → `TreeSitterInternalLanguageMode` → root `TreeSitterLanguageLayer`. No Umbra types leak into `Penumbra`; `EditorIntelligence` is untouched.
2. **Manual child layers in the root layer.** In `parseUsingReader()` and `updateChildLayers(applying:)`, after the `injectionsQuery` pass: drop automatic injections overlapping a manual range, then create/reuse manual child layers from the temporary provider plus comment discovery (resolving names through the existing `languageProvider`, so `FenceLanguageName` aliases like `js`/`yml` work), parse them over their content ranges, and shift/remove them on edits like automatic children. Manual children keep the shared `parser` and recurse into their own `injections.scm` for free.
3. **Comment discovery from the tree, not regex alone.** During the same two passes (never a standalone document scan): find comment nodes via the root tree, parse `language=ID` out of their text using the host's own comment delimiters (`lineCommentPrefix`/`blockCommentDelimiters` on `TreeSitterInternalLanguage`), then attach to the first string node starting after the comment ends on the same line or the next non-empty line. Content range = the string node's content child where the grammar has one (`string_content`, template body), else the node range minus its quote characters. Per-grammar node shapes are verified for JS/TS, Python, Java, Swift at minimum; a comment that attaches to nothing is ignored. Unknown IDs are ignored, never errors (provider returns `nil`).
4. **Bound the work.** Comment discovery runs only inside the existing injection windows: the full parse on open, and the padded edit window `updateChildLayers` already computes. No per-keystroke document walk, no `textView.text`, no line handles (`lineID(atRow:)`-style reads only) — per `docs/PERFORMANCE_RULES.md` rules 1–3. A document with no `language=` comment pays one substring check per comment node in the window.
5. **Umbra wiring.** Implement the provider over the temporary store only — comment discovery stays inside `Penumbra` (step 3) so split views of one document agree. Pass the provider at the existing `TreeSitterLanguageMode` construction sites in `IDEWorkspace` (initial load, `setLanguage`, `applyLanguageInferredFromURL`); keep `isLanguageLocked`/`setLanguage` semantics untouched. Clear a document's temporary entries on tab close.
6. **Inject action.** Add the provider + `BasicLanguageService` registration (step-decision above), the `umbra.injectLanguage` command case, and the syntax picker. Active only when the caret is inside a string literal with no existing manual injection on that range; choosing a language writes the temporary store and rebuilds the mode. No menu-bar or keymap change in v1 (⌥↩ is the entry point, matching IntelliJ).
7. **Tests.** New `Tests/PenumbraTests/LanguageInjectionTests.swift` on the `LanguagePackTests`/`testMarkdownFenceInjectsAliasedGrammar` pattern (`TreeSitterInternalLanguageMode` + `BundledLanguageProvider`, assert capture names): comment injection for SQL/HTML/JSON in at least two host languages, same-line and line-above attachment, temporary-over-comment-over-automatic precedence, unknown-ID no-op, edit inside/before a fragment invalidates and shifts correctly, interpolation excluded. Umbra-side picker/command behavior is manual-check only (no Umbra test target exists for it).

## Validation Plan

- Focused first: `swift test --filter LanguageInjectionTests`, plus existing injection coverage unmodified (`LanguagePackTests`, `MarkdownLanguageTests`, `HTTPLanguageTests`).
- Full suite with display awake: `caffeinate -u -d -i -s swift test`, watching the parse-sensitive suites named in the root `CLAUDE.md`.
- `swift run -c release PerfHarness enter-session synthetic --lines 20000` (and `120000`) on parent vs. change; Enter latency and `LineManager` handle counts unchanged.
- Manual check in Umbra: JS file with `// language=SQL` above a string (SQL colors, quotes keep host color), HTML/JS tagged template still correct, ⌥↩ Inject language applies, survives a syntax switch, and is gone after closing and reopening the tab.

## Risks / Open Questions

- String-literal node shapes differ per grammar; the comment-to-literal mapping needs per-language verification (JS/Python/Java/Swift at minimum) or some comments will attach to nothing. Mitigation: table-driven content-node lookup with quote-stripping fallback, tested per grammar in step 7.
- Escapes and interpolation (e.g. `${}` in templates) can break injected parses; mitigated by the exclude carving in the Approach, with imperfect edges accepted in v1.
- Viewport parsing: under `SyntaxParsePolicy/viewport` the root tree can be windowed, so a comment outside the parsed window yields no injection until a fuller parse lands. Accepted for v1 (same limitation as automatic injections); noted so it is not mistaken for a bug.
- Assumption, reversible: v1 ships no Settings page, no `@Language` support, no prefix/suffix evaluation, no reference injections, and no intelligence inside fragments. Say which to pull forward if the MVP scope is wrong.
