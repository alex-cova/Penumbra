# AgentEval

Loaded when working under `Tools/AgentEval`. Plan and background: `docs/AGENT_HARNESS_PLAN.md` (the eval CLI open item).

- **What it is** — a command line tool that runs scripted coding tasks through the same `AgentSession` Umbra uses and decides each trial by running the project's own tests. It runs against any provider (`ollama`, `openai`, `chat` for OpenAI-compatible servers, `mlx` for models installed through Umbra), so it is how to tell which local models can do the job and whether a prompt or tool-list change helped. Two targets: `AgentEvalKit` (task loading, sandbox, check runner, trial runner, report; tested) and `AgentEval` (arguments and provider construction; links MLX).
- **Commands** — `swift run AgentEval list`, `validate` and `run`; `swift run AgentEval help` prints every option. Typical: `swift run AgentEval run --provider ollama --model qwen-fixed:latest --trials 3 --json out.json --transcripts out/`. MLX needs the Metal library next to the binary, so run the built product (`.build/out/Products/Debug/AgentEval`, or `-c release`), and `--models-dir` points at a folder of installed models (default: Umbra's). Debug timings are fine here: the time is the model's.
- **A task** is a folder in `Tasks/<id>/`: `task.json` (`title`, `difficulty`, `prompt`, `check` shell command, `protected` globs, `timeoutSeconds`), `project/` (copied to a temp folder for every trial) and `solution/` (files laid over the project to make the reference solution). The current tasks are small Python projects checked with `python3 -m unittest discover -s tests -t . -q`, because Python needs no build step; the check may add `grep` conditions for what tests cannot see (a rename is complete, a helper exists). `tests/__init__.py` must exist or discovery fails for a reason that looks like a failing test.
- **`validate` is the guard on the task set.** Each task must fail untouched and pass with its reference solution, which must leave the protected files alone. Run it after adding or editing a task; `BuiltInTaskValidityTests` runs it in `swift test` and also checks that untouched projects fail because of their tests and not because they cannot run.
- **Scoring** — a trial passes only if the evaluator's own run of `check` exits 0 *and* no protected file (the tests) was changed, created or removed. The model's account of what it did is never used. A trial also records turns, tool calls and errors, tokens, seconds, how the run ended (`completed`, `step limit`, `timeout`, `repeated <tool>`, …) and the files changed; `--json` keeps all of it and `--transcripts` writes one readable file per trial (calls, truncated outputs, the final check).
- **Tools the model gets** — the generic AgentKit tools plus `run_tests`, which runs the task's own `check` and nothing else. There is no shell. `run_tests` is a deviation from the plan, which said the CLI would run the tests only after the task: a model that cannot run tests is measured on reading code, not on how Umbra's agent works (`--no-run-tests` measures that). `--toolset core` drops `apply_patch`, `todo` and `glob`; comparing it with `full` on a small model is how to decide whether local models should get a shorter tool list.
- **Local models** run one trial at a time (`--jobs` applies to hosted APIs only) and are asked for `min(--context or 32K, the model's maximum)`; sessions compact against that window.
- **Reading results** — a few trials per task say little about a model; use `--trials 3` or more before drawing a conclusion, and compare two settings on the same tasks. Models are not deterministic, and the check is deliberately small.
- **Not here** — grading the quality of the code (only the check is graded), Java/Gradle tasks (they would need a JDK and take minutes), and any web or network task.
